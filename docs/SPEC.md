# shitae — UI ラフスケッチ記述言語

> 下絵（したえ）。完成画の前の下描き。Figma や実装に入る前の、
> 画面・表示要素・インタラクション・遷移を、テキストで速く描いて AI と揉むための言語。

uiflow の精神（「見るもの／すること」を繋ぐ）を継ぎつつ、
画面と部品を **component** に統一し、AI との往復に最適化して再設計した。

---

## 設計原則

1. **ラフであることが機能**。穴・未定・自然文を許す。厳密さが要る段階に来たら、それは shitae の仕事ではない（状態機械なら XState 等に「降りる」）。
2. **専用記法を増やさない**。表現できないものは自然文で書く。未定も状態も注記も、自然文に開く。
3. **構造記号は構造のためだけ**。キーワードは transition verb・overlay verb・state verb のみ。見出し語を持たず多言語中立。
4. **画面と部品を区別しない**。すべて component。トップレベルで遷移グラフに乗れば「画面」に見えるだけ（SwiftUI の View と同じ）。
5. **インデントは意味を持たない**。構造はすべて明示的な記号（`#` `##` `>` `:` `*` `{}` `.` `->` `;` `[]` `@` `::` `?` `"..."` `//`）で表す。
6. **状態は条件式ではなく「variant」で表す**。「いつ何ができるか」は、変数とガードではなく、目に見えるバリエーション（variant）の列挙で表現する。

---

## two-layer model

shitae は 2 つの階層でできている。

- **component**（`#`）— 画面でも部品でもある、設計の単位。
- **バリエーション＝variant**（`##`）— 1 つの component が取りうる見た目の状態。読込中／表示中、など。
  variant は省略でき、variant を書かない component は「単一 variant だけを持つ」とみなす（＝従来の画面）。

同一ファイル内の同名 component の二重定義、同一 component 内の同名 variant の二重定義はエラー。

各 variant は **要素行**（何が見えるか。`>` を伴わない行）と **インタラクション行**（何ができるか。行頭に `>` を置いた行）からなる。`>` の後の空白・インデントは意味を持たない（原則 5）。`>` 行に `->` を含めば新しいインタラクション（行動→結果）の開始、含まなければ直前のインタラクションの結果列（result-list）の継続行になる。先行するインタラクションが無い継続行は構文エラー。継続行が探す「先行するインタラクション」は同一 single-body 内に限る——`#`/`##` を跨いだ時点で構文エラーになる。

要素行とインタラクション行は**自由に混在してよい**（行頭の `>` の有無で行が自己記述されるため、区切り記号は要らない）。正準形・推奨は「要素行を先にまとめ、インタラクション行を後にまとめる」書き方で、lint はこの整列を提案してよい（エラーにはしない）。

`##`（最初の variant）より**前**に書いた要素・インタラクションは、**全 variant に共通**する部分になる。各 variant は「共通部分 ＋ その variant 固有の部分」として描かれる（共通が先、固有が後）。共通部分は省略できる。`##` を 1 つも書かなければ、その component は「単一 variant だけを持つ」（＝従来の画面）。

```
# component名
（共通要素行）                 ← ## より前。全 variant に共通。省略可
> （共通インタラクション行）    ← 全 variant に共通。省略可
## variant1                        ← variant（省略可。無ければ単一 variant）
（固有要素行）
> （固有インタラクション行）
## variant2
（固有要素行）
> （固有インタラクション行）
```

例：`x` の variant ＝ 共通 ＋ x 固有、`y` の variant ＝ 共通 ＋ y 固有。

遷移は「component の間」も「同一 component の variant の間」も同じ transition verb で書く（行き先で区別しない）。transition verb はコア 4 語（`push`/`back`/`goto`/`exit`）＋compound verb 3 語（`present`/`dismiss`/`switch`）の計 7 語。一覧は「transition verb」を参照。

### document common（最初の `#` より前）

最初の `#` より前に書いた要素行・インタラクション行は、**そのファイルの全 component に共通**する部分になる。`##` より前が全 variant に共通であるのと相似形で、共通性は 3 階層になる：**variant 固有 > component common（`##` より前） > document 共通（`#` より前）**。要素行も同様に共通になる——document common に置いた要素は**全 component の表示に共通要素として乗る**（全画面に出るバッジ等）。

用途は「どの画面でも起こるインタラクション」——deep link、プッシュ通知、セッション切れによる強制ログアウトなど（モジュール分割時は「そのファイルの全 component」に限定される——後述）。エントリポイントはファイル先頭の component だが、任意の画面から始まりうる遷移（deep link 等）は document 共通のインタラクションとして表せる。

```
> プッシュ通知をタップ -> push(記事詳細)
> セッション切れ -> exit(@loggedIn)

# スプラッシュ
...
```

セッション切れの例で `goto(ログイン)` ではなく `exit(@loggedIn)` を使うのは、`goto` が現在フレームの最上段を置き換えるだけで祖先フレーム（開いていたタブ・進行中のセッション等）を残してしまうため。ログイン後の状態を丸ごと畳んで抜けたいなら、`exit` でセッションごと破棄する（「セッション」を参照）。

deep link で「今開いているものが何であれ、決まった場所へ連れて行く」には 2 つの慣用句がある（root へ収束する専用記法は持たない）：

```
> 通知タップ -> switch(ホーム, @tabHome) ; push(記事詳細)   // 保持系: タブへ復帰してから積む（開いていたモーダルは中断のまま残る）
> 強制更新 -> exit(@loggedIn) ; push(ログイン)              // 破棄系: セッションごと畳んでから積む
```

document common に書ける遷移先の variant 指定は必ず **`component##variant`** の形で書く。裸の `##variant` は「同一 component 内の variant」を指す記法だが、document common には母体となる component が無いため書けない（**禁止**。E022）。document common からは、まだファイル中で定義されていない component への参照（前方参照）も**可**——deep link や通知はどの画面から発生するか書く時点では決めきれないことが普通にあるため（前方参照は document common に限らず一般に可。「component に特権はない」を参照）。

モジュール分割時、実行時に有効な document common は**アクティブフレームの最上段 component が定義されているファイル**のもの。import 先の画面を表示中は、その import 先ファイルの document common が効く（「そのファイルの全 component に共通」の字義どおり）。最上段が未定義 component（どのファイルにも定義が無い）の場合は、**それを参照したファイル**に属するとみなす。掲示中 overlay の interaction の有効性はオーバーレイ節の規則によるもので、document common のスコープとは無関係。

shadow 規則も同じ原理で拡張される：（行動文字列, 対象参照）が完全一致する定義が複数の階層にあれば、より特化した階層が勝つ（variant 固有 > component common > document 共通。「完全一致」の判定基準は「操作は variant に属する」節を参照）。

## 記号一覧（これで全部）

| 記号 | 役割 |
|------|------|
| `#` 名前 | component 定義（見出し。語彙を持たない。名前はユーザー命名） |
| `#!` 名前 | singleton component 定義（**定義ファイル内**で単一インスタンス。variant 状態を全所在で共有する。共有の単位は定義ファイル——別モジュールの同名 component とは無関係。「variant はインスタンスごとに独立」の singleton 項を参照） |
| `##` 名前 | variant（バリエーション）定義 |
| `>` | インタラクション行の先頭マーカー（後続の空白・インデントは非意味）。`->` を含めば新規インタラクション、含まなければ直前インタラクションの結果列の継続行 |
| 名前 | component 参照。すべて対等（特権的な組み込み component はない）。定義があれば自作、なければ未定義。名前は自由 |
| `*` | collection（前置）。宣言側は要素行の先頭（alias の前）に置き「複数ある」と宣言する：`*サムネイル` / `*手札: カード`。参照側でも前置でき、`*手札` は collection 全体、`手札` は 1 インスタンスを指す（対称参照。「collection」を参照） |
| `名前: 実体` | alias（`左: 右` ＝ 名前: 実体）。要素や inline に呼び名を与え、参照・命名に使う |
| `{ ... }` | inline component（その場限りの定義。中身は `;` か改行で区切る。variant・インタラクションは持てない——要素のみ） |
| `.` | 要素参照（`alias.要素alias` / `名前.要素alias`）。1 段まで。他の component の内部要素も外から参照でき、文脈ごとに挙動を差せる |
| `##` | variant 参照（`component##variant` / 同一 component 内は `##variant`）。遷移先に variant を指定する時。定義 `## variant` と数が揃う |
| `->` | 行動と結果の境界 |
| `;` | 結果列の区切り（改行でも可） |
| `[ ... ]` | condition label（評価しない注記。分岐の目印） |
| `?` | presence gate（行動対象への後置。`行動(対象?)`）。opt-in：その variant に対象が存在する時だけ行動が有効になる。`?` 無しの行動は always-on |
| `"..."` | quoted name（空白を含む name を囲む。エスケープ機構なし——ラフ記法に複雑なエスケープ規則を持ち込まないため、`"` を含む name は言い換えで回避する）。component 名・variant 名・alias・参照・行動対象などすべての name 位置で有効。正準値は quote を剥いだ文字列で、bare の同名と同一の name として照合される |
| `@名前` | セッション（開始して破棄する期間の名前）。`push(X, @名前)` / `present(X, @名前)` / `switch(X, @名前)`（新規作成時）で開始し、`exit(@名前)` / `dismiss(@名前)` で破棄 |
| `::` | 名前空間区切り（`モジュール::component`）。import した別ファイルの component を参照。要素行・行動対象・遷移先のいずれでも使える |
| `// 自然文` | コメント（行末・行頭どちらでも）。`#` と衝突しないので component 定義と紛れない |

**予約語**：
- transition verb（コア）：`push` `back` `goto` `exit`
- transition verb（複合）：`present`（= barrier ありの `push` ＋セッション） `dismiss`（= 直近の無名セッション、または `@S` を破棄） `switch`（= フレームの中断と復帰。resume-or-create）
- overlay verb：`show`（オーバーレイ集合に component を掲示） `hide`（掲示を外す）。フレーム木を操作しない別カテゴリ（「オーバーレイ」を参照）
- state verb：`set`（singleton の共有 variant を、遷移を伴わず書き換える。フレーム木も掲示も操作しない第 3 カテゴリ。「singleton component」を参照）
- 構造キーワード（モジュール化）：`import` `as`

これ以外のキーワードは持たない。

`.`（要素）と `##`（variant）は軸が違う：`.` は component の中身、`##` は component の variant。

ある component に置いた別 component（部品）の内部要素を、外側から `インスタンス.要素alias` で参照できる（例：`自分.フォロー -> push(編集)`）。これにより、同じ部品を文脈ごとに違う挙動で使える（自分のページなら編集へ、他人のページならフォロー）。部品定義側に書いた挙動はその部品単体でのデフォルト、外側から書いた参照はその文脈での上書き。

参照は **alias 名（または component 名）** で引く。要素を参照したいときは、その要素に alias を付けておく（同名の要素が複数あり得るため）。同名の要素 alias が複数の variant にまたがって存在しても、名前解決は**曖昧にはならない**（`.要素alias` は現在の variant の実効 body から一意に見つかる）。ただしこれは**参照が一意に解決できるという保証**であって、各 variant でその alias が指す実体が意味的に同じ役割を果たすことまでは保証しない——同じ alias 名を variant を跨いで違う意味で使わないのは**書き手の責任**である。したがって variant を明示する合成記法（`component##variant.要素`）は不要で、用意しない。

**alias のスコープと優先順位**：alias は宣言された **single-body（variant 固有 body・component common body・document common のいずれか）にローカル**——その body の中から参照でき、名前が衝突する component 名より**優先**して解決される。component 名と一致する bare な要素名（alias を付けていない要素をそのまま書いたもの）は、component への参照なのか単なる見出しラベルなのか紛らわしい——処理系はこれを**警告**してよい（例：タブバー内に飾りとして「ホーム」という要素をそのまま置くと、`ホーム` という component への参照に見えてしまう）。

## 文法（EBNF 風）

```ebnf
document        = { import } , document-common , { component } ;
document-common = single-body ;                      (* 最初の "#" より前。全 component に共通。空でもよい *)

import          = "import" , module-name , "as" , alias-name ;
module-name     = (* 同ディレクトリの .shitae ファイル名（拡張子省略）またはパス *) ;

component       = header , common-body , { variant } ;
header          = ( "#" | "#!" ) , name ;            (* "#!" は singleton（variant 状態を共有する単一インスタンス）。
                                                          セッションはここでは打たない（遷移時に打つ） *)

common-body     = single-body ;                      (* ## より前。全 variant に共通。空でもよい *)
variant         = "##" , name , single-body ;      (* variant 固有。variant が 0 個なら単一 variant *)
single-body     = { body-line } ;                    (* element-line と interaction-line は自由に混在可。
                                                          正準形・推奨は「要素行を先に、インタラクション行を後に」 *)
body-line       = element-line | interaction-line ;

element-line    = [ "*" ] , [ alias-name , ":" ] , ( ref | inline ) ;  (* * は行頭（alias の前） *)
alias-name      = name ;
ref             = [ module-name , "::" ] , name ;    (* [モジュール::]名前。すべて対等。自作/未定義を問わない *)
inline          = "{" , inline-body , "}" ;          (* 要素のみ。variant(##)やインタラクション(interaction-line)は持たない *)
inline-body     = element-line , { ( ";" | newline ) , element-line } ;

interaction-line     = ">" , ( new-interaction | continuation ) ;
                        (* 行頭 ">"。">" の後の空白・インデントは非意味（原則 5） *)
new-interaction      = action , "->" , result-list ;
                        (* "->" を含む: 新しいインタラクションの開始 *)
continuation         = result-list ;
                        (* "->" を含まない: 直前インタラクションの result-list への継続行。
                           先行するインタラクションが無い継続行は構文エラー。
                           探索は同一 single-body 内に限る（"#"/"##" を跨いだ時点で構文エラー） *)
action               = free-text , [ "(" , reference , [ "?" ] , ")" ] ;
                        (* 行動は自然文。対象を取るときだけ括弧。対象なしは括弧省略。
                           "?" を対象に後置すると presence gate（opt-in）：構造的 presence（対象が今の variant の実効 body に
                           存在するか）で行動の有効性を決める。"?" が置けるのは行動対象のみ *)
reference           = [ "*" ] , [ module-name , "::" ] , name , [ "." , name ] ;
                        (* [モジュール::]component名 / alias.要素alias。1段。
                           先頭の "*" は collection 全体への参照（宣言側の "*" と対称。「collection」を参照） *)

result-list     = result , { ( ";" | newline ) , result } ;  (* (条件, 結果) の列。";" と改行（継続行）はどちらも区切り。
                                                                  複数の result が並ぶときの逐次意味論は「未定・分岐」を参照 *)
result          = [ "[" , label , "]" ] , ( transition | overlay | state | effect ) ;
label           = free-text ;                        (* condition label。評価しない注記 *)
(* 意味論: 行動 A(C) -> R は (条件, 結果) の列。
   最初のラベルより前の result は常に成立。
   [ラベル] は、次の別のラベルが現れるまでの以降の result 群に掛かる（1 個とは限らない）。
   矢印 -> は 1 つだけ。分岐は -> の後に ; または改行（継続行）で複数の [条件] 結果を並べる。
   -> R -> R のように矢印を重ねるのは構文エラー。 *)
transition      = push-nav | present-nav | goto-nav | back-nav | exit-nav | dismiss-nav | switch-nav ;
(* 積む側：第2引数に任意のセッション @S *)
push-nav        = "push" , "(" , nav-target , [ "," , session ] , ")" ;
(* present は独立の compound verb（barrier ありの push ＋セッション）。barrier は push だけでは表せないため push の糖衣ではない *)
present-nav     = "present" , "(" , nav-target , [ "," , session ] , ")" ;
(* 置き換え：セッション不可（積まないので begin 地点を残せない）。ただし現在フレームの begin マーカーは保存する——後述「フレーム木」参照 *)
goto-nav        = "goto" , "(" , nav-target , ")" ;
(* 戻る：画面方向。引数は常に component（セッションではない）。戻り先が無い場合は「戻り先が無いとき」を参照 *)
back-nav        = "back" , "(" , [ back-target ] , ")" ;
back-target     = [ module-name , "::" ] , name ;    (* component のみ。"##variant" は書けない——戻り先の variant はスタックが決める *)
(* セッション破棄：引数は常にセッション。戻り先が無い場合は「戻り先が無いとき」を参照 *)
exit-nav     = "exit" , "(" , session , ")" ;
dismiss-nav     = "dismiss" , "(" , [ session ] , ")" ;   (* 空なら直近の無名セッションを破棄（named は飛ばして子孫ごと破棄）。戻り先が無い場合は「戻り先が無いとき」を参照 *)
(* switch は中断・復帰の compound verb。セッション必須（辞書のキーになるため省略不可） *)
switch-nav      = "switch" , "(" , nav-target , "," , session , ")" ;
session         = "@" , session-name ;
nav-target      = [ module-name , "::" ] , name , [ "##" , name ]   (* [モジュール::]component[##variant] *)
                | "##" , name ;                                     (* 同一 component 内の variant。
                                                                         collection への遷移という概念は無いため "*" は付けられない *)
(* オーバーレイ：フレーム木を操作しない別カテゴリ。show は掲示、hide は掲示解除（掲示されていなければ no-op）。
   引数は component（##variant 指定は掲示時の variant を選ぶ。裸 "##variant" は母体が無いため書けない） *)
overlay         = show-nav | hide-nav ;
show-nav        = "show" , "(" , [ module-name , "::" ] , name , [ "##" , name ] , ")" ;
                        (* name は必須。裸 "##variant"（母体 component なし）は E027 *)
hide-nav        = "hide" , "(" , [ module-name , "::" ] , name , ")" ;
                        (* hide に "##" は本来書けないが、誤り検出のため字句上は認識する——
                           component 付き（hide(X##v)）は E020、裸（hide(##v)）は E027 *)
(* state verb：フレーム木を操作せず・掲示もしない第 3 カテゴリ。singleton の共有 variant を書き換える（「singleton component」を参照） *)
state           = set-nav ;
set-nav         = "set" , "(" , [ module-name , "::" ] , name , "##" , name , ")" ;
                        (* ##variant は必須（E029）。裸 "##variant"（アクティブ画面の variant 切替は goto(##v) の仕事）・
                           "*"（collection）・セッションは書けない——いずれも E029 *)
effect          = free-text ;                        (* 副作用。reload 等もこれ。予約語なし *)

comment         = "//" , free-text ;                 (* 行頭・行末どちらでも *)
name            = quoted-name | bare-name ;
quoted-name     = '"' , (* 任意の文字列。エスケープ機構なし *) , '"' ;
                        (* 空白を含む name はこれで囲む。正準値は quote を剥いだ文字列で、
                           bare の同名と同一の name として照合される *)
bare-name       = (* 任意の識別子。日本語可 *) ;
free-text       = (* 任意の自然文。行コメント // の手前まで。
                     結果列の中では区切り ; と次の result まで。
                     行動内（括弧前）では -> の手前まで。
                     行動の自然文（括弧前）は丸括弧を含めない——括弧を含む名前・文が要るときは quoted name を使う *) ;
```

アンカー（セッション）を打てるのは `push` / `present` / `switch`（新規作成時）。`exit` / `dismiss` / `switch`（復帰時）は参照側（`@名前` で対象を指す）。`back` はセッションと無関係に component 名で戻り先を指す（variant は指定できない——戻り先の variant はスタックが決める）。戻り先が見つからない場合（後述「戻り先が無いとき」）は no-op。

## 操作は variant に属する（条件式を持たない理由）

インタラクションは、それが書かれた**variant の中でだけ有効**。
「ある状況でだけ可能な操作」は、ガード条件式ではなく、その操作を持つ variant を用意することで表す。

```
# プロフィール
## 未フォロー
フォロー
> タップ(フォロー) -> フォローする ; goto(##フォロー済)

## フォロー済
フォロー解除
> タップ(フォロー解除) -> 解除する ; goto(##未フォロー)
```

未フォローの variant には「フォロー」操作があり、フォロー済の variant には無い（代わりに「フォロー解除」がある）。
「いつ何ができるか」が、`if 状態 == X then ...` ではなく、variant ごとの操作の有無として現れる。
どの variant に居るかが決まれば、そこで何ができるかは構造的に決まっている。

### 2 種類の「ガード的なもの」

shitae には遷移の可否に関わる要素が 2 つあるが、どちらも評価式ではない。

1. **presence gate（`?`・opt-in・構造的 presence）**：`行動(対象?)` のように対象へ `?` を後置すると、「対象が存在する時だけ行動が有効」という条件を明示できる。`?` を付けない行動（`行動(対象)`）は、それが書かれた variant のスコープで**常に**有効——対象の存在は自動的には条件にならない。

   ここでの「存在」は**式や値比較を評価しない構造的 presence**として定義する：その参照表記が解決される先の variant の**実効 body（共通＋固有）**に、対象と同名の alias または ref が element-line として書かれているかだけを見る。
   - 裸参照（`投了?`）は **host component（その行動が書かれている component）の現在 variant** の body 直下を見る。
   - member 参照（`日付.選択可能?`）は **対象インスタンス（`日付`）の現在 variant** の body を見る——host 側の variant ではなく、参照先そのものの variant で判定する。
   - 参照に `*` が前置されていても（`*手札?`）、判定は `*` を剥いだ名で行う——collection かどうかではなく、その名前の要素があるかどうかを見る。
   - 対象が未定義 component など判定不能なときは **always-on**（ラフさ優先。lint はヒントを出してよいが、エラーにはしない）。
   - **document common の裸参照**は、発火時に**アクティブな component の現在 variant の実効 body** で判定する——裸 `##variant` の動的解決と同じ原理で、document common の interaction はアクティブ component に書かれたかのように振る舞う（「variant の参照は必ず ##」を参照）。これにより「その要素を持つ画面でだけ有効な deep link」が書ける：`> 通知タップ(記事リンク?) -> push(記事詳細)`。
   - **overlay 掲示中 component の裸参照**は、host（その行動が書かれている component）＝**掲示中 component 自身**の表示 variant の実効 body で判定する——document common の裸参照とは異なり、判定はアクティブ画面の body を見ない。overlay の interaction には字句ホスト（overlay 自身）が明確に存在するため、document common（字句ホストが無いから動的解決する）とは事情が異なる（「オーバーレイ」を参照）。
   - `?` が置けるのは**行動対象のみ**。nav-target（遷移先）への後置（例 `push(次?)`）は**構文エラー**（E013）。要素行の参照への後置（例 要素行に `投了ボタン?`）も**構文エラー**（E025）——要素の「あるかもしれない」は variant で分けるか自然文で注記する。

   `?` が opt-in（既定は「対象不在でも always-on」）なのは、**要素行に書いていない対象への行動を許す**ため。ラフの段階では、まだ要素行に置いていない・置くかどうか未定の対象へ行動を書くことが普通にある（`> タップ(投了) -> goto(##リザルト)` と書くとき「投了」ボタンを要素行に置き終えている必要はない）。存在を自動で行動の条件にすると、これらの行動が黙って無効になり、ラフさの核が壊れる。だから既定は always-on とし、存在を条件にしたいときだけ書き手が `?` で opt-in する。典型の使いどころは共通部分（`##` より前）に置いた行動で、「その対象を持つ variant でだけ有効」にしたいとき。

   XState の `guard`（同じ状態でも式の真偽で可否が変わる動的な制御）との違いは、**任意の述語を持たない**こと——presence gate が見るのは「その名前の要素が今の variant の body にあるか」という構造的な一点だけで、値比較や条件式は評価しない。

   gate が書けるのは**対象自身の状態で対象自身への操作を制御する**形だけ——`?` は行動対象に付き、判定もその対象（の component）の variant で行われる。「A の状態で**別の要素 B** への操作を制御する」（ハートが残っている時だけレッスン開始ボタンが押せる、等）は gate では書けない。その場合は host component の variant を分けて表す（`##通常` / `##ハート切れ`——本節の本則どおり「操作を持つ variant を用意する」）。条件源の変化にその variant を追随させる書き込みは `set` で書ける（「singleton component」を参照）。

   対象が別 component のインスタンスの場合、その**インスタンスの現在 variant**は shitae の中の遷移だけでなく、外部データ（在庫・カレンダーの空き状況等）によっても決まりうる。どちらの variant に居るかを shitae は判定しない——condition label の「どちらに転ぶかは shitae の外で決まる」（後述「未定・分岐」）と同じ整理である。

   ```
   # 日付
   ## 選択可能
   選択可能
   > タップ(日付) -> 日付を選択する

   ## 満席
   満席

   # 予約
   *日付
   > タップ(日付.選択可能?) -> push(時間選択)   // 満席の variant には「選択可能」要素が無いので gate が off
   ```

2. **condition label（評価しない注記）**：`[成功]` / `[失敗]` のような分岐の目印。結果がどちらに転ぶかは動的な判断を要するが、shitae は評価せず、ラベルとして注記するにとどめる。どちらに転ぶかは shitae の外（実装・実際の挙動）で決まる（「未定・分岐」を参照）。

shitae が「条件を評価しない」と言うとき、それは presence gate と condition label の両方を指す——存在は構造的 presence の判定に留め、分岐はラベルの注記に留める。状態機械のように式を評価して遷移を制御することはしない。gate とオーバーレイの掲示状態は**別軸**——gate は掲示中かどうかを見ない（「オーバーレイ」を参照）。

**共通部分と variant 固有部分で同じ行動が衝突したとき**（共通に `> タップ(戻る) -> back()`、ある variant にも `> タップ(戻る) -> goto(別)` があるなど、（行動文字列, 対象参照）が完全に一致する場合）、**variant 固有の定義が共通の定義を shadow する**（variant 固有が有効になり、共通の定義はその variant では無効になる）。これは、外部からの要素参照上書き（部品定義側の挙動はデフォルト、外側からの参照が文脈で上書きする。「記号一覧」を参照）と同じ「特化が一般に勝つ」原理での統一である。行動文字列や対象参照が完全一致しなければ（行動の書き方や対象が異なれば）両方とも有効なまま残る——そこはラフさの範囲である。

ここでの「完全一致」は次の基準で操作的に判定する：**行動文字列**は字句正規化後（空白の畳み込み等）の比較、**対象参照**は quote を剥いだ name の等価、**`?` の有無は一致判定に含めない**（`行動(対象)` と `行動(対象?)` は同じ行動として shadow の対象になる）。ただし **`*` の有無は一致判定に含める**——`行動(*対象)`（collection 全体）と `行動(対象)`（1 インスタンス）は異なる対象への操作であり、shadow せず両立する（`?` は同一の行動への条件付与、`*` は対象そのものの変更、という区別）。

### variant はインスタンスごとに独立

同じ component を複数の場所に置いたとき（画面 A と画面 B に同じ「プロフィールカード」等）、各インスタンスの variant は**独立**している。一方のインスタンスで `goto(##フォロー済)` しても、他方のインスタンスの variant は変わらない。

インスタンス間で variant を同期させたい（A でフォローしたら B のカードも変わる）は、共有データの関心であり実装の領分——shitae はデータを持たないと決めたが、variant がデータの代理をする以上この問題は variant に滲み出る。shitae は言語では扱わず、同期するという事実が設計上重要なら自然文で注記する（`> タップ(フォロー) -> フォローする ; 他画面のカードにも反映される ; goto(##フォロー済)`）。simulator 上でインスタンス間の variant が食い違って見えるのはラフの代償として許容する。

ただし「**そもそもインスタンスを分けたくない**」——一度受け取ったクーポンはどこから開いても受取済、設定した再生速度は画面を閉じても残る、のように variant がフレームの生死をまたいで生き続けてほしい——場合は、次の singleton を使う。

### singleton component（`#!`）

定義ヘッダを `#!` にすると、その component は**定義ファイル内で単一インスタンス**になる。どこから `push` / `present` / `show` しても、要素として何箇所に置かれても、**variant 状態を共有**する（インスタンス独立の既定を opt-in で覆す）。

共有の単位は**定義ファイル（モジュール）**。どのモジュールから `mod::クーポン` で参照しても同一の共有状態を読み書きするが、**別モジュールの同名 component**（通常・singleton とも）とは無関係——名前空間はモジュールで分かれる（「モジュール化」を参照）。

```
#! クーポン
## 未受取
> タップ(受け取る) -> クーポンを受け取る ; goto(##受取済)
## 受取済
適用ボタン
```

- variant 指定なしで開くと、初回は initial variant、以降は**最後に遷移した variant**で開く（initial に戻らない）。一度受け取れば、以後どこから `present(クーポン)` しても `##受取済` で開く。
- singleton の variant は**共有レジストリへの参照**であり、スナップショットをどこにも作らない。フレームスタック・オーバーレイ集合に置かれた singleton は、他所で共有 variant が進めば追随する——「戻り系は積まれた時点の variant へ戻る」「新規作成・`show` は initial variant で開く」の各規則は singleton には**適用しない**。
- `X##v` 指定・`goto(##v)` は共有状態の書き換えとして働く（全所在に即時反映）。この書き換えは **`switch(X##v, @S)` の resume 経路にも及ぶ**——resume は X を無視してフレームを復帰するが、明示 `##v` の共有 variant 書き換えだけは副作用として効く（「全所在に即時反映」の字義どおり）。
- **`set(X##v)`（state verb）は、遷移も掲示もせずに共有 variant だけを書き換える**。「画面 A で起きた出来事が画面 B の状態を変える」——ハートを使い切ったら学習画面をハート切れ表示に、時間経過で回復したら通常に戻す——を、B へ遷移せずに書ける。掲示中の singleton にも即時反映される（掲示中のミニプレイヤーが singleton なら、他画面からの `set` がその場で見た目を変える）。対象は singleton のみ——通常 component はインスタンス独立で「どのインスタンスに書くか」が定まらないため、`set` の対象にできない（E030）。遠隔から状態を書きたくなったら、その component を `#!` にする（タブ画面のような事実上単一インスタンスの画面は `#!` にしてよい）。未定義 component への `set` は、他の判定不能な対象と同じくエラーにせず素通りする（ラフさ優先。gate の「判定不能なら always-on」と同じ整理）。

  ```
  # 問題
  > タップ(選択肢) -> [不正解・ハート切れ] set(学習##ハート切れ) ; exit(@lesson)

  > ハートが回復する -> set(学習##通常)     // document common でもよい（非アクティブ中の事象）
  ```

  「ハートが回復する」のような外部で起きる事象も、行動の自然文として書くのは想定内の用法（「行動（インタラクションの左辺）」を参照）。

- 参照側の記法は無変更（`present(クーポン)`——特別な参照記号は要らない）。フレーム木の**構造操作**の規則（push で積まれ、back で降ろされ、exit で破棄される）も不変——singleton で変わるのは variant の選択・保持だけ。
- singleton に collection の `*` は付けられない（**E028**）——「単一インスタンス」と「複数ある」は矛盾する。宣言側の要素行（`*バッジ`）も参照側の行動対象（`行動(*バッジ)`）も同様。
- 共有するのは variant（見た目の状態）だけで、値・カウンタは従来どおり扱わない（「扱わないもの」を参照）。独立インスタンスが欲しければ既定の `#` のまま。

## transition verb

コアは **`push` / `back` / `goto` / `exit`** の 4 語。**`present` / `dismiss` / `switch`** は barrier とセッションにまつわる意図を一語に束ねた**compound verb**（後述）。

| 語 | 何をする | 後で戻れる |
|----|----------|------------|
| `push(X)` / `push(X, @S)` | X へ進む（積む。back で戻れる）。`@S` で「@S セッション」を開始（back barrier なし） | ○ |
| `back()` / `back(X)` | 直前へ／component X まで戻る（画面スタックを戻る）。戻り先が無ければ no-op | — |
| `goto(X)` | 現在を X に置き換える（積まない） | ✗ |
| `exit(@S)` | @S セッションを破棄（begin した地点へ戻る）。戻り先が無ければ no-op | — |
| `present(X)` / `present(X, @S)` | モードに入る（モーダル・ログイン後フロー等）。back barrier あり＋セッションを束ねた compound verb | △ |
| `dismiss()` / `dismiss(@S)` | 直近のモーダルを閉じる／@S を破棄。戻り先が無ければ no-op | — |

無名 `dismiss()` が探すのは**無名セッション（`present(X)` が開始したもの）だけ**——`push(X, @S)` で begin した named session は畳まない（素通りする named session は道連れで消えることはあるが、`dismiss()` 自身の対象にはならない）。push-begin の `@S` を畳むのは `exit(@S)`（`dismiss(@S)` も同義）。
| `switch(X, @S)` | フレームの中断と復帰（タブ等の並行文脈）。@S が生きていれば中断位置へ復帰、無ければ X で新規開始（resume-or-create）。back barrier あり | △ |

`back` は **画面スタックを戻る**（引数は常に component）。`exit` は **セッションを終える**（引数は常にセッション `@S`）。役割が違うので予約語を分ける——`back(X)` の X は必ず画面、`exit(@S)` の @S は必ずセッション。`@` で見分けるのではなく、語で意味が確定する。

### push / goto と行き先

- **`goto`** は「積まない置き換え（ジャンプ）」。対象は同一 component の variant でも別 component でもよい。
  - `goto(##表示)` … 同一 component の別の variant へ（variant change。`##` で variant を明示、component 名は省略）
  - `goto(ホーム)` … 別 component へ、戻れない置き換え（ログイン→ホーム等）
- `goto` は**セッションを開始できない**（`goto(X, @S)` は不可）。セッションは「begin した地点に戻る」ために、begin 時点でフレーム上の新しい一位置を必要とするが、`goto` は積まずに現在フレームの最上段を置き換えるだけなので、新しい begin 地点を作れない（畳む基点になれない）。
  この規則は、goto が**既存の** begin マーカー（現在フレームがすでに begin しているセッション）を保つかどうかとは独立——`goto` は新規セッションを開始できないが、現在フレームがすでに持っている begin マーカーは壊さずそのまま残す（「フレーム木」を参照）。
- 行き先は `component` / `component##variant` / `モジュール::component` / `##variant`（同一 component 内の variant）。
- セッション無しの `push(##v)` は「アクティブ component の variant v を現在フレームに積む」——`goto(##v)`（置き換え）と違い `back()` で元の variant へ戻れる。フレームを作らないので E023 の対象外。

### variant の参照は必ず `##`

variant を参照するときは常に **`##variant`** と書く。定義の `## 表示` と参照の `##表示` で `#` の数が揃う。

- `記事詳細##表示` … 別 component の variant（component ＋ `##` variant）
- `##表示` … 同一 component 内の variant（component 名を省略）

同一 component 内では component 名を省略できるが、**variant 名を component 名のように裸で書いてはいけない**。`goto(表示)` は「表示という component へ」の意味になり、variant change にならない。variant change は `goto(##表示)`。

裸 `##variant` の「同一 component」は**実行時にアクティブな component**（アクティブフレームの最上段）を指す——書かれた場所（字句上のホスト）ではない。document common から継承した interaction の `goto(##v)` は、発火時にアクティブな画面の variant を切り替える。掲示中 overlay の interaction でも同じ（overlay 自身の variant を変えたいときは再 `show`。「オーバーレイ」を参照）。

フレームを新規作成する形（`push(##v, @S)` / `present(##v[, @S])` / `switch(##v, @S)`）に裸 variant を書くのは**構文エラー**（E023）——variant 切替のつもりで書いた読者の前でフレームが増える驚きを防ぐ。switch が実行時に resume するか新規作成するかによらず、構文段階で一律に禁止する。document common に裸 `##variant` を書くのも従来どおり禁止で、E022 として検出される。

### initial variant とエントリポイント

variant 指定なしの遷移（`push(X)` / `goto(X)` / `present(X)` 等、`##variant` を伴わないもの）は、X の**最初に定義された variant**（最初の `## variant`。variant を持たない component ならその単一 variant）で開く（singleton は除く——初回以降は最後に遷移した variant で開く。「singleton component」を参照）。

ドキュメント全体のエントリポイントは**ファイル先頭の component**。モジュール分割時は、エントリファイル（起点となる `.shitae` ファイル）の先頭 component がエントリポイントになる。component を 1 つも持たない文書は不正（エントリポイントが定まらない）。

### セッション（`@S`）

セッション `@S` は **「開始して、まとめて破棄する、ひとまとまりの期間」**。ログインセッション、チェックアウトセッション、モーダルを開いている間、など。`push(X, @S)` / `present(X, @S)` / `switch(X, @S)`（新規作成時）で**開始**し（その遷移が begin）、`exit(@S)` / `dismiss(@S)` で**破棄**する（begin した地点へ戻る）。

```
> タップ(開始) -> push(確認, @checkout)        // @checkout セッション開始（確認へ進む）
> タップ(確定) -> 注文する ; exit(@checkout)  // @checkout を破棄して begin 地点へ
```

- セッションを開始できるのは積む側（`push` / `present`）と `switch`（新規作成時）のみ。`goto` は不可、`back` は画面方向なので無関係。
- **セッションは遷移に紐つく**。`push(X, @S)` を実行したその push が begin。同じ画面を別の場所で push すれば別のセッションになる。component や variant そのものにセッション名が固定されるわけではない。
- **同名 `@S` を続けて begin すると入れ子になる**。`push(確認, @checkout)` の中でさらに `push(支払い, @checkout)` と書いても「同じセッションの継続」にはならない——begin のたびに新しいフレームが入れ子で増え、`exit(@checkout)` / `dismiss(@checkout)` は LIFO で**直近の 1 つ**しか畳まない（出口が壊れる典型の誤読——「直近の 1 つ」は該当フレームとその**子孫フレームを全部**破棄する意味であり、内側の `@S` がさらに子を持っていてもその子孫ごと消える。「フレーム木」を参照）。フロー全体をひとまとまりにしたいなら、begin は**入口の 1 回だけ**——フロー内部の遷移は素の `push` で書く。処理系は生存中の同名 `@S` の再 begin を実行時に警告してよい（R005。`push`/`present` が対象——`switch` は resume-or-create なので同名 `@S` が生存中なら必ず resume に倒れ、そもそも「再 begin」が起き得ない）。

**出口を固定したいとき**：`exit(@S)` は begin 地点（そのセッションを開始した push/present の位置）へ戻る。複数の入口から同じウィザードに入ると begin 地点が入口ごとに変わるので、「出口は常にホーム」という要件は `exit(@S)` 単体では書けない。戻り先を上書きする専用記法は用意しない代わりに、result-list の逐次適用（後述「未定・分岐」）を使った **`exit(@S) ; push(固定先)`** が慣用句になる——`exit` がセッションと子孫フレームを破棄する保証を保ったまま、続く `push` で出口を決定的にできる。

```
> タップ(完了) -> 申し込みを確定する ; exit(@wizard) ; push(ホーム)   // 入口によらず出口はホーム
```

#### セッションと「back barrier」は直交

「まとめて破棄できる範囲（セッション）」と「モード内から外へ通常の `back` で出られるか（back barrier）」は**別の軸**。

| | back barrier なし | back barrier あり |
|---|---|---|
| **セッションあり** | 閲覧フロー（`push(X, @S)`）：経路を `back` で 1 つずつ遡れる＋ `exit(@S)` で一気に戻れる | モーダル／モード（`present(X, @S)`）：内側で `back` しても外へ出ず、`dismiss`/`exit` で一括 |

- **`push(X, @S)`** … back barrier**なし**＋セッション。例：記事 → 関連記事 → さらに関連、と深く潜り、各段は `back` で遡れるが、「ホームへ」で `exit(@S)` すれば何段潜っていても一気に戻れる。
- **`present(X, @S)`** … back barrier**あり**＋セッション。モード（モーダル）に入り、内側の `back` は外に出ない。`dismiss`（無名）／`exit(@S)`（名前付き）で出る。

`present` は「barrier あり＋セッション」を一語で束ねた compound verb。`push(X, @S)` は「barrier なし＋セッション」。barrier を独立に指定する記法は持たない（頻出するこの 2 パターンに名前を与えれば足りる）。

### フレーム木

処理系は内部的に**フレーム木**を持つ。**フレーム**＝ (component, variant) の組を積むスタック 1 本＋barrier の有無。ルートはエントリポイントを積んだ無名フレームで、**アクティブなフレームは常に 1 つ**。ユーザーが木を直接操作する記法はない（意味を与えるための内部モデル）。

- `push(X)` / `goto(X)` / `back()` は現在フレームのスタックを操作する（積む／最上段を置き換える／降ろす）。**`goto(X)` は最上段を置き換えるが、現在フレームの begin マーカー（そのフレームが begin したセッション、あれば）は保存する**——`push(A, @S) → goto(B) → exit(@S)` は @S の begin 地点へ正しく戻る（「goto はセッションを開始できない」という規則とは独立に成り立つ。「push / goto と行き先」を参照）。
- `push(X, @S)` / `present(X, @S)` / `present(X)`（無名——無名の子フレームを作る）は現在フレームの**子**フレームを作ってアクティブにする（begin 地点＝親フレーム内のその位置）。`push(X)`（セッションなし）はフレームを作らず現在フレームに積む。push/present のうち barrier を立てるのは present のみ（switch も barrier を立てる。次節）。
- `switch(X, @S)` は中断と復帰（次節）。
- `back()` / `back(X)` / `dismiss()`（無名）の走査は**アクティブパス**（現在フレームから祖先方向）のみ。中断中の兄弟フレームは見ない。`exit(@S)` / `dismiss(@S)` はまずアクティブパスを「新しい方から最初の @S」規則で走査し（@S が一意なら範囲破棄、同名複数なら直近まで（LIFO）、の説明は変わらない）、見つからなければ木全体から @S を探して**遠隔破棄**する（そのフレームを子孫ごと裏で破棄し、アクティブフレーム＝画面は動かない。「switch（中断と復帰）」を参照）。木の複数箇所に同名の `@S` が存在する場合（別々の `push(X, @S)` 呼び出しがたまたま同じ名前を使った等）、遠隔破棄・switch 復帰の対象は**作成が最も新しいフレーム**にする。exit/dismiss がまずアクティブパスを優先する（パス上の古い @S が別枝の新しい @S に勝つ）のに対し、switch 復帰にはアクティブパス優先が**無い**（常に木全体で最新）——この非対称は意図的である。
- `exit(@S)` / `dismiss(@S)` は @S と**その子孫フレームを全部**破棄し、begin 地点へ戻る。子孫ごと破棄なので「ログアウトでタブ全滅」が規則の追加なしに導かれる。
- barrier を持たない子フレーム（`push(X, @S)` が作る無 barrier の子）の**最下段**（そのフレーム内でこれ以上遡れない位置）で `back()` すると、barrier が無いのでそこで止まらず、**子フレームを（begin マーカーごと）破棄して親フレームへ抜ける**。barrier がある子フレーム（`present`/`switch` 製）の最下段では、barrier が壁として働き `back()` は no-op（「戻り先が無いとき」を参照）。
- 戻り系はスタックに積まれた時点の variant へ戻る（initial variant にリセットしない。singleton は除く——常に共有 variant の現在値が見える。「singleton component」を参照）。`goto(##variant)` は現在フレームの最上段の variant を書き換える——後で戻ってきたときは書き換え後の variant が見える。
- フレーム木・セッションの生存は**同一プロセス内**の意味論として定義される。アプリ再起動やプロセス終了を跨いで `@S` やフレームが生き残るかは shitae の意味論の**範囲外**——永続化するかどうかは実装の選択。

switch を使わないドキュメントでは木は一本道になり、従来どおり「単一のセッションスタック」として読める。

### switch（中断と復帰）

`push` / `present` が**開始**、`exit` / `dismiss` が**破棄**であるのに対し、`switch` は**中断と復帰**。「離れても破棄されず、戻れば続きから」という並行文脈——タブナビゲーションが代表——を表す。開始・破棄しか無い世界では「離れる＝破棄」しかできず、タブ（各タブのスタックを保持したまま行き来する）が書けない。

- **`switch(X, @S)`** — @S が生存していれば、現在フレームを**中断**（破棄しない）して @S の中断位置（そのフレームの最上段の (component, variant)）へ復帰する。このとき X は無視される（ツールは定義と異なる X を警告してよい）。@S が無ければ（未作成または破棄済み）、フレームを新規作成して X で開く。resume-or-create の一語。復帰できるかどうかは、その @S を最初に開始した verb（`push` / `present` / `switch` のどれだったか）を**問わない**——push 製・present 製どちらのフレームにも `switch` で中断・復帰できる。**自己参照**（`switch(X, @S)` を @S 自身がアクティブなフレームから呼ぶ）は無変化——すでに中断位置にいるので中断も復帰も起きない。
- 引数はこの 1 形式のみ。セッションは辞書のキーなので省略できず、resume 専用形（`switch(@S)`）も持たない——常に resume-or-create なので、初回と復帰を書き分けなくてよい。
- **barrier あり**（present と同様）。switch 先のフレームの底で `back()` しても元のフレームへは漏れない（no-op）。
- **兄弟規則**：switch でフレームを新規作成するとき、現在フレームから祖先方向に**最も近い switch 製フレーム**があればその**兄弟**（その親の子）、無ければ現在フレームの**子**にする。これにより、タブ内で push/present を何枚挟んでいても、タブ群は訪問順によらず常に横並びになる（「常に子」にすると木の形が訪問順に依存し、`exit(タブ1)` が後から訪れたタブ 2 を道連れにする事故が起きる。タブ内の閲覧セッション `push(記事, @reading)` の中からタブを切り替えても、新タブは @reading の子にならず、`exit(@reading)` に道連れにされない）。
- 中断中（非アクティブ）の @S への `exit(@S)` は**可**。そのフレームを裏で破棄し、画面（アクティブフレーム）は動かない。
- 破棄済み @S への `switch(X, @S)` は再作成（まっさらの X で開き直す）。「再ログインでタブが初期状態」が規則の追加なしに導かれる。

**タブの慣用句**。タブの 1 枚目（ホームタブ）だけが switch 製でないと、ホームタブのタップが `switch` で重複フレームを作ってしまう。そこで**タブ群への入場自体を名前付きフレームで行う**（例：ログイン成功時の `present(ホーム, @tabHome)`）。ホームタブが他タブの親（anchor）になる非対称は許容する——「ホームタブがルート」という実装プラットフォームの通例とも一致する。

```
# ログイン
> タップ(ログインボタン) -> [成功] present(ホーム, @tabHome)   // ホームタブ＝anchor frame

# ホーム
タブバー
> タップ(タブバー.検索) -> switch(検索, @tabSearch)
> タップ(タブバー.ホーム) -> switch(ホーム, @tabHome)   // 生存中なので復帰。重複生成しない
> ログアウト -> exit(@tabHome)   // 子孫ごと破棄＝全タブ破棄
```

タブが増えたら、**switch 群をタブバー部品に持たせて各画面は要素として置くだけ**にすると、画面ごとの複製が消える：

```
# タブバー
> タップ(ホームボタン) -> switch(ホーム, @tabHome)
> タップ(検索ボタン) -> switch(検索, @tabSearch)
> タップ(ライブラリボタン) -> switch(ライブラリ, @tabLibrary)

# 検索
タブバー          // 要素として置くだけ。switch 群は部品側にある
検索窓
```

なお `switch` の復帰先は常に**中断位置**（そのフレームの最上段）——実 UI の「タブ再タップでタブの先頭へ戻る」を表したいなら、復帰のあとに戻しを重ねる（`> タップ(ホームボタン) -> switch(ホーム, @tabHome) ; back(ホーム)`）。

エントリ画面自体がそのままタブ 1 枚目になる（ログインのような別入口を経由しない）場合も、同じ問題が起きる——タブ 1 枚目のタップがそのまま `switch` で重複フレームを作ってしまう。そのときは表示を持たない薄い**起動 component**を立て、そこから `present(ホーム, @tabHome)` でタブ群に入る（起動 component をファイル先頭＝エントリポイントにする）。

```
# 起動
> 起動 -> present(ホーム, @tabHome)   // アプリ起動時の唯一の入口。表示は持たない

# ホーム
（この先は上のタブ慣用句と同じ）
```

### present / dismiss は compound verb

`present` / `dismiss` は `push` / `exit` に還元しきれない**独立の compound verb**である。barrier（モード内から通常の `back` で外に出られない性質）は `push` だけでは表せないため、`present` は「push ＋ セッション（無名または名前付き）＋ back barrier」を一語に束ねたものであり、単なる糖衣ではない。

- `present(X)` … X へ進み（積み）、無名セッションを開始し、back barrier を立てる。「これはひとまとまりで `dismiss` でまとめて閉じる対象」という**意図**を読み手に伝える。
- `present(X, @S)` … 同様に、セッションへ `@S` という名前を付ける。
- `dismiss()` … アクティブパスを現在フレームから遡り、**直近の無名セッション**を破棄して begin 地点へ戻る。途中に名前付きセッション（`@S`）があっても**素通りする**——`dismiss()` が探すのは無名セッションだけであり、素通りした名前付きセッションはその破棄に**子孫として道連れ**にされて一緒に消える。多段 `present` は無名セッションが積み重なり、`dismiss()` は**LIFO で直近の無名を 1 つ**破棄。
- `dismiss(@S)` … `@S` を破棄する（アクティブパス走査 → 見つからなければ遠隔破棄、という規則は「フレーム木」を参照）。複数のモーダルを跨いで破棄したい／区別したいときに使う。**named session を指定したときの `exit(@S)` と `dismiss(@S)` は同義**——@S を開始したのが `push` / `present` / `switch` のどれであっても、`exit(@S)` と `dismiss(@S)` はどちらも「@S と子孫を破棄し begin 地点へ戻る」という同じ操作になる。動詞の選び分けは書き手の意図を読み手に伝えるためのものであり、実行結果を変えない。

`present` は専用セッション名を予約しない。「セッション省略 ＝ 無名、`dismiss` は直近対応」というだけ。

素通りと道連れを frame 列で追うと（`present(A, @S)` → `present(B)` → `present(C, @T)` の状態で `dismiss()`）：

```
root ─ A[@S] ─ B[無名] ─ C[@T]   ← アクティブ
dismiss(): C は named なので素通り → B（直近の無名）を破棄 → 子孫の C[@T] も道連れ
root ─ A[@S]                      ← アクティブ（@S は無傷）
```

**`present` は「モードに入る」遷移全般に使う**。画面上の見せ方（全画面・シート・ダイアログ）は問わない。本質は「独立した文脈（モード）に入り、戻るときはそのモードごと終える」こと。モーダルだけでなく、たとえば**ログイン後フロー**もこれで表す：

```
# ログイン
ログインボタン
> タップ(ログインボタン) -> present(ホーム, @loggedIn)   // ログイン後モードに入る（ログインには戻れない＝back barrier）

# 設定
アカウント削除
> タップ(アカウント削除) -> present(削除確認)             // 確認モーダル

# 削除確認
削除実行
> タップ(削除実行) -> アカウントを削除する ; exit(@loggedIn)   // ログイン後モードを抜ける＝ログインへ
```

`present(ホーム, @loggedIn)` は「ホームをモーダル提示する」のではなく「ログイン後というモードに入る」。ログインには通常の `back` で戻れない（back barrier）。ログアウト／アカウント削除は `exit(@loggedIn)` でそのモードを抜け、begin 地点（ログイン）へ戻る。`present`/`dismiss` という語は UI の見せ方を連想させるが、ここでは「モードの出入り」という本質で使っている。

### verb ごとのフレーム木の変化（対応表）

全 transition verb について、フレーム木がどう変わるかを 1 枚にまとめる。「フレーム木」「switch（中断と復帰）」「present / dismiss は compound verb」で説明した規則の要約であり、新しい規則は含まない。表の variant 選択（「initial で開く」「積まれた時点の variant に戻る」）は**非 singleton の既定**——singleton では共有規則が優先する（「singleton component」を参照）。

| verb | before | 操作 | after |
|---|---|---|---|
| `push(X)` | フレーム F、最上段 (A, a) | F のスタックに X を積む | 同じ F。最上段が (X, initial variant)。barrier・begin マーカーは不変 |
| `push(X, @S)` | フレーム F がアクティブ | F の**子**フレーム F′ を新規作成（barrier なし、begin マーカー = @S） | F′ がアクティブ。F′ のスタック = [(X, initial)]。F は破棄されず中断されたまま木に残る |
| `present(X[, @S])` | フレーム F がアクティブ | F の子フレーム F′ を新規作成（**barrier あり**、begin マーカー = @S または無名） | F′ がアクティブ。F′ のスタック = [(X, initial)] |
| `goto(X)` | フレーム F、最上段 (A, a) | F の最上段を置き換える（積まない） | 同じ F。最上段が (X, initial)。**begin マーカー・barrier は保存される** |
| `goto(##v)` | フレーム F、最上段 (A, a) | 最上段の variant だけ書き換える | 同じ F。最上段が (A, v) |
| `back()` | フレーム F、スタック 2 段以上 | 最上段を降ろす | 同じ F。最上段が積まれた時点の (component, variant) に戻る。**これ以上降ろせない**位置では：barrier があれば no-op、barrier が無ければ F を（begin マーカーごと）破棄して親フレームへ抜ける |
| `back(X)` | フレーム F | アクティブパスを X まで遡る。barrier なしフレーム境界は**越えて**探索し、越えた子フレームは begin マーカーごと**破棄**する | 見つかったフレームがアクティブになり、最上段 = (X, 積まれた時点の variant)。barrier に当たる／見つからない場合は no-op（`##variant` は指定できない） |
| `exit(@S)` | @S が begin したフレーム F′（アクティブパスに無ければ木全体から遠隔探索） | F′ と子孫フレームを全部破棄 | F′ の**親フレーム**がアクティブに戻る（begin 地点）。遠隔破棄時はアクティブフレーム自身は動かない |
| `dismiss()` / `dismiss(@S)` | `dismiss()`：アクティブパス上の直近の無名フレーム（named は飛ばして子孫ごと破棄）／`dismiss(@S)`：`exit(@S)` と同義 | 対象フレームと子孫を全部破棄 | `exit(@S)` と同じ木変化 |
| `switch(X, @S)` | @S 生存：中断中のフレーム F′／@S 不在：新規作成 | 生存時：F を中断（破棄しない）、F′ をアクティブに（木の形は不変）／不在時：新規フレームを作成（兄弟規則：最も近い switch 製祖先の兄弟、無ければ現在 F の子） | F′ がアクティブ（生存時は続きから、新規時は X の initial variant から）。**barrier あり**、begin マーカー = @S |

### 戻り先が無いとき

`back()` / `back(X)` はともに **barrier で停止し no-op**——barrier の外側は通常の `back` で越えられない。壁を越えて畳めるのは `exit` / `dismiss` だけ、という役割分担を保つ。barrier の**無い**フレーム境界は `back(X)` の探索が越える——越えた子フレームは begin マーカーごと破棄される（`back()` の最下段規則と同型。`push(A, @S)` の中から `back(ホーム)` すると @S も消え、後続の `exit(@S)` は no-op になる）。木のどこにも積まれていない component を `back(X)` の対象に指定した場合や、ルートで `back()` した場合も同様に no-op。
`exit(@S)` / `dismiss()` で戻り先が見つからない場合（木のどこにも該当する `@S`／無名セッションが無い）も **no-op**（何も起きない）。ツールはいずれも警告してよい（「セッションの mismatch」と同じ方針）。

### セッションの mismatch

`push` で積んだ無名の範囲を `dismiss()` で閉じようとする（無名セッションが無ければ no-op）、`present(X)` で開いたモードを `back()` で抜けようとする（barrier で止まる no-op）、といった**開始と終了の形が食い違う**組み合わせ（**mismatch**）は、shitae では**エラーにしない**。静的に検出しづらく、止めると作図の妨げになるため。ただしこのまま実装に進むと画面遷移の設計問題になりうるので、処理系は**実行時に警告**してよい。

なお、named session については `exit(@S)` と `dismiss(@S)` が同義（「present / dismiss は compound verb」を参照）なので、`present(X, @S)` で開始したセッションを `exit(@S)` で閉じるのは**ねじれではない**——正規の対応である。

## オーバーレイ（show / hide）

「アクティブなフレームは常に 1 つ」の外側に、常時表示されうる component がある——ミニプレイヤー、PiP、着信バナー、トーストなど。これらはフレーム木のどこか 1 点に属する画面ではなく、フレームをまたいで画面の上に乗り続ける。

処理系は実行時状態として**オーバーレイ集合**を持つ。エントリは **(component 名, 表示 variant)** の組——ID は component 名が兼ねる（同一 component の多重掲示は扱わない）。

- result として `show(X)` / `show(X##v)` / `hide(X)` と書ける。どの interaction の結果列からでも、掲示の追加・除去ができる。
- `show(X##v)` は表示 variant を v にして掲示する。`show(X)`（variant 省略）は **X の initial variant** で掲示する。
- **掲示中の component への再 `show` は表示 variant を上書きする**（`hide` を経由しない。省略形の再 show は initial への上書き）。掲示中 component が自分の見た目を変える正攻法はこの**自己再 show**——裸 `##v` の遷移はアクティブ画面側に解決されるため、この用途には使えない（「variant の参照は必ず ##」を参照）。
- X が singleton（`#!`）の場合、エントリは共有レジストリへの参照であり、initial への上書き規則は適用しない（共有 variant の現在値が常に見える）。逆に singleton への `show(X##v)`（明示 variant）は**表示 variant の選択ではなく共有状態の書き換え**——取得済みクーポンに `show(クーポン##未受取)` と書くと状態が巻き戻る。共有の現在値をそのまま掲示したいときは省略形 `show(X)` と書く（「singleton component」を参照）。
- `hide(X)` は X が掲示されていなければ **no-op**。
- 掲示中の component は**全画面で表示**され、その**表示中 variant の実効 body（共通＋固有）**の interaction がどのフレームがアクティブでも有効——presence gate の判定も同じ基準（掲示中 component 自身の表示 variant。アクティブ画面の body は見ない）で行う（「操作は variant に属する」の裸参照規則を参照）。
- overlay の interaction に書いた**無修飾 component 参照**（`set` / `show` / `hide` / nav-target）の module 帰属は、**overlay 自身が定義されたファイル**（レキシカル）で解決する——発火時にどの画面がアクティブかとは無関係（「モジュール化」を参照）。裸 `##variant`（自己再 show 等）はこの規則の対象外——同一 component 内の variant 切替は引き続きアクティブフレーム側の動的解決のまま（「variant の参照は必ず ##」を参照）。
  例：モジュール `mod` で定義した `#! 状態` を掲示中の component が持つ interaction に無修飾 `set(状態##停止)` と書いた場合、掲示元の画面がどのモジュールでアクティブでも `mod` の共有状態が書き換わる——`mod::状態` と明示したのと同じ意味になる。
- オーバーレイは**フレームではない**——`back` / `exit` / `dismiss` の走査対象に入らない。消えるのは明示的な `hide(X)` のときだけ（フレームが破棄されても連動しては消えない）。
- ID は component 名が兼ねる。同一 component の多重掲示は初版では扱わない（実需が出るまで別 ID は導入しない）。
- 引数は component 1 つ——collection の `*` は書けない（`show(*X)` は E024）。裸 `##variant` も書けない（母体が無い。E027）。
- テキストだけの一時的なヒント（トースト等）に専用機構は用意しない。**本文がそのテキストである component を `show` する**ことで表す。
- gate（presence gate）とは**別軸**。gate は「その variant の実効 body に対象があるか」だけを見て、掲示状態は見ない。オーバーレイの interaction の有効性は gate ではなくこの節の規則による。
- 特定の画面でだけオーバーレイを除外する（例：Now Playing 画面の上にはミニプレイヤーを出さない）記法は初版では見送る。既知の制限として、必要なら書き手が自然文で注記する。

```
# プレイヤー
> 曲をタップ -> 再生を開始する ; show(ミニプレイヤー##再生中)
> 停止 -> hide(ミニプレイヤー)

# ミニプレイヤー
## 再生中
曲名
> タップ(一時停止) -> show(ミニプレイヤー##一時停止)   // 自己再 show で表示 variant を切り替える
> タップ(曲名) -> push(プレイヤー)                      // 掲示中はどの画面からでも押せる
## 一時停止
再開ボタン
> タップ(再開ボタン) -> show(ミニプレイヤー##再生中)
```

## 行動（インタラクションの左辺）

インタラクションの左辺は **行動**。行動は**自然文で何でもよい**（タップ／長押し／引っ張って更新／3秒長押し…）。評価されない注記であり、同じ対象に複数の異なる行動を書ける。

対象を取るときだけ括弧に参照を入れる。対象を限定しない行動（画面全体のスワイプ、対象が自明な更新など）は括弧を省略してよい。空の括弧（`行動()`）は構文エラー（E026）——対象なしなら括弧ごと省略する。

- 構造記号としての丸括弧は**半角** `(` `)` のみ。全角 `（）` は自然文の一部として素通りする（`> プッシュ通知（新着）をタップ -> push(記事詳細)` の `（新着）` は行動文字列の一部）。
- 行動はユーザー操作に限らない。**外部で起きること**（プッシュ通知の受信・セッション切れ・配達完了など）も行動の自然文として書くのは想定内の用法。
- OS の戻るボタン・戻るジェスチャも自然文で書く（`> 戻るジェスチャ -> back()`）。`back()` は結果側の transition verb であって、行動側の語彙ではない。

```
> タップ(設定) -> present(設定)
> 長押し(設定) -> present(クイック設定)            // 同じ対象に別の行動
> タップ(保存) -> 設定が保存される ; dismiss()      // 副作用と遷移を併記
> 更新 -> リストが更新される                        // 対象なし・遷移なし。括弧省略
```

左辺 `行動(対象)` と、右辺の遷移 `transition verb(対象)` は同じ「語(対象)」の形で対称。左辺の語は自由な自然文、右辺の transition verb はコア 4 語（`push`/`back`/`goto`/`exit`）＋compound verb（`present`/`dismiss`/`switch`）に限られる。右辺にはこのほか副作用（自然文）も書け、`;` で並べられる。

> 注意：右辺に transition verb がなければ**副作用**（自然文）と解釈される。`保存 -> 完了` の `完了` は「完了する」という副作用であって、画面遷移ではない。`完了` という画面へ遷移させたいなら `push(完了)` と書く。遷移のつもりで transition verb を書き忘れると、黙って副作用扱いになる（ラフさの代償）。図示ツールは、未定義 component への遷移は描けても、transition verb なしの自然文は edge にしない。

## component に特権はない

`card` `text` `button` `field` のような**組み込み component は持たない**。すべての名前は対等で、定義があれば自作 component、なければ未定義 component（ラフに置いただけ）。参照は**定義順と無関係**——ファイル中で後に定義される component への前方参照は、document common に限らずどこからでも可。`button` と書いてもよいが、それは「button という名の component を置いた」だけで、押せる・見た目がボタン、といった特別な意味は持たない（押せるかどうかは行動を書いたかで決まる）。

アラート・トースト・モーダルのような汎用部品も、必要になったらその場で `#アラート` のように明示的に定義して使う。言語はメカニズム（component 定義と遷移）だけを提供し、どんな部品があるかという語彙は書き手が決める。

## inline component とグルーピング

`{ ... }` で、その場限りの component を定義できる（**要素のみ**。variant `##` やインタラクション行は持たない）。alias を付ければ、入れ物と中身の両方に名前が付く。

collection 全体への操作は、参照側でも `*` を前置した素の `*サムネイル` を行動対象にすれば書ける——inline で包む必要はない（「collection」を参照）。

```
*サムネイル
> スクロール(*サムネイル) -> 続きを読み込む       // collection 全体への操作
> タップ(サムネイル) -> push(記事詳細)            // 1 インスタンスへの操作
```

「入れ物とその中身に別々の名前を付けたい」（フィードという入れ物の中にサムネイルという collection がある、と呼び分けたい）ときは、inline で包んで別名を与える——これは**追加の手段**であり、collection 全体を参照するのに必須ではない。

```
フィード: {
  *サムネイル
}
> スクロール(フィード) -> 続きを読み込む          // 入れ物（フィードという別名）への操作
> タップ(フィード.サムネイル) -> push(記事詳細)     // 中の要素への操作
```

`*` を付ける名前で collection 性が決まる：`*フィード: { サムネイル }` なら「フィードが複数」、`フィード: { *サムネイル }` なら「単数のフィード、中にサムネイルの collection」。`in` のような専用記法は導入しない。inline が物足りなくなったら（variant やインタラクションを持たせたくなったら）、名前付き `#` component に昇格させる。inline は「要素をまとめる軽い箱」、挙動は外側のインタラクション行から参照して書く。

**inline の入れ子は 1 段まで**。`{ { ... } }` のように inline の中に inline を書くのは**構文エラー**——それ以上の階層が要るなら、内側を名前付き `#` component に昇格させる。

## モジュール化（名前空間）

規模が大きくなったら、**ファイル＝モジュール＝名前空間**として分割する。見出しレベル（`#`/`##`）に名前空間を積まない（レベルのインフレを避ける）。1 ファイル内の文法は分割しても変わらない。

```
import auth as auth          // auth.shitae を読み込む

# ホーム
> タップ(ログイン) -> push(auth::ログイン画面)     // 別モジュールの component を :: で参照
```

- `import モジュール名 as 別名` で別ファイルを読み込み、`別名::component` で参照する。モジュール名は同ディレクトリの `.shitae` ファイル名（拡張子省略）。サブディレクトリはパスで書く。
- **モジュールの同一性はファイルで決まる**。alias は参照側の別名にすぎず、同一ファイルを別 alias で import しても同一モジュール（同一の singleton 共有状態・同一の document common）を指す。`別名::` の解決は、その参照が書かれたファイルの import 表による。
- 区切りは `::`（`.` は要素参照、`#` は variant 参照と用途が分かれているため別記号）。
- `import` と `as` は構造キーワード（transition verb とは別カテゴリ）。
- 循環 import は許容する——`import` は名前解決のみで実体の埋め込みではないため、循環しても展開が無限にならない。
- 同名 alias の再 import はエラー（同じ別名で複数のモジュールを import すると衝突する）。
- singleton（`#!`）のモジュール越し共有は**定義ファイル単位**——別モジュールの同名 component とは無関係（「singleton component」を参照）。
- **無修飾（module 修飾なし）の component 参照**（`set` / `show` / `hide` / nav-target とも）の module 帰属も同じ原則で決まる——**その interaction が書かれたファイル**の module に解決する（レキシカル）。発火時にどの画面がアクティブかとは無関係。裸 `##variant`（同一 component 内の variant 切替）はこの規則の対象外——「同一 component」自体が実行時のアクティブ component を指す動的な記法であり、named reference（`X##v`）の module 部分がレキシカルなのとは解決基準が異なる（「variant の参照は必ず ##」を参照）。
- **要素行の参照にも `モジュール::` を前置できる**（`モジュール::部品`）。他モジュールで定義した component を、画面の要素として直接置ける（`x: モジュール::部品` のように alias とも、`*モジュール::部品` のように collection とも組める）。
- モジュール横断で共通する事象（通信途絶・セッション切れ等、どの画面でも起こりうるもの）を 1 箇所にまとめて書く記法は無い——document common はファイル単位のスコープを持つため、各ファイルの document common に複製して書く。

## collection（`*`）

- `*` は要素行の**先頭**（alias があればその前）に置く。「この行が宣言する参照単位が複数ある」という意味。
  - `*サムネイル` … 複数のサムネイル
  - `*手札: カード` … 複数のカード、各々を「手札」と呼ぶ（`手札` で 1 枚を指す）
- `*` を先頭固定にすることで、alias や inline と組んでも掛かる先が一意になる（`*フィード: { *サムネイル }` ＝ 複数のフィード、各々の中に複数のサムネイル）。
- `*` は**参照側にも対称に現れる**（宣言側と参照側で同じ記号が同じ意味を持つ）。インタラクションで**`*` なしに参照**したときは **1 インスタンス**を指す（`タップ(サムネイル) -> push(詳細)` ＝ サムネイルを 1 つ選んだら詳細へ）。**`*` を付けたまま参照**したときは **collection 全体**を指す（`スクロール(*サムネイル) -> 続きを読み込む` ＝ サムネイル全体へのスクロール操作）。
- 入れ物と中身に別々の名前を付けたい（フィードの中にサムネイル、のように呼び分けたい）ときは、inline で包んで別名を与える——これは**追加の手段**であり、collection 全体を参照するのに必須ではない（「inline component とグルーピング」を参照）。
- presence gate（`?`）を collection 参照に付けたとき（`*手札?`）も、存在判定は `*` を剥いだ名で行う（「操作は variant に属する」を参照）。「collection が空でない（1 つ以上ある）」を gate にする記法は無い——要るなら condition label（`[手札なし] ...`）で注記する。
- singleton（`#!`）に `*` は付けられない（E028。「singleton component」を参照）。
- collection は順序を保証しない。前後関係（次の・最後の等）が要るなら condition label や自然文で注記する。

## 未定・分岐

- **未定**は専用記法を持たない。`present(まだ決めてない画面)` `削除 -> 行き先は未定` のように自然文で書く。
- **分岐**は condition label `[...]` を結果に添えて、**1 つの `->` の後に並べる**。条件は評価されない注記。正準形は 1 行 1 ラベルの継続行（`->` を含まない `>` 行）で並べる書き方：

```
> タップ(保存) ->
>     [成功] goto(詳細)
>     [失敗] エラーを表示する
```

`;` で 1 行にまとめても同じ意味になる（`> タップ(保存) -> [成功] goto(詳細) ; [失敗] エラーを表示する`）。

**矢印 `->` は 1 行に 1 つだけ**。分岐を `-> R -> R` のように矢印を重ねて書くのは構文エラー。複数の結果は必ず `;`（または改行の継続行）で区切る：

```
// 誤り（矢印が 2 つ）
> タップ(保存) -> [成功] goto(詳細)
>             -> [失敗] エラーを表示する

// 正しい（-> は 1 つ、継続行で並べる）
> タップ(保存) ->
>     [成功] goto(詳細)
>     [失敗] エラーを表示する
```

**意味論**：結果列は **(条件, 結果) の列**。最初のラベルが現れるまでの result は常に成立する。`[ラベル]` は、**次の別のラベルが現れるまで**の以降の result 群に掛かる（1 つの結果に限らない）。`;` と改行（継続行）はどちらも result の区切りとして同等。同一のラベルが再び現れた場合は同じ条件の再指定であり、その条件の結果群に合流する（別の選択肢にはならない）。

**result は左から順に適用される**。遷移を含む複数の result が同じ結果列に並ぶとき、後続の result は**直前の遷移が変えた状態**に対して効く（frame 木・オーバーレイ集合とも、逐次に更新されていく）。

```
> タップ(通知) -> switch(検索, @tabSearch) ; push(スレッド)   // タブ切替 → 切替後のタブでスレッドへ push
> タップ(完了) -> exit(@wizard) ; push(ホーム)                // セッション破棄 → 破棄後の地点からホームへ push
> タップ(保存) -> dismiss() ; push(次へ)                       // モーダルを閉じる → 閉じた後の画面から次へ push
```

> 注意：逐次適用は裸 `##variant` にも及ぶ。`switch(フィード, @tabFeed) ; goto(##通常)` の `goto(##通常)` は**切替後のフィード**の variant を書き換える（元居た画面ではない）。「元の画面のバッジを消してからタブを移る」なら順序を逆にする——`goto(##通常) ; switch(フィード, @tabFeed)`。

`exit(@S) ; push(固定先)` は「セッション」節で述べた**出口固定の慣用句**（複数の入口から同じセッションに入っても出口を一定にする）。`dismiss() ; push(次へ)` も同型で、モーダルを閉じてから決まった行き先へ進む。

結果は 2 種類の仕組みで条件づけられる：対象の存在（`行動(対象?)` の `?` による opt-in の presence gate。構造的 presence——「操作は variant に属する」を参照）と、condition label（`[成功]` 等。動的で、評価しない注記）。shitae はどちらも評価しない——存在は構造的 presence の判定に留め、分岐はラベルに留める。この形式化により、処理系・図示ツールは「どの条件でどの結果か」を構造として扱える。

> 注意：遷移は必ず transition verb（`push` 等）で書く。`タップ(保存) -> 完了` のように transition verb なしで component 名を書くと、それは**遷移ではなく副作用（自然文）**として扱われる（「完了する」という意味になり、`完了` 画面への遷移にはならない）。画面へ遷移させたいなら `push(完了)` と書く。ラフさの代償として、この取り違えは処理系では検出されない（後でグラフ化や実装に落とす段で気づく）。

condition label は**結果**に付く記法であり、要素行の名前を `[空席] 座席` のように書くのは想定外——処理系は `[` で始まる要素名を警告してよい（W104）。条件付きの要素は variant で分けるか自然文で注記する。

## 扱わないもの（意図的に持たない）

- 状態の条件式・ガード・並行状態（variant で表す。式は評価しない）→ 状態機械（XState 等）の領分
- データ／コンテキスト（変数、フォーム値の保持）、component への引数・props → 実装の関心
- 履歴スタックのデータ構造、戻り先の自動解決
- レイアウト・見た目・寸法 → Figma 等の領分
- component の型・プロパティ定義
- atom / molecule のような粒度（実装・デザインシステムの語彙）

### プロジェクト単位の検査

`check`（診断報告）は**プロジェクト単位**で行う——エントリファイルだけでなく、エントリ + 全 import 先の parse/check 診断を報告し、いずれかに error があれば不正な文書として扱う。E030 / W105 / E028 は、module 修飾つき参照（他モジュールで定義された component への `set` / `goto` / singleton `*` 等）に対しても、その定義先モジュールの情報を使って検査する——モジュール境界を越えたからといって検査対象から外れることはない。

### lint 推奨

処理系は以下を**警告**として出してよい（エラーにはしない）：

- **`語(引数)` の形をした effect**：transition verb の typo（例 `gotoo(X)`）や、まだ予約されていない語を予約語のつもりで書いている可能性がある。
- **component 名と一致する bare 要素名**（「alias のスコープと優先順位」参照）。
- **同一 `@S` の静的な再 begin**：遷移グラフ上、`begin(@S)` から `exit`/`dismiss(@S)` を経ずに到達しうる別の `begin(@S)` を、処理系は警告してよい（分岐で exit する経路があるケースの誤検出リスクがあるため error にはしない）。

予約語は今後増える可能性がある——今は effect として素通りしている `語(引数)` が、その語が将来 transition verb / overlay verb に加わった時点で黙って意味を変える。既存文書の effect がある日から遷移として解釈され得ることに注意する。
