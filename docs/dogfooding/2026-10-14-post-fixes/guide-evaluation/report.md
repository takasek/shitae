# AI_GUIDE の独立利用評価

評価対象は `e985f4ee58ab76339df5b0f59144e1f1a5da91c8`。小課題は「固定の代表文書 A/B の状態（未編集・編集中・保存済）をそれぞれ保持し、対象文書の状態を別の場所から変更する」。README と AI_GUIDE から着手し、過去の dogfooding モデル・レポートは読んでいない。shitae-authoring スキルは適用したが、今回の独立評価に合わせ、既存サンプルは参照していない。製品コードは変更していない。

## 初案と採用したモデル

`initial.shitae` を初案から変更せず採用した。A/B の共有状態をそれぞれ `#! 代表文書A` / `#! 代表文書B` に持たせ、文書一覧、A/B の編集画面、外部操作画面に置いた。編集画面は通常 component で、閲覧・入力という画面の表示状態だけを持つ。共有文書状態と編集中画面の表示状態を分けるためである。

`外部操作画面` の六つの操作は、文書 A/B を名前で指定した `set` により、対象だけの状態を変える。その場で表示されている A/B の状態は更新されるが、外部操作画面に留まる。文書一覧へ戻っても、編集画面を開き直しても同じ文書状態を読む。たとえば A を保存済にしても B は未編集のままである。

編集画面の `編集開始` は `set(代表文書A##編集中) ; goto(##入力)`、`保存` は `set(代表文書A##保存済) ; goto(##閲覧)` とした。`set` は文書の共有 variant を変え、`goto` はアクティブな編集画面の variant を変える。画面を閉じて開き直すと通常 component の編集画面は initial の閲覧になるが、singleton の文書状態は保持される。編集中の文書を再開したら入力画面も自動復元する、という追加要件は今回のモデルには含めていない。

初案を組む時点の根拠は `docs/AI_GUIDE.md:13`（通常 component の独立と singleton の共有）、`:69`（裸 goto の作用先）、`:73-100`（set と固定 A/B の例）だった。これだけで小課題の構成を決められた。

## 普通 component と singleton

通常の `# 文書` を複数の場所に置くと、それぞれのインスタンスの variant は独立する。同じ component 定義であることは、同じ文書 ID の状態を共有することを意味しない。さらに `set(文書##保存済)` では対象インスタンスを特定できないため、定義済み通常 component なら E030 になる。

`#! 代表文書A` は、その定義ファイルを共有の単位として単一の variant 状態を持つ。別の場所に置いても同じ A の状態を参照し、フレームを閉じても文書状態は残る。別モジュールに同名で定義したものは別の共有状態となる。今回の A と B は異なる singleton 定義なので、両者の状態は独立する。

## goto と set の作用先

裸の `goto(##保存済)` は実行時にアクティブな component の variant を変更する。書いた部品そのものを指定する記法ではない。`receiver-probe.shitae` はこの区別を確認するためのモデルで、通常文書という部品に `goto(##保存済)` を書いた。包含画面がアクティブな状態でこの操作を実行した場合、期待値は包含画面が保存済になり、部品の通常文書は未編集のままになる。

`goto(代表文書A##保存済)` と名前を書けば、アクティブな画面を A に置き換える遷移になり、A が singleton なので共有状態も書き換える。外部操作画面に留まって A の状態だけを更新したいときは、`set(代表文書A##保存済)` を使う。`set` は遷移も掲示もしない。アクティブな component 自体が singleton A の場合は `goto(##保存済)` も A の共有 variant を書き換える。

## 有限代表文書と任意数の文書

このモデルは、名前で列挙した固定の二文書を表す。文書 C を増やすなら別定義と別操作を追加することになり、文書 ID を引数として渡す仕組みではない。

任意数の文書をラフに置くなら通常 component を `*文書` として使えるが、同じ文書 ID の状態を画面間で共有・同期する処理は実装の領分で、必要な関係を自然文で注記する。`#! 文書` と `*文書` を組み合わせても、ID ごとの状態管理にはならない。この組合せは E028 になる。共有するのは有限に列挙した variant だけで、ファイル内容、ID、カウンタなどの値は保持しない。

## 困った点と初案からの修正

文書状態の保持・遠隔変更の小課題については、AI_GUIDE の短い A/B 例が直接の足場になり、意味論で詰まる箇所はなかった。通常 component の独立、裸 goto の receiver、固定 A/B と任意数の文書の違いが同じガイドに明示されていたため、部品の状態を裸 goto で更新する初案には進まなかった。

追加確認は singleton を collection にできるか、という限界の確認だけだった。ガイドには「任意個の文書へ一般化できない」とあるが、E028 の直接的な説明は SPEC に進む必要があった。ガイドが詳細の参照先を示しているため、必須の欠落とは評価しない。

CLI の `--help` と引数なし `simulate` は Usage を表示して exit 1 になった。README には `make simulate FILE=...` があるが、CLI `simulate <file>` が HTML を標準出力へ生成することは記載されていない。今回の生成方法は実際の CLI 呼出しで確認した。この使い方の説明があれば生成物を保存する作業は容易になる。

初案のモデル修正はゼロ。負例モデルは最初に空の variant を使い W103 も出たため、各 variant に自然文の要素を加えて対象の E030/E028 のみを残した。この修正は採用モデルとは別の検査用負例に限る。

## 検証結果と残る確認

`verification.json` は実際の各 subprocess の終了コードと出力を記録する。`initial.shitae` と `receiver-probe.shitae` は check が exit 0、標準出力・標準エラーとも空で、診断なし。`ordinary-set-negative.shitae` は exit 1 / E030、`singleton-collection-negative.shitae` は exit 1 / E028 を確認した。

`initial.html` と `receiver-probe.html` は CLI simulate で生成し、いずれも exit 0、標準エラーなし、DOCTYPE と日本語 HTML の開始を確認した。HTML 生成成功はブラウザで期待どおり状態が変わることの証明ではない。ブラウザ操作は親タスクが担当するため、ここでは未実施と記録する。

ブラウザ確認の手順と期待値：

1. `initial.html` の文書一覧で A/B が未編集であることを確認する。
2. 別の場所へ進み、Aを保存済にする。外部操作画面に留まり、A は保存済、B は未編集になる。
3. Bを編集中にする。A は保存済のまま、B だけ編集中になる。
4. 戻って文書一覧を確認し、Aを開く。A は保存済、編集画面は閲覧である。編集開始で文書 A は編集中、編集画面は入力になる。保存で文書 A は保存済、編集画面は閲覧になる。
5. 戻って A を再び開く。A の保存済が残る。B を開くと B の編集中が残り、編集画面は通常 component の initial である閲覧になる。
6. `receiver-probe.html` で部品に書いたgotoを実行する。包含画面の variant は保存済、通常文書の variant は未編集のままになる。

現時点で AI_GUIDE からモデルの作成と機械診断までは完了した。画面操作における状態の保持、他文書を変えないこと、receiver の実挙動は親タスクの確認待ちである。
