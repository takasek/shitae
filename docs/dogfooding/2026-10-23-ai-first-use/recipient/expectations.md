# 受取側が操作前に置いた期待

追加資料要求は1回。HTMLを開くAPIが拒否され、公開CLIで再生・編集するにはsource bytes付きモデルが必要なため、元モデル一式を親へ求めた。提供は1回、visit.shitaeのみ（import・simconfigなしと親が明示）。合格条件や作者の意図の追加回答は求めていない。

## 既存記録の継続

問い: 予約済のまま予約確認を開いて案内を変更し、確定せず取り消しても予約状態が失われないか。

期待: 現地案内で開く → オンライン案内へ変わる → 取り消すと施設詳細へ戻る。共有予約状態は予約済のまま、確定通知は出ない。再保存して別processで再生しても同じ状態と経緯になる。

## 一件だけの要件変更

予約確認を新しく開いた直後の案内をオンライン案内にする。取り消した後に再度開いてもオンライン案内で始まる。共有予約状態、確定後の通知、一覧往復で予約済が残ることは維持する。通常componentの最初のvariantが初期値であるとのAI_GUIDEに基づき、variant節の順序だけを変える。

変更前Red: 元モデルで「詳細を見る → 見学を予約する」を実行し、オンライン案内という期待に対して現地案内が返った（new-requirement-red.json）。このファイルは変更前の実行後に記載した。

変更後の期待: オンラインで開く → 現地へ変更 → 取り消す → 開き直すとオンライン → 確定で施設詳細・予約済・通知あり → 通知を閉じる → 一覧へ戻って詳細を再訪しても予約済、通知なし。旧scenarioは変更後モデルで拒否され、新規記録は保存・別process再生できる。

自己点検: variant参照は##、共有予約状態は既存#!とsetを維持、presentとexitの対応を維持。新しいキーワード・条件式・データ値・遷移先を追加せず、通常componentとsingletonの寿命を変えない。公開CLI checkで構文・参照を確かめる。
