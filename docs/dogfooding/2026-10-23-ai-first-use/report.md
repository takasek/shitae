# 初見AIによる作成・受取の評価

会話を引き継がない新規subagent2体で、公開ドキュメントからのモデル作成と、既存保存記録の受取を評価した。公開CLIでは、作成・取消と確定状態の区別・保存・別process再開・小さな要件変更後の再検討まで進められた。人による受取評価は利用者判断で保留とし、この作業の完了待機条件から外した。

## 1. 作成側：自然文からの備品貸出

作成担当には固定1件の備品貸出という自然文の目的だけを渡し、既存解答モデル・操作列・過去評価・製品実装を渡さなかった。READMEと必要な公開ガイドから表現方法を選び、自分でモデル・期待・JSONLの送受信を用意した。

| 検討 | 公開CLIで観測した結果 | 根拠 |
| --- | --- | --- |
| 取消で仮の受取選択を捨てる | v1はロッカー選択→取消で未依頼、再入場すると窓口。v2は窓口選択→取消で未依頼、再入場するとロッカー | author/expectations.md、各版cli.responses.jsonl |
| 確定後に一覧・詳細を開き直す | ロッカー依頼済を保持。実通信・永続保存の成功とは扱わない | author/v1・v2/confirmed.scenario.json |
| 新規確認の初期受取方法だけを変える | variant節順だけを変更し、新版はロッカーから開始。取消・確定の結果列は同じ | author/change.md、v1/v2のequipment.shitae |
| 保存と版の照合 | 両版の同版別process再生はexit0。新版へ旧記録はMODEL_MISMATCH/exit1。旧記録のhashを修正せず新版を新規記録 | author/validation.json、各replay記録 |

作者liveは17 dispatch・19 query・2 exportの38応答で全てok。17件のhandleを応答から手転記し、要求を17回手入力した。追加の同版再生queryはlive集計に含めない（[作者報告](author/report.md)）。親も両版のcheck・再生・共有値・旧記録拒否を公開CLIで照合した（evidence/parent-author-validation/）。

設計上の収穫は、取消する一時選択と保持する確定依頼を分け、初期値の政策変更を操作で照合できたこと。AI_GUIDEにはこの課題へ直接対応する受取取消・共有予約の説明があり、今回の成功はガイドに近い題材への適用の証拠である。難しい方式の独力発見や任意の業務模型を正しく書ける保証とはしない。

## 2. 受取側：作者の答えを渡さない段階

別の新規subagentには、既存の見学予約v2のHTML・scenario・処理系版だけを渡した。作者のbrief・report・補助script・操作ログは見せず、まず初期推測を保存させた（[stage1](recipient/stage1.md)）。これは上の新規備品モデルの引継ぎとは別の試行である。

受取側はscenarioのtimeline・finalから、案内の切替、確認を閉じて再入場、予約の確定と通知の終了、一覧往復という経緯、および現在は施設詳細・予約済・通知なしであることを説明できた。一方、作者が何を合格条件にしたか、オンライン案内から閉じた意図までは記録外なので不明と明示した。経路からの推測と作者の明示した問いを混同しなかった。

ブラウザーでのHTML表示ができなかったため、この段階はAIによるscenario JSONの読解であり、GUIの読みやすさの成功ではない。公開CLIで再開するため元モデルを1回追加提供した。モデル本文をscenarioから復元したり、内部Sessionへ注入したりしていない。

## 3. 受取後の継続・小変更

元モデルを受領後、既存9 dispatchを新processで再生し、本人が選んだ確認を開く→オンライン案内へ→取消の3操作を加え、12 dispatchの記録を保存した。別process再開後の再exportは保存物全体と一致した（recipient/continued.scenario.json、resumed.scenario.json、verification.json）。元9操作の再入力は不要だった。

次に、初期案内をオンラインへ変える小さな要件変更を本人が選び、元モデルを自分の出力先へコピーしてvariant節順だけを変更した。旧モデルでは新期待と一致しないことを確認し、変更後モデルで9 dispatchを新規記録・別process再開、再export全体の一致を確認した。旧scenarioはMODEL_MISMATCH/exit1で拒否された。確定直後の観測点では通知あり・予約済を公開照会で確認した（recipient/changed-confirm-observation.json）。この旧期待との差は模型変更の検討であり、製品のTDD Redや不具合ではない。

受取側の補助コードは、公開actionsから操作名でhandleを選びassertionも行っている。これはAIの作業として記録するが、手転記負担を測った試行とは分ける。作成側と同じ種類の初期variant変更を選んだため、二者の成功を広範な要件変更の網羅としない。

## 4. 環境・隔離の限界

両担当とも実GUIは未確認。subagentでの表示指定が使えず、file: URLはブラウザーツールに明示拒否された。拒否後にHTTP・別surface・内部APIで回避せず、許可された公開CLIとファイル読取の範囲で進めた。API・URL・拒否全文は author/gui-blocker.md と recipient/stage1.md にある。人に操作を依頼していない。以前の親によるGUI往復成功を、今回の初見AIによるGUI成功には換算しない。

新規subagentは親の会話を継承しないが、共通指示・スキル一覧や履歴メモリが注入される。受取側はメモリが見えていたことと、評価根拠に使わなかったことを申告している。共有filesystemと自己申告による資料制限であり、知識が完全にゼロのAIを用意できたという証明ではない。公開ガイドに過去評価の要約・リンクが含まれる点も両担当が申告し、リンク先は開いていない。読取範囲は各報告を参照。

## 5. 次の判断

AI用として、ガイドを学んでモデルを作ること、保存された状態・経緯を読んで不足資料を求めること、公開CLIで継続・変更後の再検討を行うことは今回の範囲で成立した。新しい処理系不具合はこの試行では見つからず、機能追加を増やさずAIの実案件で利用を続ける判断を維持する。

残る負担は、CLIの送受信準備・handleの再取得、HTMLだけではCLI再開に足りず元モデル一式が必要なこと、問い・期待は作者が別途渡す必要があること。いずれも実際に観察したが、自動移行・照合緩和・新しい言語構文を追加する根拠にはしない。GUIのAI初見利用は未確認で、利用環境の正規の条件が整ったときに別途確認する。

#27/#35/#44の人向け受入は未実施のまま保留し、AIの結果で達成済みにしない。元の48操作／11操作のGUI保存実体は、このAI試行とは別に後から再作成版を受領し、[旧版CLIでの再生と継続を確認](../2026-10-23-recreated-gui/README.md)した。当時の原物を回収したものではなく、AI試行の成功で過去の欠落を埋めたとも扱わない。
