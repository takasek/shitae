# 初見作成・探索記録

対象処理系: `3c68321001771faab35a35fc212056f54bb02bf1`。通常利用者向け文書から初めて作る AI agent 1 名の探索であり、人間一般の評価や正式なユーザビリティ評価ではない。実装、過去 dogfooding、解答モデルは読まない。README、AI_GUIDE、AGENTS、shitae-authoring スキルを読んだ。

## 作成前の問いと期待

題材は図書予約。検索結果から一冊の詳細を開き、予約確認を取り消すか確定する。検索条件・書籍 ID・空き数・予約 API・利用者認証・レイアウトは表現しない。代表の一冊と分岐の選択だけを使い、自然文の予約処理は実データへの書込みを意味しない。

問いは「確認モーダルで戻るを押したら詳細まで漏れるか」「取消後に詳細から検索結果へ戻れるか」「確定後に back すると再び確認画面が出ないか」。検索結果は検索画面の variant、詳細はその上の通常スタック、予約確認は詳細に属する無名の barrier セッションとする。取消または確定で確認セッションの寿命を終える。

| 操作列 | 作成前の期待 |
| --- | --- |
| 検索→本を開く→予約する→戻る | 予約確認に留まる。barrier を越えない |
| 検索→本を開く→予約する→取り消す | 本の詳細へ戻る |
| 取消→詳細で戻る | 検索結果へ戻る |
| 検索→本を開く→予約する→確定する | 確認を閉じ、詳細を予約完了に置換する |
| 確定→戻る | 検索結果へ戻り、確認や詳細を再表示しない |

初案では検索結果画面に失敗時の再入力を含めない。まず寿命と戻り先を歩き、使って必要と感じた小さな修正を別ファイルにする。

## 文書参照の負担

初回は README、AI_GUIDE、AGENTS、shitae-authoring を各 1 回読んだ。SPEC 参照は 0 回。session-usage 参照は 0 回（後で使用した場合は追記）。AI_GUIDE のチェックリストで variant、push、present/dismiss、goto の対象、未定義要素を自己点検した。遷移先は全て定義し、表示用のラフ要素は未定義のままとする。

保存と再開の操作が必要になったため `docs/design/session-usage.md` を 1 回参照した。公開CLIのquery/dispatch/exportScenario/replayとGUIの保存/読込を使うためである。同ファイルを表示した際、末尾の過去検証概要も同時に表示されたが、その評価結論やリンク先は今回の根拠・モデル作成には使っていない。過去dogfooding、解答モデル、実装ソース、SPECは読んでいない。したがって完全に過去評価情報を目にしない実験ではなく、評価文書と手順書が同居する入口の制限がある。

## 初案の検査と実行

`models/author/library-v1.shitae` に対する `check` と `simulate` はともにexit 0。各stderrは空で、静的warning/errorは0件。未定義の表示用要素はラフなままでも診断にならなかった。HTML生成の成功を操作成功の代用にせず、別途CLIと実ブラウザで事前期待を確かめた。

CLIは `evidence/author/run-cli.py` で、受理操作の後に毎回queryして新しいhandleを選んだ。10 dispatch、23 requestを記録し、終了コード0。確認の「戻る」だけはR003のno-opだが受理された操作として記録され、確認画面に留まった。取消は詳細へ戻り、詳細の戻るは検索結果に戻った。確定は確認を閉じた後で詳細を完了画面に置き換え、その後の戻るは検索結果へ戻った。根拠は `evidence/author/v1-cli-trace.json` と `library-v1.scenario.json`。

実ブラウザでも10操作を行い、同じ戻り先を確認した。入力欄を実際に入力して検索したのではなく、shitaeの「タップ(検索する)」という操作を選んだ。モデルは検索語や検索実処理を持たない。`v1-barrier.ax.txt`/`v1-barrier.png` はR003と現在地が予約確認である証拠、`v1-browser-observations.json` は取消後から確定後に戻るまでのAX観測、`v1-confirmed.png` は完了時のスタックの証拠である。GUIの「シナリオを保存」で取得したものを `library-v1-gui.scenario.json` として保持した。GUI保存物を元モデルの公開CLI `session --replay` に渡した別processはexit 0・stderr空だった（`cli-statuses.json`）。

## 小さな要件変更と比較

初案のR003は期待どおりであり、処理系の不具合ではない。ただし、確認画面に「取り消す」と並ぶ「戻る」を置いたのに、後者が何も起こさない設計には利用者の迷いがありそうだと、このagentは判断した。「確認画面の戻るも取消として閉じる」に要件を1件変更した。検索失敗の追加など、ほかの変更は行っていない。

派生先は `models/author/revised/library-v1.shitae`。元ファイルは保持し、entry/module名を変えず、確認画面の1行だけを `back()` から `dismiss()` に変えた。変更後の `check` と `simulate` もexit 0・stderr空。前後HTMLを `evidence/author/library-v1.html` と `library-v2.html` に分けた。同じ `library-v1` 表示でも画面上のmodel短縮IDは初案 `01022bc25e3f`、修正版 `3d6bd2f2364c` となった。

修正版を実ブラウザで「検索→本→予約→戻る」の4操作で歩くと、R003に留まらず詳細へ戻った。`v2-before-mismatch.ax.txt` と `v2-back-dismiss.png` に記録した。これにより、確認の寿命を「取り消す／戻る／確定」で終える判断を具体化できた。画面遷移の安全性と、ボタンの意味の分かりやすさは別の判断だった。

## 旧シナリオの拒否と再検討

旧GUIシナリオを修正版モデルのCLIへ渡すとexit 1で `MODEL_MISMATCH: source bytesが異なるmodule: library-v1` となった。entry名やengineの違いを混ぜていない。CLI診断は、完全一致の保存時HTMLとscenarioの組で再開するか、変更後モデルで新しく記録するよう示した（`v2-old-scenario-replay.stderr.txt`）。

実ブラウザでは、修正版の4操作で詳細に戻ったところへ旧GUIシナリオを選択した。同じsource bytesの不一致を表示した。拒否前後とも現在地は本の詳細、dispatch 4件、現在まで6観測点、スタックは本の詳細と図書検索/結果ありのまま。さらに「戻る」を実行するとdispatch 5件・7観測点となり、検索結果へ正常に進んだ。根拠は `v2-before-mismatch.ax.txt`、`v2-after-mismatch.ax.txt`、`v2-model-mismatch.png`、`v2-continued.ax.txt`。GUI内部全状態の同一性を直接読んだ主張ではなく、現在地・来歴件数・スタックの表示保持と続行を実ブラウザで確認した主張である。

同じ問いを修正版で検討し直すため、公開CLIで新しく11操作を選び、23要求で `library-v2-new.scenario.json` を保存した。旧版の操作列を自動補正してはいない。変更された「戻る」が詳細へ出るため、取消を試す前に「予約する」を1回選び直す必要があった。新規記録は旧版10 dispatchに対して11 dispatchで、必要な再入力は全11操作、増分は確認を開き直す1操作。queryは毎回最新の操作一覧を取り、同名操作を選び直した。

新scenarioを同じ修正版モデルの別processへ渡すとexit 0、再開後queryで図書検索/結果あり・15観測点を確認した。`run-v2-cli.py`、`v2-cli-trace.json`、`v2-new-scenario-replay.stdout.txt`、`v2-new-scenario-status.json` が再実行手順と根拠である。旧版への再開成功と修正版での新記録は別の経路として扱う。

## 所要と負担の解釈

初見作成で構文失敗や修正による再checkは発生しなかった。実行中のR003 1件は意図したbarrier確認である。版変更後のMODEL_MISMATCHはCLI1件・GUI1件で、意図した拒否として扱う。生成成功、静的診断なし、実ブラウザの操作成立、自由文の予約登録の実処理は区別した。予約APIへの書込みは行っていない。

ブラウザ入口には環境の負担があった。subagentのvisibility引数はtrue/falseとも非対応で、省略すると利用できた。file URLはHTTP/HTTPSのみというブラウザポリシーで拒否され、ユーザーが明示していた一時loopback HTTP入口を親が用意してから操作した。製品操作そのものの失敗には数えない。

GUI保存のdownload待機ツールは約716秒、GUI読込のfilechooserを含むツールは約380秒後に返った。後者はchooserのtimeoutMs 10000とtoolのtimeout_ms 20000を指定していた。最終的に保存・選択・読込結果は取得できたが、この壁時計時間を製品の処理時間や一般利用者の作業時間には帰属できない。速度・使いやすさの一般化は行わない。

今回得られた価値は、実装を作らずに確認セッションの寿命と確定後の戻り先を具体化し、見た目だけでは曖昧な「戻る」の要件を1行の派生差分として比較できたこと。負担は、公開Sessionのhandleを毎回照会する手順、変更前後のファイル管理、旧シナリオを変更後モデルで使い回せず操作を選び直すことである。これらはこのAI agent 1名・この図書予約モデル・固定処理系版での観測に限る。
