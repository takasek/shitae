## R1: presence gate の裸参照アルゴリズムが document common では host component を持てない

確度: 高

引用（「操作は variant に属する」節）：
> 裸参照（`投了?`）は **host component（その行動が書かれている component）の現在 variant** の body 直下を見る。

引用（「document common」節）：
> 最初の `#` より前に書いた要素行・インタラクション行は、**そのファイルの全 component に共通**する部分になる。

なぜ問題か：presence gate の裸参照判定は「その行動が書かれている component（host component）の現在 variant」を必須の参照点として定義している。しかし document common は定義上「`#` より前」＝どの component にも属さない領域であり、host component が存在しない。document common に書いたインタラクションに `?` を使った場合（例：`> プッシュ通知をタップ(お知らせ?) -> push(記事詳細)` のような形）、裸参照の判定アルゴリズムは適用不能になる。「対象が未定義 component など判定不能なときは always-on」という既存のフォールバック（同節）は「参照先が未定義」を想定した規定であり、「host 自体が存在しない」という別の失敗モードを文面上カバーしていない。なお member 参照（`日付.選択可能?`）は「対象インスタンスの現在 variant」を見るため、この問題の影響を受けない——裸参照のケースに限られる。

修正候補：document common のインタラクションで裸参照 `?` を使った場合の扱いを明記する。最も自然な選択は「host component が存在しない場合は判定不能として always-on」と既存フォールバックを明示的に拡張すること。あるいは document common では裸参照 `?` の使用自体を禁止し、診断コードを割り当てる。

## R2: document common での裸 `##variant` 禁止に対応する診断コードが無い

確度: 高

引用（「document common」節）：
> document common に書ける遷移先の variant 指定は必ず **`component##variant`** の形で書く。裸の `##variant` は「同一 component 内の variant」を指す記法だが、document common には母体となる component が無いため書けない（**禁止**）。

なぜ問題か：この禁止は文法（EBNF）では捕捉できない。`nav-target` の第 2 選択肢 `"##" , name` は文脈非依存で常に合法な生成規則であり、component 内で書こうが document common で書こうがパーサ上は区別がない。つまりこれは純粋に意味論的な制約であり、診断コードでの施行が必須のはずだが、診断コード表（E001〜E021、W101〜103、R002〜004）にこれに該当するコードが無い。近い候補の E007「`##` が component の外で書かれた」は variant **定義**（`## name single-body`）が component 外に出た場合を指しており、文法上そもそも `component = header, common-body, {variant}` によって variant 定義が component の外に出ることはできない（EBNF レベルで排除済み）ため、E007 はこの禁止とは別物である。

修正候補：新規診断コード（例 E022）を追加し「document common 内の nav-target に裸 `##variant`（同一 component 内 variant 形）を書いた」をエラーとして表に明記する。

## R3: 対応表の `back(X)` 行が「同一フレーム内探索」と「barrier を越える」で自己矛盾

確度: 高

引用（「verb ごとのフレーム木の変化（対応表）」節）：
> `back(X)` | フレーム F | **F のスタックを X まで遡って降ろす** | 見つかれば同じ F・最上段 = (X, 積まれた時点の variant)。**barrier を越える**／見つからない場合は no-op（`##variant` は指定できない）

なぜ問題か：「操作」列は探索範囲を「F のスタック」（＝現在フレーム 1 つの内部）に限定しているように読める。しかし「after」列は「barrier を越える」場合に言及しており、barrier はフレーム境界（親子間）に存在する性質であって単一フレームのスタック内部には存在しない。したがって「barrier を越える」という記述が意味を持つためには、`back(X)` の探索がフレーム境界を越えて祖先フレームまで及ぶ（`back()` が barrier 無しの最下段で子孫フレームを破棄して親へ抜けるのと同型の挙動をする）ことを前提にしているはずだが、それなら「見つかれば**同じ F**」という結論とも矛盾する（祖先フレームで見つかった場合、アクティブフレームは F ではなく祖先フレームに変わるはず）。実際「戻り先が無いとき」節の本文は `back(X)` が barrier で止まることを明言しており（「`back()` / `back(X)` はともに barrier で停止し no-op」）、これは複数フレームにまたがる探索を前提とした記述であり、対応表の「F のスタックを...」という単一フレーム限定の言い回しと食い違う。

修正候補：対応表の `back(X)` 行を「現在フレームから祖先方向へ、barrier に当たるまで探索し、X を含むフレームまで降ろす（該当フレームがアクティブになる）」のように、探索がフレーム境界を越えうることと、成功時にアクティブフレームが変わりうることを明記する。

## R4: 対応表 `goto(X)` 行の「（B2）」が本文中どこにも定義されない孤立参照

確度: 高

引用（「verb ごとのフレーム木の変化（対応表）」節）：
> `goto(X)` | フレーム F、最上段 (A, a) | F の最上段を置き換える（積まない） | 同じ F。最上段が (X, initial)。**begin マーカー・barrier は保存される（B2）**

なぜ問題か：「（B2）」という記号が SPEC.md 全体を通してここ以外に一度も出現せず、対応する定義・脚注・番号付きルールが存在しない。編集時に残った内部ラベル（ドラフト段階の規則番号など）の消し忘れと見られ、読者には何を指すか分からない。

修正候補：「（B2）」を削除するか、意図していたであろう参照（「push / goto と行き先」節、または「フレーム木」節の該当箇所）への `「...」を参照` 形式のリンクに置き換える。

## R5: `show(X)`（`##variant` 省略時）がどの variant を表示するか未規定

確度: 高

引用（「オーバーレイ（show / hide）」節 EBNF コメント）：
> 引数は component（`##variant` 指定は掲示時の variant を選ぶ。裸 `"##variant"` は母体が無いため書けない）

引用（「initial variant とエントリポイント」節）：
> variant 指定なしの**遷移**（`push(X)` / `goto(X)` / `present(X)` 等、`##variant` を伴わないもの）は、X の最初に定義された variant（最初の `## variant`）で開く。

なぜ問題か：「variant 指定なしの遷移は最初の variant で開く」という規則は明示的に「遷移」（transition）を対象にした文であり、`transition` の EBNF 定義（`push-nav | present-nav | goto-nav | back-nav | exit-nav | dismiss-nav | switch-nav`）に `show`/`hide` は含まれない。実際「記号一覧」節・「オーバーレイ」節はどちらも overlay verb を「フレーム木を操作しない**別カテゴリ**」と明言しており、transition とは明確に区別されている。したがって `show(X)`（`##variant` を省略した場合）がどの variant を表示するかについて、SPEC のどこにも明文の規定が無い——「initial variant で開く」規則を流用してよいのか、独立に決めるべきなのか読者には分からない。

修正候補：「initial variant とエントリポイント」節の対象範囲を transition だけでなく `show` にも明示的に拡張するか、「オーバーレイ」節に独立して「`##variant` を省略した `show(X)` は X の最初に定義された variant を表示する」を追記する。

## R6: 掲示中 component が自分の variant を変える手段（`goto(##variant)`）とフレーム前提の齟齬

確度: 中

引用（「オーバーレイ」節）：
> オーバーレイは**フレームではない**——`back` / `exit` / `dismiss` の走査対象に入らない。

引用（「フレーム木」節）：
> `push(X)` / `goto(X)` / `back()` は**現在フレームのスタック**を操作する（積む／最上段を置き換える／降ろす）。

なぜ問題か：`show(X##v)` は掲示時に 1 回だけ variant を選べるが、ミニプレイヤーの再生／一時停止のように、掲示中の component 自身が内部インタラクションで自分の表示 variant を後から変える（`goto(##variant)` 相当）ケースは自然に想定される。しかし `goto` は「現在フレームの最上段を置き換える」と定義されており、オーバーレイは明示的に「フレームではない」とされているため、掲示中 component の interaction がどの「フレーム」に対して `goto` を作用させるのか（あるいはそもそも作用させられないのか）が定義されていない。「オーバーレイの interaction はどのフレームがアクティブでも有効」（同節）という記述も、これが「表示中の variant に紐づく interaction のみ有効」なのか「component の全 variant の interaction が有効」なのかを明確にしていない。

修正候補：オーバーレイ component 自身が `goto(##variant)` で自分の表示 variant を切り替えられるかどうかを明記する。できないなら、掲示中の variant 変更はどう表現するのか（例：`hide` してから別 variant で `show` し直す、を慣用句として明示する）を追記する。

## R7: 同一 component の再 `show`（多重掲示・variant 変更）の挙動が未規定

確度: 中

引用（「オーバーレイ」節）：
> `hide(X)` は X が掲示されていなければ **no-op**。
> ID は component 名が兼ねる。**同一 component の多重掲示は初版では扱わない**（実需が出るまで別 ID は導入しない）。

なぜ問題か：`hide(X)` の「既に非掲示なら no-op」という対称の規定が `show(X)` 側には無い。すでに `X##v1` が掲示中の状態で `show(X##v2)` を呼んだ場合に「表示 variant が v2 に更新される」のか「多重掲示として扱われない（何が起きるか未定義）」のか、規定が無い。「同一 component の多重掲示は初版では扱わない」は「複数インスタンスとして別々に積み上がる」ケースについての言及であり、「同じ ID を指すが variant 指定だけ異なる再 `show`」という、集合意味論（ID による重複排除）そのものからは排除されないはずの通常操作についての規定が欠落している。

修正候補：「掲示中の component に対する再 `show(X##v)` は、掲示 variant を v に更新する（`hide` を経由せず上書き）」のように明記する。

## R8: shadow の「完全一致」判定基準が `*`（collection 全体参照）の有無を明示していない

確度: 中〜高

引用（「操作は variant に属する」節）：
> ここでの「完全一致」は次の基準で操作的に判定する：**行動文字列**は字句正規化後（空白の畳み込み等）の比較、**対象参照**は quote を剥いだ name の等価、**`?` の有無は一致判定に含めない**（`行動(対象)` と `行動(対象?)` は同じ行動として shadow の対象になる）。

引用（「collection」節）：
> `*` は**参照側にも対称に現れる**...**`*` なしに参照**したときは **1 インスタンス**を指す...**`*` を付けたまま参照**したときは **collection 全体**を指す。

なぜ問題か：`?` については「有無を一致判定に含めない」と明示的な取り扱いが書かれている一方、同じ節で新設された `*` の対称参照については同様の明示が無い。EBNF 上 `reference = ["*"], [module::], name, ["." , name]` であり、「name」は `*` を含まない別プロダクションなので、「対象参照は quote を剥いだ name の等価」という一致基準を文字通り読めば `*` の有無は等価判定に含まれない（`*手札` と `手札` は同一対象参照として shadow 判定される）ようにも読める。しかし `*手札`（collection 全体への操作）と `手札`（1 インスタンスへの操作）は意味的に別の操作対象であり、同じ行動文字列でこの 2 つが衝突したときに一方が他方を shadow してしまってよいのかは、`?` のケースと違って一言も議論されていない。

修正候補：`?` と同様に「`*` の有無は一致判定に**含める**（`*手札` と `手張` は異なる対象参照として扱われ、shadow の対象にならない）」旨を明記する（意味的に別の操作である以上、この結論が自然と思われる）。

## R9: 診断コード E001 と E012 が同一の「二重矢印」エラーを重複定義しているように読める

確度: 中〜高

引用（診断コード表）：
> E001 | 継続行の直前に `->` がある（二重矢印。左辺が空） | error
> E012 | 矢印重複（`-> R -> R`。「未定・分岐」参照） | error

引用（「未定・分岐」節、E012 が参照する箇所）：
> **矢印 `->` は 1 行に 1 つだけ**。分岐を `-> R -> R` のように矢印を重ねて書くのは構文エラー。

なぜ問題か：E012 が参照する「未定・分岐」節の誤り例（591〜597 行付近）は、まさに「継続行のはずの行に `->` が現れる」というパターン（1 つ目の `>` 行が `->` を含み新規インタラクションを開始し、2 つ目の `>` 行も `->` を含む）であり、E001 の説明文「継続行の直前に `->` がある（二重矢印。左辺が空）」と字面上区別がつかない。継続行は文法上「`->` を含まない」ことで定義される（`continuation = result-list`）ため、「継続行でありながら `->` を含む」という状態は本質的に「新規インタラクションが 2 つ連続して現れ、2 つ目に本来あるべき行動（左辺）が無い」＝ E012 の `-> R -> R` パターンと同一の違反にしか見えない。E001 と E012 がどう違う入力に対して発火するのか、区別する例が無い。

修正候補：E001 と E012 のどちらかを削除して一本化するか、両者が異なる入力パターンを検出するものであれば、それぞれに区別可能な具体例を追記する。

## R10: エントリポイントの記述に表現ゆれ（「ファイル先頭の component の 1 つ」 vs 「ファイル先頭の component」）

確度: 低

引用（「document common」節）：
> エントリポイントはファイル先頭の component の 1 つだが、任意の画面から始まりうる遷移（deep link 等）は document 共通のインタラクションとして表せる。

引用（「initial variant とエントリポイント」節）：
> ドキュメント全体のエントリポイントは**ファイル先頭の component**。

なぜ問題か：「ファイル先頭の component」は定義上ファイル中にただ 1 つしか存在しない（先頭は 1 箇所）ため、「の 1 つ」という言い回しは文法的に不自然で、あたかも複数のエントリポイント候補があるかのように読める。後段の「initial variant とエントリポイント」節では単数形で明確に言い切っており、表現が統一されていない。

修正候補：「document common」節の文を「エントリポイントはファイル先頭の component だが、...」に修正し、後段の表現と揃える。
