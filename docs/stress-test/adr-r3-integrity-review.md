# ADR r3（0013〜0016）内部整合レビュー

対象: `docs/adr/0013-singleton-module-boundary.md` / `0014-set-verb-remote-variant-write.md` / `0015-doccommon-bare-gate-dynamic-resolution.md` / `0016-least-surprise-batch-r3.md`。突合先: `docs/SPEC.md`（現行）、`docs/adr/0007〜0012`（r2 既決定）、`docs/stress-test/findings-2026-07-r3.md`（D1〜D8）。

目的は転記の忠実性ではなく、転記元 4 ADR 自体および既存決定との**矛盾・未決定・相互衝突**の検出である。

## 観点1: 4 ADR 相互の衝突

### G1: `set(mod::X##v)` の解決と ADR-0013 のキーは論理的には整合するが、相互参照が無い

引用（ADR-0014 決定部）: `set-nav = "set" , "(" , [module-name , "::"] , name , "##" , name , ")"`
引用（ADR-0013 決定部）: 「共有レジストリのキーは (module, component) の組...どのモジュールから `mod::X` で参照しても、同一の (mod, X) レジストリを読む・書く」

問題: `set(mod::X##v)` が (mod, X) の共有レジストリを一意に書き換えることは ADR-0013 の一般原則からの帰結として成立し、論理矛盾は無い。ただし ADR-0014 は ADR-0013 を一度も参照しておらず、両者は同日（2026-07-14）に独立して確定した体裁になっている。set のモジュール修飾がキー規則と整合することが「設計上の意図」なのか「たまたま両立した」のかが記録上判別できない。

深刻度: 要一文（ADR-0014 の Decision または Consequences に「(module, component) キーは ADR-0013 のとおり」の一文を足すべき。実質矛盾なし）

### G2: 診断コード番号は重複・欠番なし

E027・E028（ADR-0016）、E029・E030（ADR-0014）は E026 から連番で衝突しない。R005 も R004 から連番。W105 は新設ではなく既存コードの条件拡張。

深刻度: 問題なし（ただし両 ADR は同日に並行策定されており、番号調整が明示的な相互確認の結果である記録が無い。次バッチでも同様の並行策定が起きるなら、確定前に採番を突き合わせる一言運用を勧める——指摘としては記録のみ）

### G3: W105 の「既存コード拡張」と E027 の「新コード新設」でポリシーが不統一

引用（ADR-0016 A3）: 「従来 `hide(##v)` は E020...に偶然引っかかっていたが、指摘の本質（母体なし）が違うため **E027 へ付け替える**」
引用（ADR-0014 決定部）: 「W105 拡張: `set(X##v)` の v が X に定義されていない variant」

問題: ADR-0016 は「同じ形に見えても指摘の本質（動詞）が違うなら新コードを立てる」という方針を明示的に採る（E020 → E027 の切り出しがその実例）。一方 ADR-0014 は逆に、goto 専用だった W105（「`goto(##X)` の X が未定義 variant」）を set にもそのまま**拡張流用**する。両者は同じ「動詞が違う類似指摘」というケースに対して逆の処理をしており、同一バッチ内でポリシーが割れている。

深刻度: 要一文（設計者に一貫性確認を促す。W105 拡張のままでよいか、W106 を新設するかの判断待ち。実害は軽微だが診断コード設計の一貫性原則に触れる）

### G4: C2（gate の条件源分離不可）の決定が ADR-0014・ADR-0016 の 2 箇所に重複記録されている

引用（ADR-0014「検討した代替案」）: 「gate 自体は「対象=条件源」型のみと SPEC に明記して現状維持」
引用（ADR-0016 C2）: 「gate は「対象自身の状態で対象自身への操作を制御する」型のみ、と SPEC に明記」

問題: 結論は一致しており矛盾ではないが、同一の SPEC 編集項目（gate は対象=条件源型のみ、との明記）が 2 つの ADR の Consequences に独立に書かれている。転記時にどちらを正典としてリンクすべきか曖昧で、片方だけ見た転記者がもう片方の存在に気づかない可能性がある。

深刻度: 要一文（どちらかに「詳細は ADR-00xx を参照」の相互参照を足し、正典を一本化する）

### G5: E029 の例示 4 パターンに collection（`*`）型の誤用が含まれていない

引用（ADR-0014 決定部）: 「E029（parser）: `set` の引数が `component##variant` の形でない（`set()` / `set(X)` / `set(##v)` / `set(X, @S)`）」
引用（同、直前）: 「collection `*`・session `@S` は取れない」

問題: session 誤用（`set(X, @S)`）は E029 の例示に含まれるが、collection 誤用（`set(*X##v)`）は例示に無い。しかも既存の類似ケース（nav-target への `*` は E021、overlay verb への `*` は E024）はいずれも動詞カテゴリごとに専用コードを立てる先例があり、`set` の `*` 誤用が E029（形状不正の包括コード）に含まれるのか、専用コードが要るのかが読み取れない。

深刻度: 要一文（E029 の例示に `set(*X##v)` を追加するか、E021/E024 と同じ扱いにするかを明記する）

### G6: R005 の対象動詞リストに `switch` を含めるのは論理的に到達不能な条件を含んでいる

引用（ADR-0016 B4）: 「**R005**（runtime warning）: アクティブパス上に**生存する同名 @S** がある状態での再 begin（`push`/`present`/`switch` **新規作成**）を警告」

問題: `switch(X, @S)` の resume-or-create 判定は SPEC のとおり**木全体**（アクティブパス限定ではない）で @S の生存を見る（「switch 復帰にはアクティブパス優先が無い（常に木全体で最新）」）。したがって switch が「新規作成」に分岐するのは @S が木のどこにも存在しない場合に限られ、その時点でアクティブパス上にも同名 @S は存在し得ない。つまり「アクティブパス上に生存する同名 @S がある」かつ「switch が新規作成する」という R005 の発火条件は、switch に関する限り両立しえない——到達不能な分岐である。push/present は逆に、begin 判定がアクティブパスの状態と無関係に常に新規作成するため、この矛盾は生じない。

深刻度: 要一文〜要修正（switch を対象動詞リストから外すか、switch について R005 が実質発火しない旨を注記する。実装しても害はない死んだ分岐だが、リストに残すと実装者が無駄な設計をする・仕様の理解を誤らせる）

## 観点2: 既存 ADR・SPEC との衝突

### H1: 設計原則 3「キーワードは transition verb と overlay verb のみ」が set 追加で文字どおり誤りになる

引用（SPEC.md 冒頭「設計原則」）: 「3. **構造記号は構造のためだけ**。キーワードは transition verb と overlay verb のみ。見出し語を持たず多言語中立。」
引用（ADR-0014）: 「予約語カテゴリ：transition verb / overlay verb と並ぶ**第 3 カテゴリ「state verb」**」

問題: set 導入後もこの原則文をそのまま残すと、SPEC 冒頭の最も目立つ主張が自己矛盾する。ADR-0014 の Consequences は「記号一覧・EBNF・予約語・「singleton component」節に追記」とだけ書き、**設計原則そのものの文言修正には触れていない**——4 ADR のどの Consequences にも「設計原則」節の編集指示が無い。

深刻度: 要修正（転記チェックリストから漏れやすい。原則 3 の文言に state verb を追加する編集が必須）

### H2: SPEC 現行の singleton 節「document 内で単一インスタンス」が ADR-0013 の file-scoped 定義と衝突

引用（SPEC.md「singleton component」節）: 「定義ヘッダを `#!` にすると、その component は document 内で**単一インスタンス**になる。」
引用（ADR-0013）: 「singleton の「document」は**定義ファイル（モジュール）**を指す...別モジュールの同名 component（通常・singleton とも）は無関係」

問題: 現行文言はモジュール分割時の挙動について「document」が何を指すか未規定のまま放置されており、ADR-0013 確定後もこのまま残すと「同名なら別モジュールでも共有される」という r2 実装のバグ挙動（今回 B1 として否定された挙動）を読者に連想させたままになる。単純追記ではなく、既存文の意味を上書きする書き換えが要る。

深刻度: 要修正

### H3: SPEC 現行「操作は variant に属する」節の always-on 列挙が ADR-0015 と正面衝突

引用（SPEC.md）: 「対象が未定義 component など判定不能なときは **always-on**...host component が存在しない **document common の裸参照**も同じく判定不能として always-on。」
引用（ADR-0015）: 「document common の裸 gate 参照は、**発火時のアクティブ component の現在 variant の実効 body**...で判定する」

問題: ADR-0015 は ADR-0012 B7a を明示的に supersede する（ADR-0015 冒頭に明記）。SPEC 側の該当文（上記引用）をそのまま残すと、旧規則（判定不能→always-on）と新規則（動的解決）が同一節に両方存在することになり、読者はどちらが有効か判別できない。ADR-0015 の Consequences は「always-on 列挙から「document common の裸参照」を削除し」と明記しており、単純追記ではなく**削除を伴う書き換え**であることが指定されている点は良い（見落としにくい）。

深刻度: 要修正（ADR 自身が書き換え指示を明記済みなので実装漏れリスクは低いが、削除対象の一文が長い列挙文の中に埋め込まれているため、転記時に文の境界を誤って削りすぎる/削り足りないリスクがある）

### H4: hide-nav の EBNF に `##` の受け皿が無く、ADR-0016 が言う「`hide(X##v)`（component 付き）専用」という区分が成立しない

引用（SPEC.md EBNF）: `hide-nav = "hide" , "(" , [ module-name , "::" ] , name , ")" ;`（`##` を含む代替が一切ない）
引用（SPEC.md EBNF、show-nav 側）: `show-nav = "show" , "(" , [ module-name , "::" ] , name , [ "##" , name ] , ")" ;`（component 付きの `##` のみ許容。裸 `##v` は不可）
引用（ADR-0016 A3）: 「E020 は `hide(X##v)`（component 付き）専用に戻る」

問題: 現行 EBNF は hide-nav に `##` を一切許可していない——bare でも component 付きでも構文上は非production である。にもかかわらず診断コード表の E020 は「`hide()` に `##variant` を書いた」を条件として掲げており、これは EBNF の正規形には無い入力を parser が寛容に受理してエラー化していることを前提にした記述である（E021/E024/E025/E026 も同様の「正規形には無い誤り入力を専用コードで検出する」パターンを既に採用しており、これ自体は先例に沿う）。ADR-0016 はこの寛容パースの存在を暗黙の前提として「component 付きなら E020・裸なら E027」と場合分けするが、show-nav 側には「裸 `##variant` は母体が無いため書けない」という注記が EBNF コメントに存在するのに対し、hide-nav 側には対応する注記が無く非対称。

深刻度: 要一文（hide-nav の EBNF コメントに、show-nav と対称な一文——「`##` は本来書けないが、誤り検出のため字句上は component 付き/裸のいずれも認識し E020/E027 で弾く」——を足す。実装の実態には影響しないが、EBNF だけを読む転記者・実装者への説明不足）

### H5: EBNF の `result` production に state verb（set）の受け皿が無い

引用（SPEC.md EBNF）: `result = [ "[" , label , "]" ] , ( transition | overlay | effect ) ;`
引用（ADR-0014 Consequences）: 「SPEC: 記号一覧・EBNF・予約語・「singleton component」節に追記」

問題: 「EBNF に追記」とは書かれているが、具体的に `result` production へ `state`（= `set-nav`）という第 3 の代替枝を追加する必要がある点が Consequences から明示的には読み取れない。transition / overlay と並ぶ「第 3 カテゴリ」という決定の重みに対し、Consequences の記述は抽象的すぎ、転記時に `result` production 自体の書き換えが漏れる可能性がある（`set-nav` という新 production を追加するだけでは、`result` から辿れず孤立した規則になる）。

深刻度: 要修正（`result` production の書き換えは意味論上必須。転記チェックリストに明示すべき）

### H6: 「モジュール化」節に singleton のモジュール境界への言及が無い

引用（SPEC.md「モジュール化（名前空間）」節）: import・`::` 参照・循環 import・同名 alias 再 import エラーのみを規定し、singleton の共有スコープには触れていない。
引用（ADR-0013 Consequences）: 「SPEC: singleton 節に...明記（document common 節と相似の 1 段落）」

問題: ADR-0013 の Consequences は編集対象を「singleton 節」とだけ指定しており、「モジュール化」節側からのポインタ（「singleton のモジュール越し共有については singleton 節を参照」といった一言）を置く指示が無い。document common は「document common」節と「モジュール化」節の両方に記述があるのに対し（SPEC.md 79 行目「モジュール分割時、実行時に有効な document common は...」）、singleton だけ「モジュール化」節に不在のままだと非対称になる。

深刻度: 要一文

## 観点3: 各 ADR 内部の未決定・二義性

### I1: ADR-0013 のエントリモジュール `null` 表現は意図的に未決定のまま——問題なし

引用: 「エントリモジュールの module 表現（現行 `null`）とモジュール名文字列の正規化は**実装詳細**——キーの一意性が保たれれば良い。」

これは ADR 自身が「決めない」ことを明示的に決定した箇所であり、曖昧さの残置ではなく意図的なスコープ限定。SPEC 転記でもこの表現詳細には立ち入らない方針で問題ない。

深刻度: 問題なし

### I2: ADR-0014 の set が overlay 掲示中の singleton に及ぼす効果が、一般則の暗黙適用に留まり明示例が無い

引用（ADR-0014）: 「**意味論**: `set(X##v)` は X の共有レジストリに v を書き込む**だけ**...全所在に即時反映（ADR-0011 の共有規則そのまま）。」
引用（ADR-0011、既存）: 「X が singleton の場合、エントリは共有レジストリへの参照であり、initial への上書き規則は適用しない（共有 variant の現在値が常に見える）。」

問題: ADR-0011 の既存規則から論理的に導けば、「オーバーレイ集合に掲示中の singleton は set の書き換えを即座に反映する」という結論に矛盾なく到達できる（オーバーレイエントリが共有レジストリへの参照だから）。ただし ADR-0014 はこれを具体例として明示しておらず、「全所在に即時反映」という一般文の中に暗黙に含まれているだけである。D7（findings-r3）は逆方向（`show(X##v)` を variant 選択と誤読する事故）を「よくある取り違え」として明記する提案をしており、set → 掲示中 singleton の即時反映も同種の直感に反する挙動になりうる（書き手が「掲示中の見た目は show でしか変わらない」と誤解する可能性）。具体例が無いのは D7 と対になる抜け。

深刻度: 要一文（singleton 節に 1 例——たとえば「掲示中のミニプレイヤーが singleton なら、他画面の `set` がその場で反映される」——を足すことを推奨）

### I3: ADR-0016 R005 の判定タイミングは push/present については明確、switch については G6 のとおり別問題を含む

判定対象は「アクティブパス上に生存する同名 @S」であり、これは既存の frame 木節が定義する「アクティブパス」（現在フレームから祖先方向）をそのまま流用している。push/present の新規 begin については、begin 実行**前**のアクティブパスを見て判定するという読み方で一意に定まり、二義性は無い。switch を含めることの論理的な問題は G6 に記載のとおり。

深刻度: 問題なし（push/present に関する限り）。switch については G6 を参照。
