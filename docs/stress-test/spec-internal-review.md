## R1 ⚠️ 継続行が `##`/`#` の境界を越えたときの「先行するインタラクション」が未定義

該当: 「two-layer model」（30行目）、EBNF の `continuation` コメント（135〜137行目）。

30行目・137行目はいずれも「先行するインタラクションが無い継続行は構文エラー」とだけ言う。
しかし文法上 `single-body` は `document-common` / `common-body` / 各 `variant` ごとに独立したリストであり（116〜123行目）、「先行する」の探索範囲がこの `single-body` 境界を越えてよいかが書かれていない。

境界例:

```
# X
> タップ(A) -> foo
## v1
>     [成功] goto(v2)
```

`## v1` の直下にある継続行（`->` を含まない `>` 行）は、`X` の common-body にある `タップ(A) -> foo` を継続しているのか、それとも `v1` という新しい `single-body` の先頭に「先行インタラクションなし」で置かれた構文エラーなのか、字面から一意に決まらない。
document-common → component の跨ぎ（`#` 境界）でも同型の問題が起きる。

提案: 「継続行の先行探索は同一 `single-body` 内に限る（`##`/`#` を跨いだ時点で常に構文エラー）」と明記する一文を EBNF コメントに追加する。

## R2 ⚠️ shadow 規則の「完全一致」の判定粒度が未定義

該当: 「document common」節（66行目）、「操作は variant に属する」節（212行目）。

shadow は「（行動文字列, 対象参照）が完全一致」で発火するとあるが、「完全一致」がどのレベルの一致か定義されていない。

境界例1（空白・表記ゆれ）:

```
> タップ(戻る) -> back()
## v1
> タップ (戻る) -> goto(別)
```

`action` は `free-text` であり（138行目）、`free-text` は「任意の自然文」（174行目）としか定義されない。
「タップ(戻る)」と「タップ (戻る)」は文字列としては別物だが、書き手の意図としては同じ行動である。
文字レベルの完全一致で判定すると、空白の有無だけで shadow が発火しない事故が起きる——原則5（インデントは意味を持たない）の精神とも整合しない。

境界例2（quoted name の内外）:

```
> タップ(戻る) -> back()
## v1
> タップ("戻る") -> goto(別)
```

`戻る` と `"戻る"` は `name` の文法上どちらも同じ文字列を指しうるが（171行目 `name = quoted-name | bare-name`）、対象参照としての等価性判定（quote の有無を無視して比較するか）が書かれていない。

提案: 「完全一致」を「行動文字列は自然文としての字面比較（空白の正規化を行うか否かを明記）、対象参照は quote の有無を無視した name の等価性」という形で操作的に定義する。

## R3 ⚠️ presence gate と collection の交差 — 「存在」の単位が未定義

該当: 「記号一覧」の `?`（86行目）、「操作は variant に属する」2.（207行目）。

`?` は「その variant に対象が存在する時だけ行動が有効」と説明されるが、対象が `*`（collection）のときの「存在」が何を意味するか書かれていない。

境界例:

```
# フィード
*サムネイル
> タップ(サムネイル?) -> push(詳細)
```

`サムネイル` は collection であり「複数あるという宣言」（78行目）だが、複数の下限（0個でもよいか）は規定されていない。
`タップ(サムネイル?)` の `?` は「collection が空でない」ことを条件にするのか、それとも「`*サムネイル` という宣言行そのものがそのvariantに存在する」ことだけを条件にするのか(＝要素数に関係なく常に真)が不明。
前者だとすれば shitae が持たないはずの「個数」という動的な状態を暗黙に導入することになり、原則6（状態は variant で表す）と緊張する。

提案: presence gate の「存在」を「そのvariantの実効body（共通＋固有）に、対象と同名の alias／ref が element-line として書かれているか」という静的・構文的な条件として明文化し、collection の場合も同じ基準（個数は問わない）であることを明記する。

## R4 ⚠️ document common からの裸 `##variant` 参照はどの component の variant か未定義

該当: 「document common」節（52〜64行目）、EBNF `nav-target`（166〜167行目）。

`nav-target` は `"##" , name`（同一 component 内の variant参照）を独立した選択肢として許す。
これは component 内部（`common-body` や `variant` の中）を想定した規則だが、grammar上は `document-common`（=`single-body` の一種）でも同じ `interaction-line` が使え、そこから `##variant` を書くことを文法は禁止していない。

境界例:

```
> プッシュ通知をタップ -> push(記事詳細)
> セッション切れ -> goto(##ログイン画面)

# スプラッシュ
...
```

document common は「そのファイルの全 component に共通」（52行目）であり、特定の「現在の component」という文脈を持たない。
`##ログイン画面` は「同一 component 内の variant」という前提（82行目、251行目）が成立する母体が無いため、この行が指す先が定義されない。
静的エラーにすべきか、それとも「呼び出し元 component の同名 variant」のような動的解決を意味するのか、どちらとも取れる。

提案: 「document common では裸 `##variant` は使用不可（常に `component##variant` 形式を要求する）」という制約を明記する。あるいは意図的に許すなら解決規則を定義する。

## R5 ⚠️ 同名 `@S` の多重開始・遠隔破棄の曖昧性

該当: 「フレーム木」節（293行目）、「セッション」節（270〜271行目）。

271行目は「同じ画面を別の場所で push すれば別のセッションになる」と述べ、同名 `@S` が複数同時に生存しうることを前提にしている。
293行目は `exit(@S)`/`dismiss(@S)` の探索を「アクティブパス上で同名複数なら直近まで（LIFO）」→見つからなければ「木全体から@Sを探して遠隔破棄」と規定するが、後者（遠隔破棄）で同名 `@S` が木の複数箇所（アクティブパス外）に同時に存在する場合、どれを破棄するかの規則が無い。

境界例:

```
# A
> タップ(1) -> push(B, @s)
> タップ(2) -> push(C, @s)
```

`A` から `push(B, @s)` した後 `back()` で `A` に戻り（`@s` セッションは破棄されず残存— push,@S は back barrier なしのため back で `A` の位置には戻れるがフレーム自体は残る、と読める）、続けて `push(C, @s)` すると同名 `@s` の子フレームが2つ、アクティブパス外に並存しうる。
この状態で他の場所から `exit(@s)` を遠隔実行したとき、どちらが破棄されるか（生成順？ 木の走査順？）が規定されていない。

提案: 同名セッションの多重開始をそもそも禁止（lint／静的エラー）するか、遠隔破棄の場合の探索順（例: 深さ優先で最初に見つかったもの、生成が新しい方、等）を明記する。

## R6 ⚠️ component 名・variant 名の重複が禁止されていない

該当: 「記号一覧」`#`/`##`（74〜75行目）、EBNF `header`/`variant`（117・120行目）。

文法上、同一ファイル内で同じ名前の `# X` を複数回書くこと、同一 component 内で同じ名前の `## v` を複数回書くことを妨げる規則が無い。

境界例:

```
# A
## v1
...
## v1
...

# A
...
```

`push(A)` はどちらの `# A` を指すか、`goto(##v1)` はどちらの `## v1` を指すかが未規定。
component 名はグラフの頂点そのものであり（244行目 nav-target の `name`）、遷移語彙全体の参照解決の土台になるため、重複が許されるのかどうかは軽微な問題ではない。

提案: 「同一スコープ内での component 名・variant 名の重複は禁止（静的エラー）」を明記する。

## R7 ❌ `back(X##variant)` の文法と「積んだ時点の variant へ戻る」原則の緊張

該当: EBNF `back-nav`/`nav-target`（159・166〜167行目）、「フレーム木」節（295行目）。

`back-nav = "back" , "(" , [ nav-target ] , ")"` であり、`nav-target` は `component##variant` 形式を許す（166行目）。
文法上 `back(記事詳細##コメント)` は valid である。

一方 295行目は「戻り系はスタックに積まれた時点の variant へ戻る（initial variant にリセットしない）」と明言し、戻り先の variant はスタックに記録された過去の状態で決まる、つまり呼び出し側が variant を指定して選べないという設計を示している。

この2つは両立しない。`back(X##variant)` という記法が文法上存在するのに、意味論はそれを使う余地を与えていない。
考えられる解釈は少なくとも3つある。

1. `##variant` 部分は back では常に無視される（デッドシンタックス）。
2. `##variant` はスタック内から「X かつその variant」の位置を検索するためのフィルタとして働く（複数箇所に同じ X があるとき、どれへ戻るかを絞り込む）。
3. `##variant` は到達後に variant を強制上書きする（295行目の原則を破る特殊ケース）。

どれが正なのか SPEC からは判定できない。

提案: `back-nav` の `nav-target` から `##variant` を落として `back(component)` のみに単純化するか、上記解釈のいずれかを明文化する。

## R8 ⚠️ barrier なし子フレームが `back()` で使い果たされたときの「現在フレーム」遷移が未定義

該当: 「フレーム木」節（290〜291行目）、「セッションと『back barrier』は直交」節（281行目）。

290行目は「`back()` は現在フレームのスタックを操作する（…降ろす）」と、back の作用対象を常に「現在フレーム」のスタックに限定する。
しかし281行目の例（`push(X, @S)` の閲覧フロー）は「記事→関連記事→さらに関連…各段は `back` で 1 つずつ遡れる」と書いており、これは `push(X,@S)` が作った barrier なし子フレームの中を降りていく話である。
子フレームのスタックを最後まで降りきった（＝子フレームの積んだ先頭要素まで戻った）とき、barrier が無いのだから理屈上さらに `back()` すれば親フレームへ「抜ける」はずだが、この「子フレームの底を割って親フレームへ抜ける」遷移そのもの——現在フレームというアクティブなポインタが子から親へどう付け替わるか、その際に子フレーム自体は破棄されるのか、それとも空のまま木に残り続けるのか——が一切定義されていない。

境界例:

```
# ホーム
> タップ(記事) -> push(記事, @reading)

# 記事
> タップ(関連) -> push(関連記事)   // 同一フレーム内に積む（セッションなし）

# 関連記事
> 戻る -> back()   // 記事へ。ここでさらに戻る
```

`記事` の位置（`@reading` の begin 地点）でさらに `back()` した場合、これは「子フレーム `@reading` のスタックが尽きたので親フレーム（ホーム）へ抜ける」動作になるはずだが、この遷移を規定する条文が無い。
294行目は `exit(@S)` による明示的破棄しか子孫破棄の契機として述べておらず、「暗黙の使い果たしによる破棄」は別扱いなのか同じ扱いなのか不明。

提案: 「barrier なし子フレームのスタックが尽きた状態で `back()` した場合、子フレームを（`exit(@S)` 相当で）破棄し親フレームへ復帰する」という遷移規則をフレーム木節に追記する。

## R9 ⚠️ alias 名前空間と component 名前空間の関係が未定義

該当: 「記号一覧」（77・79行目）、「`.`と`##`は軸が違う」節（99〜103行目）。

`名前: 実体`（alias）と component 参照はどちらも同じ字句カテゴリ `name` を使う（77行目「名前は自由」、79行目 alias）。
alias は「要素や inline に呼び名を与え」局所的に使われるものだが、その局所性（スコープ）が明記されておらず、グローバルな component 名前空間との衝突規則も無い。

境界例:

```
# ボタン
...

# X
ボタン: 保存
> タップ(ボタン) -> push(詳細)
```

`X` の中で `ボタン` という alias を宣言すると、同じ字句 `ボタン` がトップレベルに実在する component 名でもある。
`X` 内で `ボタン` を参照したとき、ローカル alias（保存要素）が勝つのか、グローバルな `# ボタン` component が勝つのか、あるいは曖昧としてエラーになるのか規定が無い。
103行目「参照は alias 名（または component 名）で引く」という一文は両者が同一の解決ロジックに載ることを示唆するだけで、優先順位を与えていない。

提案: alias は常にそれが宣言された `single-body`（とその内側）にローカルスコープであり component 名前空間より優先される、と明記する。あるいは alias と component 名は別名前空間であり構文上区別する（例: 別記号を与える）よう再設計する。

## R10 ⚠️ inline の多段ネストと「`.` は1段まで」の衝突で内部要素が到達不能になる

該当: 「記号一覧」`.`（81行目）、EBNF `reference`（141行目）、「inline component とグルーピング」節（383〜395行目）。

`inline-body`（129行目）は `element-line` の並びであり、`element-line` は `ref | inline` を取れる（125行目）ため、inline は文法上何段でもネストできる。
一方 `.` による要素参照は「1段まで」と明記されている（81・141行目）。

境界例:

```
# A
フィード: {
  グループ: { *サムネイル }
}
> タップ(フィード.グループ.サムネイル) -> push(詳細)
```

`フィード.グループ` までは1段参照だが、その先の `.サムネイル` を足すと2段になり文法上表現できない。
`フィード.グループ` という中間の inline（グルーピング用の空箱）を参照しても、その中身の要素へは外側から一切到達できないことになる——inline を2段以上ネストする理由（グルーピング）そのものが、外部からは使い物にならない。

395行目は「inline が物足りなくなったら…名前付き `#` component に昇格させる」と述べるが、これは「variant やインタラクションを持たせたい」場合の昇格理由であり、「2段ネストしたら参照できなくなる」という別の制約には触れていない。
1段制限の動機（なぜ2段以上を禁じるのか）もどこにも書かれていない。

提案: 「`.` は名前付き component をまたぐときのみ1段」「同一 component 内の inline ネストチェーンは制限しない（`フィード.グループ.サムネイル` のような複数ドットを許す）」のように、制限の対象を明確化する。あるいは「inline のネストは1段までしか意味を持たない」ことを明記し、2段目以降を静的エラーにする。

## R11 ⚠️ 同名要素 alias が variant 間で異なる実体を指すとき、「曖昧にならない」の主張が破れる

該当: 「`.`と`##`は軸が違う」節（103行目）。

103行目は「同名の要素 alias が複数の variant にまたがって存在しても曖昧にはならない。それは『variant に依らず存在する共通の操作』を意味し、挙動はどの variant でも共通」と述べる。
しかしこの前提（挙動が共通）を強制する構文的な制約は無い——同じ alias 名が variant ごとに異なる実体を指すことを文法は禁止していない。

境界例:

```
# プロフィール
## 未フォロー
アクション: フォローする
## フォロー済
アクション: フォロー解除する
```

外部から `プロフィール.アクション -> push(詳細)` のように参照したとき、103行目の主張（「挙動はどの variant でも共通」）は実際には成立していない——`未フォロー` の `アクション` と `フォロー済` の `アクション` は指す実体（ref）が異なる。
「曖昧にならない」という言明は、あくまで「解決先のalias名が一意に定まる」ことを言っているだけで、「その解決先が意味的に同じ操作である」ことは書き手の規律に委ねられており、SPEC はそれを検証も強制もしていない。

提案: 103行目の記述を「参照解決は曖昧にならない（alias名は一意に定まる）が、意味的な一貫性（挙動が本当に共通か）は書き手の責任であり shitae は検証しない」のように、保証の範囲を正確に書き直す。

## R12 ⚠️ action の自由文がリテラルな括弧を含む場合のパース曖昧性

該当: EBNF `action`（138行目）、`free-text`（174〜176行目）。

`action = free-text , [ "(" , reference , [ "?" ] , ")" ]` であり、`free-text` は「任意の自然文（行コメント `//` の手前まで…行動内（括弧前）では `->` の手前まで）」としか制限されない。
つまり `free-text` 自体に丸括弧を含めることを妨げる規則が無い。

境界例:

```
> いいね(2回目) -> push(詳細)
```

書き手の意図が「『いいね(2回目)』という一つの自然文の行動」（対象なし）だったとしても、パーサは `いいね` を `free-text`、`(2回目)` を対象参照の括弧と解釈しうる——`対象を取るときだけ括弧に参照を入れる`（364行目）という運用ルールと、自然文が自由に括弧を含みうるという `free-text` の緩さが正面衝突する。
quoted name はこの曖昧性を解消しない（quoted name は `name` の話であって `free-text` 全体を囲む機構ではない）。

提案: 「`free-text` は丸括弧を含んではならない（含めたい場合は行全体または該当部分を `"..."` で囲む）」という制約を `free-text` の定義に明記する。

## R13 💭 quoted name にエスケープ機構が無いことの動機が書かれていない

該当: 「記号一覧」`"..."`（87行目）、EBNF `quoted-name`（172行目）。

SPEC は他のほぼ全ての制約（`.` の1段制限を除く）について「なぜそう決めたか」を丁寧に書く文書だが、「エスケープ機構なし」という制約だけは理由の記述が無い。
帰結として、name の中にリテラルな `"` を含めることが原理的に不可能になる（例: `"5\"インチ画面"` のような表現ができない）。
ラフ言語としては許容範囲かもしれないが、他の箇所の説明密度と比べると不自然に軽い。

提案: 一言でよいので「ラフ記法に複雑なエスケープ規則を持ち込まないため（原則2）。`"` を含む name が必要な場合は自然文側の言い換えで回避する」等の動機を添える。

## R14 ⚠️ import 循環の扱いが未規定

該当: 「モジュール化（名前空間）」節（397〜410行目）。

`import auth as auth` の例はあるが、`A.shitae` が `B.shitae` を import し、`B.shitae` が `A.shitae` を import する相互参照（循環 import）についての規定が無い。
`::` による参照は名前解決だけであり実体の埋め込みではないため実害は薄いと推測できるが、SPEC 上「許可する」とも「エラーにする」とも書かれていない。

提案: 「import は名前解決のみを行い、循環しても実行時・解析時に問題は起きない」旨を一文で明記する（意図的に許容するなら、それを言明するだけで十分）。

## R15 ⚠️ component が0個のドキュメントでは「エントリポイント」が定義できない

該当: EBNF `document`（110行目）、「initial variant とエントリポイント」節（259行目）。

`document = { import } , document-common , { component }` であり `{ component }` は0回でもよい。
一方259行目は「ドキュメント全体のエントリポイントはファイル先頭の component」と断言する。

境界例:

```
> プッシュ通知をタップ -> push(記事詳細)
```

これだけで構文上は valid なドキュメントだが、component が1つも無いため「ファイル先頭の component」という前提が成立せず、エントリポイントが存在しない。
実務上こういうファイルを書く動機は薄いかもしれないが、文法が許す形と意味論の前提が食い違っている点は事実として指摘しておく。

提案: 「1つ以上の component を持つことをドキュメントの妥当性条件とする」と明記するか、component 0個時のエントリポイント未定義を許容する旨を書く。

## R16 ⚠️（文書構成 / 規範の分散）「戻り先が無いとき」の規則が4箇所に重複記述されている

該当: `back-nav` コメント（158行目）、`exit-nav` コメント（160行目）、`dismiss-nav` コメント（162行目）、「戻り先が無いとき」節（352〜354行目）。

「戻り先が見つからなければ no-op」という同一規則が、EBNF の各 nav コメントで3回個別に述べられ、さらに専用の節でもう一度まとめて述べられる。
内容は一致しているため今回は矛盾ではないが、将来 no-op の条件（例: warning の出し方）を変更する際に4箇所すべてを同期する必要があり、修正漏れのリスクが構造的に埋め込まれている。

提案: EBNF コメント側は「詳細は『戻り先が無いとき』を参照」と参照だけにし、規範の実体は専用節に一本化する。

## R17 ⚠️（文書構成 / 前方参照）shadow 規則が「document common」節で先出しされ、詳細な定義は約150行後

該当: 66行目「shadow 規則も同じ原理で拡張される」と212行目の本体定義。

66行目は「shadow 規則」という語を初出でいきなり使い、「（行動文字列, 対象参照）が完全一致する定義が複数の階層にあれば、より特化した階層が勝つ」と簡潔に述べるが、この時点では読者はまだ「shadow」が何を指すか説明を受けていない（本体の定義は212行目「操作は variant に属する」節に置かれている）。
節をまたいだ前方参照であり、「詳細は後述『操作は variant に属する』を参照」のような明示的なポインタが無い。

提案: 66行目に「（詳細は『操作は variant に属する』節を参照）」という一文を足す。あるいは shadow 規則の完全な定義を先に一箇所にまとめ、両節から参照する構成にする。

## R18 💭 collection の「全体」参照が常に二重ラッピングを要求される

該当: 「collection（`*`）」節（412〜419行目）。

`*手札: カード` のように単独で collection を宣言すると、参照 `手札` は常に単一インスタンスを指す（418行目）。
collection 全体（例: シャッフルする、枚数を数える、といった全体操作）を参照したい場合、419行目の指示に従い `フィード: { *サムネイル }` のように別名でもう一段くるむ inline が必須になる——「複数であること」を宣言した `*手札` 自身を、そのままの形で「全体」として参照する構文が存在しない。

デザインとしての可能性: `*` を宣言時だけでなく参照時にも使えるようにし、`*手札`（`*` 付きで参照）＝全体、`手札`（無印で参照）＝単一インスタンス、という対称な記法にすれば、二重ラッピングをせずに「宣言した collection をそのまま全体としても参照できる」ようになる。

# もし自分がこの DSL を再設計するなら

以下は後方互換を考慮しない自由提案。

1. **name の名前空間を統一的に設計し直す。** 現状 component 名・alias 名・variant 名・session 名がすべて緩く `name` として扱われ、スコープ規則（ローカル優先か、衝突時どちらが勝つか）が場所ごとに暗黙・不統一（R6, R9）。再設計するなら「component 名前空間はファイル（＋import）全体でグローバル、alias 名前空間は宣言された `single-body` に閉じたローカル」と最初から明言し、両者は別の記号（例えば alias の宣言記号自体を component 定義の `#` と混同しない別の一文字にする）で視覚的にも分離する。

2. **presence gate の「存在」を、変数を持ち込まずに構文的関数として明文化する。** `exists(ref, variant) := ref が variant の実効 body に element-line として現れるか` という一文だけで R3 の曖昧性は消える。「評価しない」という思想を守りながら定義を厳密にできる箇所であり、コストは低い。

3. **collection の宣言と参照を対称にする（R18）。** `*alias` で宣言したら、参照側も `*alias`（全体）／`alias`（単一）の対で書けるようにし、grouping 専用の inline ラッピングを「必須の回避策」ではなく「名前を変えたいときだけの追加オプション」に格下げする。

4. **`back` の対象は常に「素の component 名」に限定し、`##variant` を許す nav-target を back には使わせない。** 「戻った先の variant はスタックが決める」という一貫した原則（295行目）と矛盾する文法上の穴（R7）を、対象文法を絞ることで根本から消す。

5. **shadow 規則の「完全一致」を、字面比較ではなく正規化された比較として最初から定義する。** 自然文である `action` の字面一致に頼る設計は原理的に脆い（R2, R12）。むしろ「行動」に対しても軽量な alias 機構（`行動名: 自由文`）を持たせ、shadow は alias 名の一致で判定する——という設計であれば、空白や表記ゆれに左右されない。ただしこれは原則2（専用記法を増やさない）とのトレードオフになるため、要検討。

6. **フレーム木の「暗黙の遷移」をすべて名前付きの規則として書き下す。** `push`/`goto`/`back` が現在フレームに対して行う操作、子フレーム生成の条件、子フレームが尽きたときの親への復帰（R8）は、いずれも「フレーム木」という1つの内部モデルの状態遷移関数として厳密に書ける性質のもの。表形式（before状態・操作・after状態）で明示すれば、今回見つかったような「書かれていないので推論するしかない」ケースを構造的に無くせる。

7. **重複の禁止をデフォルトにする。** component 名・variant 名の重複禁止（R6）、同名セッションの多重生存の禁止または明示的な優先規則（R5）は、ラフさを損なわずに静的検証できる範囲の規則であり、「ラフは自然文への逃げ道を用意する」という原則1と衝突しない——むしろ参照解決という構造の根幹なので、意図的な曖昧さの対象から外すべきだと考える。
