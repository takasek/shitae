## 1. singleton component（`#!`）

### 発見1（矛盾）: 対応表・「initial variant とエントリポイント」節が singleton の再入場規則と衝突

- 引用（L347、「initial variant とエントリポイント」節）: 「variant 指定なしの遷移（`push(X)` / `goto(X)` / `present(X)` 等、`##variant` を伴わないもの）は、X の**最初に定義された variant**（最初の `## variant`。variant を持たない component ならその単一 variant）で開く。」
- 引用（L299、singleton 節）: 「variant 指定なしで開くと、初回は initial variant、以降は**最後に遷移した variant**で開く（initial に戻らない）。一度受け取れば、以後どこから `present(クーポン)` しても `##受取済` で開く。」
- 引用（L490〜491、verb 対応表 `push(X, @S)` 行）: 「F′ のスタック = [(X, initial)]」。`present(X[, @S])` 行（L491）も同様に「F′ のスタック = [(X, initial)]」。

L345〜349 の一般規則および verb 対応表は、variant 指定なしの遷移が常に initial variant で開くと無条件に述べており、singleton に対する除外注記が無い。しかし singleton 節（L299）は明示的にこれを覆す（2回目以降は initial に戻らない）。「両立可能な特殊ケースの書き漏れ」ではなく、一般規則の文言が singleton にはそのまま当てはまらない実例が明記されているにもかかわらず、一般規則側にその旨のポインタが無い。**矛盾**。

### 発見2（矛盾）: 「戻り系は積まれた時点の variant へ戻る」規則・対応表 `back()` 行が singleton のスナップショット不在と衝突

- 引用（L392、フレーム木節）: 「戻り系はスタックに積まれた時点の variant へ戻る（initial variant にリセットしない）。」
- 引用（L494、対応表 `back()` 行）: 「同じ F。最上段が積まれた時点の (component, variant) に戻る。」
- 引用（L300、singleton 節）: 「singleton の variant は**共有レジストリへの参照**であり、スナップショットをどこにも作らない。フレームスタック・オーバーレイ集合に置かれた singleton は、他所で共有 variant が進めば追随する——「戻り系は積まれた時点の variant へ戻る」…の各規則は singleton には**適用しない**。」

singleton をフレームに積んだ状態から `back()` で戻ってきたとき、対応表・フレーム木節の文言は「積まれた時点の variant」に戻ると述べるが、singleton 節はこの規則が適用されないと明言している（スナップショットが無いので常に最新の共有 variant が見える）。フレーム木節・対応表のどちらにも singleton 例外の注記が無い。**矛盾**。

### 発見3（曖昧）: singleton の「document 内で単一」がモジュール分割時にどう振る舞うか明記が無い

- 引用（L90）: 「`#!` 名前 | singleton component 定義（**document 内**で単一インスタンス。variant 状態を全所在で共有する。…）」
- 引用（L287）: 「定義ヘッダを `#!` にすると、その component は**document 内**で単一インスタンスになる。」

「document」という語は文法定義（L129）上は 1 ファイルを指す。document common には「モジュール分割時、実行時に有効な document common は…」という専用の節（L79）があり、複数ファイルに分割されたときの挙動が明記されているのに対し、singleton には同種の説明が無い。複数ファイルから `モジュール::コンポーネント` で参照される singleton の共有範囲（定義ファイル単位で一意、なのか、参照側document ごとに別レジストリになりうるのか）が読み手に委ねられている。実体としては定義がひとつしかない以上おそらく矛盾は生じないと推測できるが、document common で丁寧に扱われている論点が singleton では素通りされており、非対称。**曖昧**。

### 発見4（軽微）: 「フレーム木の規則も不変」と直前の適用除外の並置がわかりにくい

- 引用（L300〜302）: 「…「戻り系は積まれた時点の variant へ戻る」「新規作成・`show` は initial variant で開く」の各規則は singleton には**適用しない**。…参照側の記法は無変更…。**フレーム木の規則も不変**（singleton もフレームに積まれる。共有されるのは variant だけ）。」

「フレーム木の規則」（構造操作＝push/pop等）と「variant 選択規則」（initial に開く／積まれた時点に戻る）は別物だが、この2文が隣接しているため「規則は適用しない」と「規則も不変」が同じ「規則」を指しているように誤読されやすい。指す範囲を明示すれば解消する程度の**軽微**な曖昧さ。

### 確認済み・問題なし
- オーバーレイ節の singleton 例外（L520「X が singleton（`#!`）の場合…initial への上書き規則は適用しない」）は明示的に書かれており、オーバーレイの initial 上書き規則（L519）と整合している。
- presence gate（構造的 presence 判定）と singleton の組み合わせに矛盾は見当たらない。「対象インスタンスの現在 variant」という判定基準は singleton でも共有 variant を指すだけで破綻しない。
- 「変わ扱わないもの」節（L673〜681）と singleton の variant 共有は、variant を状態表現とする設計原則（L18）の範囲内であり矛盾しない。

## 2. document common の 3 階層 shadow とモジュール分割時の有効範囲

### 発見1（曖昧）: 「どの画面でも」という用途説明とモジュール分割後のスコープ限定が食い違って見える

- 引用（L58）: 「用途は「どの画面でも起こるインタラクション」——deep link、プッシュ通知、セッション切れによる強制ログアウトなど。」
- 引用（L79）: 「モジュール分割時、実行時に有効な document common は**アクティブフレームの最上段 component が定義されているファイル**のもの。import 先の画面を表示中は、その import 先ファイルの document common が効く（「そのファイルの全 component に共通」の字義どおり）。」

単一ファイルの間は L58 の「どの画面でも」が文字通り成立するが、モジュール分割後は「今アクティブな画面が属しているファイルの document common だけ」が有効になり、エントリファイルに書いた「セッション切れで強制ログアウト」等が、ユーザーが import 先ファイルの画面に居るときには発火しなくなる。これは L79 で意図的に定義された挙動だと読めるが、L58 の「どの画面でも」という導入の説明にはこの限定が言及されておらず、後から読む L79 で初めて挙動が変わることに気づく構成になっている。実装上の矛盾ではないが、用途説明と実際のスコープ規則の間に読者を混乱させる**曖昧**さがある。

### 確認済み・問題なし
- E022 の本文根拠（L77〜78「裸の `##variant` は…書けない（禁止。E022）」）は診断コード表の E022（L717）と一致する。
- document common からの前方参照可能性（L77）は「component に特権はない」節（L567）の一般規則と整合している。
- shadow 規則の 3 階層拡張（L81「variant 固有 > component common > document 共通」）は、2 階層の shadow 規則（L275〜277）の一般原理をそのまま拡張したものであり矛盾しない。
- 掲示中 overlay の interaction 有効性は document common のスコープと無関係、という注記（L79 末尾）はオーバーレイ節の「実効 body（共通＋固有）」の定義（L522）と整合しており、document common を含まない扱いで一貫している。

## 3. presence gate の構造的判定（host/member/判定不能 always-on）と document common の交差

### 発見1（曖昧）: 裸 `##variant` の動的解決と presence gate 裸参照の静的 always-on 化が非対称

- 引用（L341）: 「裸 `##variant` の「同一 component」は**実行時にアクティブな component**（アクティブフレームの最上段）を指す——書かれた場所（字句上のホスト）ではない。document common から継承した interaction の `goto(##v)` は、発火時にアクティブな画面の variant を切り替える。」
- 引用（L248）: 「対象が未定義 component など判定不能なときは**always-on**（ラフさ優先。lint はヒントを出してよいが、エラーにはしない）。host component が存在しない **document common の裸参照**も同じく判定不能として always-on。」

同じ「document common に書かれ、発火時までホストが定まらない」という状況に対して、`goto(##v)` の対象解決は「実行時にアクティブなフレームの最上段」へ動的に解決するのに対し、presence gate の裸参照は「host が無いので判定不能→ always-on」と静的に諦める設計になっている。両者とも「document common にはホストとなる component が字句上存在しない」という同じ前提から出発しながら、一方は実行時のアクティブフレームで解決し、他方はそれをせず常時 true にする、という選択の違いが理由づけされずに並記されている。設計判断として妥当ではあり得るが、対称性を期待する読者には矛盾に見えかねない。**曖昧**。

### 確認済み・問題なし
- member 参照の presence gate（L246「対象インスタンスの現在 variant…host 側の variant ではなく、参照先そのものの variant で判定する」）は host の有無に依存しない判定なので、document common に書かれても原理上そのまま機能し、矛盾は無い。
- gate とオーバーレイ掲示状態が別軸である旨（L273、L526）は一貫して重複説明されており、矛盾はない。

## 4. E022〜E026・W104・W105 の診断コード表と本文規定の対応

### 発見1（曖昧）: E024 の参照先「オーバーレイ」節に対応する本文記述が無い

- 引用（L719、診断コード表）: 「E024 | overlay verb の引数に `*` を書いた（`show(*X)` 等。掲示対象は component 1 つ。**「オーバーレイ」参照**） | error」
- オーバーレイ節本文（L511〜527）を通読したが、「show/hide に `*`（collection 全体参照）を書けない」という主旨の文は存在しない。根拠は EBNF の `show-nav` / `hide-nav` 生産規則（L198〜199）に `*` トークンが含まれていないことのみで、これは文法ブロックのコメントにも明示されていない。表の参照先セクションに対応する説明文が無いため、読者が「オーバーレイ」節を読んでも E024 の理由に辿りつけない。**曖昧**（cross-reference の破れ）。

### 発見2（曖昧）: W104 の参照先「未定・分岐」節に対応する本文記述が無い

- 引用（L722、診断コード表）: 「W104 | 要素名が condition label 風の `[...]` で始まる（条件付き要素の意図なら variant で分けるか自然文で注記。**「未定・分岐」参照**） | warning」
- 「未定・分岐」節（L627〜670）は condition label `[...]` の結果列内での意味論（ラベルが以降の result 群に掛かる規則、矢印は1つだけ等）のみを扱っており、**要素行**の名前が `[...]` で始まる場合について言及する文は無い。W104 が警告する状況（要素行を `[条件]要素名` のように書いてしまう typo 的ケース）は、参照先の節では扱われていない。**曖昧**（cross-reference の破れ）。

### 発見3（軽微）: E025 の参照先には一般原則のみで要素行での `?` の具体例が無い

- 引用（L720、診断コード表）: 「E025 | 要素行の参照に `?` を後置した（presence gate は行動対象専用。**「操作は variant に属する」参照**） | error」
- 参照先（L249）は「`?` が置けるのは**行動対象のみ**。nav-target（遷移先）への後置（例 `push(次?)`）は**構文エラー**」とあり、nav-target への `?`（＝ E013、L708 と対応）には具体例があるが、要素行への `?`（＝ E025）には対応する具体例が無い。一般原則からは導けるため矛盾ではないが、E013 との書きぶりの非対称は改善余地がある。**軽微**。

### 確認済み・問題なし
- E022（L717）は本文（L77〜78）と一致。
- E023（L718）は本文（L343「document common に裸 `##variant` を書くのも従来どおり禁止で、E022 として検出される」も含め）と一致。
- E026（L721）は本文（L548「空の括弧（`行動()`）は構文エラー（E026）——対象なしなら括弧ごと省略する」）と完全に一致。

## 5. 「verb ごとのフレーム木の変化」対応表と各節の散文規則の一致

### 発見1（矛盾・topic1 の再掲）: 対応表は「新しい規則は含まない」と宣言するが singleton の特例を反映していない

- 引用（L485）: 「全 transition verb について、フレーム木がどう変わるかを 1 枚にまとめる。…新しい規則は含まない。」
- 対応表の `push(X, @S)` 行・`present(X[, @S])` 行（L490〜491、「F′ のスタック = [(X, initial)]」）、`back()` 行（L494、「積まれた時点の (component, variant) に戻る」）は、singleton component が絡む場合には singleton 節（L299、L300）の規則によって成立しない。対応表がカバーする範囲は暗黙に「非 singleton」を前提としており、その前提が明記されていない。1章の発見1・発見2と同一事象。**矛盾**。

### 確認済み・問題なし
- switch・goto・back の begin マーカー／barrier の扱いは、対応表各行（L487〜498）と「フレーム木」節（L382〜395）・「switch（中断と復帰）」節（L397〜436）・「戻り先が無いとき」節（L500〜503）の散文規則を突き合わせた結果、すべて 1:1 で整合している（`goto` の begin マーカー保存、`back()`/`back(X)` の barrier 停止と no-barrier 越境時の begin マーカーごとの破棄、`switch` の兄弟規則・barrier あり・resume-or-create、`exit`/`dismiss` のアクティブパス優先＋遠隔破棄、`dismiss()` の named 素通り＋道連れ、いずれも本文と対応表で矛盾なし）。
