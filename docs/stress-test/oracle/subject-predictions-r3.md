# shitae 意味論予測課題 — r3 回答

参照したのは `docs/SPEC.md` のみ。他ファイルは未参照。

## 前提の確認

- エントリポイントは `ホーム`。各シナリオ（S1〜S8）は互いに独立した実行列として扱う（同一実行内で状態が持ち越されるとは指示されていないため、各 S の冒頭で `ホーム` の root フレームが `(ホーム, ##一 または単一 variant)` として存在し、`クーポン` singleton は未初期化＝まだどの variant にも遷移していない状態から始まると仮定）。この仮定が誤りなら S2 以降の「singleton 初回オープン」の判断が変わりうる。
- `クーポン` は `#!`（singleton）、variant は `## 未受取`（initial）／`## 受取済`。
- `記事` は通常 component、`## 通常`（initial）／`## 展開`。
- 他の component（`設定` 等）は通常・単一 variant。

---

## S1: `present(クーポン)` → `goto(##受取済)` → `dismiss()` → `present(クーポン)`

**(a) アクティブ画面**: `クーポン##受取済`

**(b) フレーム木の形**: `root(ホーム)` の子として新しい無 barrier ではなく **barrier あり・無名セッション** の子フレーム F′ が生成され、F′ = `[クーポン##受取済]` がアクティブ。1 回目の present で作られた F（`present(クーポン,@S=無名)`）は `dismiss()` で破棄済みで木に残らない。

**(c) 警告**: なし（`dismiss()` は `present(クーポン)` が開いた無名セッションと過不足なく対応しており mismatch ではない）。

**根拠**:
- 「present / dismiss は compound verb」節: `present(X)` は無名セッション開始＋barrier。`dismiss()` は「直近の無名セッションを破棄」。
- 「singleton component（`#!`）」節: 「variant 指定なしで開くと、初回は initial variant、以降は最後に遷移した variant で開く（initial に戻らない）」「singleton の variant は共有レジストリへの参照であり、スナップショットをどこにも作らない」「戻り系は積まれた時点の variant へ戻る…の各規則は singleton には適用しない」。
  → `goto(##受取済)` で共有レジストリが書き換わり、`dismiss()` でフレームが破棄されても共有レジストリ自体は無傷。2 回目の `present(クーポン)` は「初回ではない」ので最後に遷移した variant＝`受取済` で開く。

**確信度**: 高。singleton 節が直接この挙動を明言している。

## S2: `present(ホーム, @A)` → `switch(クーポン, @B)` → `goto(##受取済)` → `switch(ホーム, @A)` → `switch(クーポン##未受取, @B)`

**(a) アクティブ画面**: `クーポン##受取済`

最後の `switch(クーポン##未受取, @B)` は @B が生存中なので **resume**（新規作成ではない）。「このとき X は無視される」ため、指定した `##未受取` は適用されない。resume 先は F_B の中断位置＝`(クーポン, 受取済)`（singleton は snapshot を持たないので中断中も共有レジストリの現在値をそのまま指す）。

**(b) フレーム木の形**:
- `root(ホーム)`
  - F_A = `present(ホーム,@A)` が作った子フレーム（barrier あり, begin=@A）, スタック = `[ホーム(initial)]`
    - F_B = `switch(クーポン,@B)` が新規作成した子フレーム（barrier あり, begin=@B）, スタック = `[クーポン(受取済,共有参照)]`

  兄弟規則（「switch（中断と復帰）」節）: `switch(クーポン,@B)` を呼んだ時点のアクティブフレームは F_A（`present` 製で `switch` 製ではない）。F_A の祖先方向にも switch 製フレームが無いので、新規フレーム F_B は「現在フレームの子」＝ F_A の子になる。
  最終的にアクティブなのは F_B（`switch(ホーム,@A)` で一旦 F_A に戻ったが、最後の `switch(クーポン##未受取,@B)` で再度 F_B に復帰しているため）。

**(c) 警告**: 「ツールは定義と異なる X を警告してよい」（switch（中断と復帰）節）に該当しうる——指定した `クーポン##未受取` と実際に resume した variant（`受取済`）が食い違うため、処理系は任意で警告を出してよい。ただし SPEC はこれを MUST ではなく MAY としているため、**警告が実際に出るかどうかは決められない**（実装依存）。状態遷移そのもの（(a)(b)）は一意に決まる。

**根拠**: 「switch（中断と復帰）」節（resume-or-create、X 無視の規定、兄弟規則）、「singleton component」節（中断中も共有参照）。

**確信度**: 中〜高。状態遷移の帰結は高確信度。警告の有無は SPEC が明示的に「してよい」と任意化しているため中確信度＝未規定として扱う。

## S3: `push(クーポン)` → `push(設定)` → `push(クーポン##受取済)` → `back()` → `back()`

**(a) アクティブ画面**: `クーポン##受取済`

**(b) フレーム木の形**: セッション引数を伴う push が一度も無いので新しいフレームは作られず、**単一フレーム**のスタック操作のみ。
経過: `[ホーム]` → `[ホーム, クーポン(未受取)]` → `[ホーム, クーポン(未受取), 設定]` → `[ホーム, クーポン(受取済,※), 設定, クーポン(受取済)]`（※ `push(クーポン##受取済)` の明示 variant 書き込みは共有レジストリへの即時反映のため、下段の既存 `クーポン` エントリも同時に `受取済` に見える）→ `back()` で最上段の `クーポン(受取済)` を降ろし `[ホーム, クーポン(受取済), 設定]` → `back()` で `設定` を降ろし `[ホーム, クーポン(受取済)]`。

**(c) 警告**: なし。

**根拠**: 「push / goto と行き先」「singleton component」（`X##v` 指定は共有状態の即時書き換え、かつ「戻り系は積まれた時点の variant に戻る…の各規則は singleton には適用しない」＝ back で見えるのは常に現在の共有値）。

**確信度**: 高。

## S4: `show(クーポン)` → `push(クーポン##受取済)` → `show(クーポン)`。最後に overlay に表示されている クーポン の variant は？

**特定の問いへの回答**: `##受取済`

**(a) アクティブ画面**: `クーポン##受取済`（`push(クーポン##受取済)` がセッション無しで root フレームのスタックに積まれ、そのまま最上段に残るため）

**(b) フレーム木の形**: 単一フレーム。スタック = `[ホーム, クーポン(受取済)]`。overlay 集合は別軸で `{クーポン}` のエントリを 1 つ持つ。

**(c) 警告**: なし。

**根拠**:
- 「オーバーレイ」節: `show(X)`（variant 省略）は本来 X の initial variant で掲示、再 show は上書き——ただし「X が singleton（`#!`）の場合…initial への上書き規則は適用しない（共有 variant の現在値が常に見える）」。
- したがって 1 回目の `show(クーポン)` はまだ何も書き換えていない共有初期状態（未受取）を指すが、これは snapshot ではなく参照。`push(クーポン##受取済)` が共有レジストリを `受取済` に書き換えると、overlay のエントリも自動的に `受取済` を指すようになる（再 show を待たずとも）。2 回目の `show(クーポン)`（再 show・variant 省略）も singleton には initial 上書きが適用されないため、依然として共有値＝`受取済` を指したまま。

**確信度**: 高。singleton オーバーレイの規定が直接該当。

## S5: モジュール分割 — `push(クーポン##通常)`（A ローカル参照）→ `push(B::クーポン)`

**特定の問いへの回答**: `B::クーポン` は `##未受取`（initial variant）で開く。

**(a) アクティブ画面**: `B::クーポン##未受取`

**(b) フレーム木の形**: 単一フレーム（どちらの push もセッション引数なし）。スタック = `[エントリA, A::クーポン(通常), B::クーポン(未受取)]`。

**(c) 警告**: なし。

**根拠**:
- 「モジュール化（名前空間）」節: ファイル＝モジュール＝名前空間。`モジュール::component` で明示的に別名前空間の component を参照する。
- A の `# クーポン`（非 singleton・通常）と B の `#! クーポン`（singleton）は名前が同じでも**別の component**（別ファイル＝別 document、`::` で完全に区別される）——「singleton component」節の共有スコープは「document 内」（`docs`＝ファイル単位、"document common" 節の用法と整合）であり、A と B の間に状態共有は生じない。
- B::クーポン はこの遷移列内で初参照＝singleton の「初回」に当たるため、「initial variant とエントリポイント」節の一般規則（variant 指定なしは最初に定義された variant）通り `##未受取` で開く。

**確信度**: 高。ただし「singleton の共有スコープ＝ファイル単位」という点は SPEC 中に「document 内」という表現はあるが「document ＝ 1 ファイル」の対応が document-common 節からの類推であり、singleton 節自体には「ファイルを跨ぐとどうなるか」の明示例が無い。この一点のみ中確信度寄りだが、`::` で名前空間が完全に分離される原則（「component に特権はない」節「参照は定義順と無関係」等、名前の対等性・namespace の独立性）から見て、A と B の同名 `クーポン` が状態を共有する根拠は無く、答えは一意に定まると判断する。

## S6: `push(##二)`（エントリ `ホーム` は `## 一`（initial）と `## 二`）→ `back()`。

**特定の問いへの回答**:

`push(##二)` は「フレーム新規作成系」ではない（セッション引数 `@S` が無い）ため E023 の禁止対象外。裸 `##variant` は「実行時にアクティブな component」＝現在の最上段 component を指すので、これは **同一フレームのスタックに `(ホーム, ##二)` を新たに積む**操作になる（component は変わらず variant だけを持つ新しいスタック段が増える）。

**(a) アクティブ画面（push 直後）**: `ホーム##二`。**`back()` 後**: `ホーム##一`（積まれる前の段に戻る）。

**(b) フレーム木の形**: 単一フレーム。スタック: `[ホーム(一)]` → push 後 `[ホーム(一), ホーム(二)]` → back 後 `[ホーム(一)]`。

**(c) 警告**: なし。

**根拠**: 「行き先は component / component##variant / モジュール::component / ##variant（同一 component 内の variant）」（push-nav にも nav-target が使われる文法）、E023 は `push(##v, @S)` 等**フレーム新規作成系**のみを禁止（「フレーム新規作成」＝ push with セッション、または present/switch）。`push(##二)`（セッション無し）は「push(X)（セッションなし）はフレームを作らず現在フレームに積む」規則がそのまま適用される。

**確信度**: 中。文法上・意味論上はここまで導けるが、「同一 component を variant 違いで多重にスタックへ積む」という具体例は SPEC 本文に明示された用例が無く、書き手が意図する用法かどうかまでは分からない（構文的に妥当という以上のことは言えない）。

## S7: `present(クーポン, @m)` → `goto(##受取済)` → `exit(@m)` → `present(クーポン)`

**(a) アクティブ画面**: `クーポン##受取済`

**(b) フレーム木の形**: `root(ホーム)` の子として新しい無名セッションの子フレーム F′ = `[クーポン##受取済]`（barrier あり）がアクティブ。`present(…,@m)` が作った F は `exit(@m)` で（子孫ごと。ここでは子孫なし）破棄済みで木に残らない。

**(c) 警告**: なし（`exit(@m)` は `present(…, @m)` の begin と一致しており mismatch ではない）。

**根拠**: S1 と同型。「present / dismiss は compound verb」「フレーム木」節（`exit(@S)` は @S と子孫を破棄し begin 地点＝親フレームへ戻る）、singleton 節（共有レジストリはフレーム破棄と無関係に値を保持）。

**確信度**: 高。

## S8: `push(記事##展開)` → `push(設定)` → `back()`

**(a) アクティブ画面**: `記事##展開`

**(b) フレーム木の形**: 単一フレーム。スタック: `[ホーム]` → `[ホーム, 記事(展開)]` → `[ホーム, 記事(展開), 設定]` → `back()` で `設定` を降ろし `[ホーム, 記事(展開)]`。`記事` は非 singleton なので積まれた時点の variant（展開）がそのまま保持される。

**(c) 警告**: なし。

**根拠**: 「フレーム木」節（「戻り系はスタックに積まれた時点の variant へ戻る」）、「push / goto と行き先」節。

**確信度**: 高。
