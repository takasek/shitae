# SPEC 読解による遷移予測（被験者ロール）

前提: 読んだのは `docs/SPEC.md` のみ。エントリポイントは `ホーム`。各遷移列はホームから開始し、書かれた順に発生するとする。

---

## Q1: `push(A)` → `present(B)` → `back()`

### (a) 最終画面とスタック/フレーム木

最終的にユーザーに見えているのは **B**（`present(B)` で開いた variant のまま、`back()` は no-op で画面は変わらない）。

フレーム木:
- ルートフレーム（無名、barrier なし）: スタック `[ホーム, A]`
- その子フレーム（`present(B)` が作った無名セッションのフレーム、barrier あり）: スタック `[B]`、アクティブ

### (b) 根拠

- `push(A)` はセッションを伴わないため新しいフレームを作らず、現在フレーム（ルート）のスタックに積む（「フレーム木」節: 「`push(X)`（セッションなし）はフレームを作らず現在フレームに積む」）。
- `present(B)` は無名セッション＋ back barrier を立てる compound verb で、現在フレームの**子フレーム**を作ってアクティブにする（「フレーム木」節、「present / dismiss は compound verb」節）。この子フレームのスタックは `[B]` のみ。
- `back()` はアクティブなフレーム（子フレーム）のスタックを操作する。子フレームのスタックには `B` の 1 段しかなく、その下は back barrier に阻まれてルートフレームへ漏れない。「戻り先が無いとき」節が挙げる no-op の条件の一つが「back barrier に当たる」であり、これに該当するため `back()` は no-op。
- この `present` → `back` の組み合わせは「セッションの mismatch」節が名指しする典型例そのもの（「`present` したものを `back` で戻る」）。同節は「エラーにしない」「処理系は実行時に警告してよい」としているため、警告が出る可能性が高い。

### (c) 確信度: 高

barrier の no-op、mismatch 警告候補としての言及がどちらも SPEC 本文に明示されている。

### (d) 決められない点

「警告してよい」は must ではなく may の書き方（「ツールは警告してよい」）なので、実際に警告するかどうかは処理系実装依存で、SPEC の字義だけでは確定できない。ここでは「警告しそうか」を「mismatch 検出の対象として名指しされている＝警告する可能性が高い実装」という蓋然性で答えている。

## Q2: `present(A)` → `present(B, @named)` → `dismiss()`

### (a) 最終画面とスタック/フレーム木

最終的にユーザーに見えているのは **ホーム**（`present(A)` が作った無名セッションのフレームが `dismiss()` で破棄され、その子孫である `@named` のフレームも道連れで破棄されるため、begin 地点まで一気に戻る）。

フレーム木: ルートフレーム（無名、barrier なし）のみが残る。スタック `[ホーム]`。`present(A)` のフレームと `present(B, @named)` のフレームはどちらも破棄済み。

### (b) 根拠

- `present(A)`: 無名セッション＋ barrier を立てて子フレーム C1（スタック `[A]`）を作成。begin 地点はルートフレームの `ホーム` の位置。
- `present(B, @named)`: 現在アクティブな C1 のさらに子フレーム C2（スタック `[B]`、セッション名 `@named`）を作成。begin 地点は C1 内の `A` の位置。
- `dismiss()`（無名）は「直近に開いた無名セッションを破棄」する。走査は「アクティブパス（現在フレームから祖先方向）のみ」（「フレーム木」節）。アクティブパスは C2（現在）→ C1 → ルート。C2 のセッションは無名ではなく `@named` なので対象にならず、次に見つかる無名セッションは C1。したがって C1 が破棄対象になる。
- `exit(@S)` / `dismiss(@S)` は「@S とその子孫フレームを全部破棄」する（「フレーム木」節）。C1 を破棄する操作も同じ「フレーム破棄＝子孫ごと」という一般原理に従うと読むのが自然で、その場合 C1 の子である C2（`@named`）も一緒に破棄される。これはログアウトでタブ全滅する例（`exit(@tabHome)` が子孫のタブを道連れにする）と同型の挙動。
- C1 が破棄されると begin 地点、すなわちルートフレームの `ホーム` へ戻る。

### (c) 確信度: 中

`dismiss()`（無名）が複数フレームにまたがって走査すること自体は「アクティブパスのみ」という記述から読み取れるが、「無名セッションを破棄」した際に、その内側にネストした**名前付き**セッションまで道連れにするかどうかを直接述べた文はない。「子孫ごと破棄」の明文は `exit(@S)`/`dismiss(@S)` の段落にあり、無名 `dismiss()` の段落には繰り返されていない。類推で埋めた。

### (d) SPEC の字義だけでは決められない点

上記の通り、「無名の `dismiss()` が対象フレームの子孫（名前付きセッションを含む）も道連れに破棄するか」は明文がなく、フレーム破棄の一般原理（子孫ごと）からの類推で埋めた。もし異なる設計（＝内側の名前付きセッションは温存され `dismiss()` が素通りする、あるいは `dismiss()` が C2 自体を破棄してしまう等）だとすれば結論が変わる。また、この「名前付きセッションを暗黙に巻き込む」動作が「セッションの mismatch」に該当し警告対象になるのかも SPEC は明言していない（mismatch の例示は `push`/`dismiss` や `present`/`back` の取り違えのみで、本ケースのような「上位の無名 present を正しく `dismiss` したら下位の名前付き present も道連れになった」は例示にない）。ここでは道連れ破棄は正規の挙動（タブ全滅の例と同型）と判断し、警告は出ない可能性が高いと予測したが、確信度は低い。

## Q3: `push(A, @S)` → `goto(B)` → `exit(@S)`

### (a) 最終画面とスタック/フレーム木

最終的にユーザーに見えているのは **ホーム**（`exit(@S)` が `@S` のフレームを子孫ごと破棄し、begin 地点まで戻るため）。

フレーム木: ルートフレームのみ。スタック `[ホーム]`。`push(A, @S)` が作ったフレーム（一時的にスタックが `[B]` になっていたもの）は破棄済み。

### (b) 根拠

- `push(X, @S)` はセッション付きなので、`present` と同様に現在フレームの**子フレーム**を作る（「フレーム木」節：「`push(X, @S)` / `present(X, @S)` / `present(X)`（無名）は現在フレームの子フレームを作ってアクティブにする」）。ただし barrier は立たない（barrier を立てるのは `present`/`switch` のみ、「フレーム木」節の直後の文）。子フレーム C1、セッション `@S`、スタック `[A]`。begin 地点はルートの `ホーム` の位置。
- `goto(B)` は「現在フレームの最上段を置き換える」ので、C1 のスタックが `[A]` から `[B]` に置き換わる。C1 自体やセッションには影響しない。
- `exit(@S)` は「@S とその子孫フレームを全部破棄し、begin 地点へ戻る」。C1（子孫なし）が破棄され、begin 地点＝ルートの `ホーム` へ戻る。
- `push`（セッション開始）→ `exit`（同セッション破棄）は仕様が示す正規の対応（`push(確認, @checkout)` → `exit(@checkout)` の例と同型）なので mismatch には該当しない。

### (d) 決められない点・注意

`goto(B)` で一時的に B へ画面が置き換わるが、その直後に `exit(@S)` でフレームごと破棄されるため、B はユーザーに一瞬も安定して見えない（同一ターン内の連続遷移として扱っている）。SPEC は「見える」の粒度（アニメーション途中の一瞬を『見えた』とみなすか）を定義していないため、「最終的に見えている画面」を問われている本タスクでは B は答えに含めなかった。これは字義からの外挿というより設問の解釈（「最終的に見えている」の定義）の問題。

### (c) 確信度: 高

## Q4: `push(A)` → `present(B)` → `push(C)` → `back(ホーム)`

### (a) 最終画面とスタック/フレーム木

最終的にユーザーに見えているのは **C**（`back(ホーム)` は no-op で画面は変わらない、と予測）。

フレーム木:
- ルートフレーム: スタック `[ホーム, A]`
- 子フレーム（`present(B)` が作った無名セッション、barrier あり）: スタック `[B, C]`、アクティブ

### (b) 根拠

- `push(A)`: セッションなしなのでルートフレームのスタックに積む（`[ホーム, A]`）。
- `present(B)`: 無名セッション＋ barrier で子フレーム C1（スタック `[B]`）を作成、アクティブに。begin 地点はルートの `A` の位置。
- `push(C)`: セッションを伴わない `push` はフレームを作らず**現在フレーム**（C1）のスタックに積む。C1 のスタックは `[B, C]` になる。
- `back(ホーム)`: `back(X)` は「component X まで戻る」。走査はアクティブパス（現在フレームから祖先方向）のみで、「中断中の兄弟フレームは見ない」という記述から、逆に言えば祖先方向へは複数フレームをまたいで走査しうると読める。しかし `present` が立てた barrier は「モード内から外へ通常の `back` で出られない」性質であり、「戻り先が無いとき」節は no-op の理由の一つとして明示的に「back barrier に当たる」を挙げている。`ホーム` は C1 のスタックには存在せず、barrier の外（ルートフレーム）にしかないため、`back(ホーム)` は barrier に阻まれて no-op になると予測した。

### (c) 確信度: 中

barrier が `back()`（引数なし）を止めることは明示例（`switch` の「フレームの底で `back()` しても元のフレームへは漏れない」）があるが、**引数付き `back(X)`** が同様に barrier で止まることを直接述べた例文は無い。「戻り先が無いとき」節の並び（`back()` / `back(X)` / `exit(@S)` / `dismiss()` をまとめて挙げ、その no-op 理由の一つとして「back barrier に当たる」を列挙）から、`back(X)` にも同じ制約が及ぶと読むのが自然だと判断したが、字義上「通常の back」が無引数の `back()` だけを指す可能性も排除できない。

### (d) SPEC の字義だけでは決められない点

`back(X)` が barrier を越えて祖先フレームのスタックまで探索対象にするのか（探索はするが越境はできない、という私の解釈）、それとも barrier のある子フレームの中でしか `X` を探さない（そもそも越境探索という概念自体が無く「現在フレームのスタックのみ操作する」という一文を字義通り取るなら、`back(X)` は最初から C1 のスタックしか見ない）のか、SPEC はどちらとも取れる書き方をしている。いずれの読みでも結論（no-op で画面は C のまま）は変わらないが、「barrier に当たったからか」「そもそも探索範囲外だったからか」という**理由の区別**は SPEC の字義だけでは決め切れない。また、no-op 時に警告が出るかどうかも Q1 同様「してよい」であり確定しない。

## Q5: `push(A)` → `goto(##開いた)` → `back()` → `push(A)`（A は `## 閉じた` → `## 開いた` の順で定義）

### (a) 最終画面とスタック/フレーム木

最終的にユーザーに見えているのは **A（`閉じた` variant）**。

フレーム木: ルートフレームのみ。スタック `[ホーム, A(閉じた)]`。

### (b) 根拠

- `push(A)`（1 回目）: variant 指定なしの遷移は「X の最初に定義された variant」で開く（「initial variant とエントリポイント」節）。A の最初の variant は `閉じた`。セッションなしなのでルートフレームのスタックに積む: `[ホーム, A(閉じた)]`。
- `goto(##開いた)`: 「`goto(##variant)` は現在フレームの最上段の variant を書き換える」（「フレーム木」節）。スタック最上段の `A(閉じた)` が `A(開いた)` に書き換わる: `[ホーム, A(開いた)]`。
- `back()`: 現在フレーム（ルート、barrier なし）のスタックを 1 段降ろす。最上段の `A(開いた)` を降ろして `ホーム` が最上段に。この時点でスタックからは `A(開いた)` という情報自体が失われる（保持される仕組みの記述はない — 「戻り系はスタックに積まれた時点の variant へ戻る」はスタックに**残っている**エントリに戻るときの規則であり、一度降ろされ捨てられたエントリの記憶を指す規則ではない）。
- `push(A)`（2 回目）: 新規の push であり、variant 指定なし。1 回目と同じく initial variant 規則が適用され、`閉じた` で開く。1 回目に `開いた` へ variant change したという履歴は、A がスタックから降ろされた時点で消えており、2 回目の push には引き継がれない、と読むのが自然。

### (c) 確信度: 高

initial variant のルールと、`goto(##variant)` がスタック最上段を書き換えるだけであることは明文があり、「一度降ろされたスタックエントリの variant 状態がどこかに保持されて次の push に引き継がれる」という仕組みへの言及は SPEC のどこにもない（むしろ「データ／コンテキスト...履歴スタックのデータ構造、戻り先の自動解決」を「扱わないもの」に挙げており、こうした暗黙の記憶機構を持たせない方針と整合する）。

### (d) 決められない点

「variant はインスタンスごとに独立」節は**同時に複数箇所に置かれた同一 component**の話であり、本問のような**同じスタック位置に時間差で 2 回 push した場合**に直接該当する記述ではない。ここでは類推で「2 回目の push は 1 回目とは別インスタンス相当であり、variant の記憶は引き継がれない」と判断したが、これは SPEC の別節からの外挿であり、字義そのものが直接答えているわけではない。
