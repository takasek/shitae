## Q1: present(ホーム, @tabHome) → push(記事, @reading) → switch(検索, @tabSearch) → exit(@reading)

**(1) 最終アクティブ画面**: `ホーム`（tabHome フレームの initial variant）

**(2) フレーム木**

トレース:
- `present(ホーム,@tabHome)`: R0 の子 F1 を新規作成（barrier あり、begin=@tabHome）。F1=[(ホーム,initial)]。active=F1。
- `push(記事,@reading)`: F1 の子 F2 を新規作成（barrier なし、begin=@reading）。F2=[(記事,initial)]。active=F2。
- `switch(検索,@tabSearch)`: @tabSearch 未作成 → 新規作成。**兄弟規則**：現在フレーム F2 は switch 製ではない（push 製）ため、新規フレームは F2 の**子**になる。F3 を F2 の子として作成（barrier あり、begin=@tabSearch）。F3=[(検索,initial)]。active=F3。
- `exit(@reading)`: アクティブパス（F3→F2→F1→R0）を現在フレームから遡って走査。F2 の begin が `@reading` で一致。F2 と**その子孫（F3 を含む）**を破棄。active は F2 の親 F1 に戻る（begin 地点 = F1 のスタックトップ、変化なし）。

最終木:
```
R0 = [(ホーム, initial)]
└─ F1 (present製, barrier=あり, begin=@tabHome) = [(ホーム, initial)]  ← active
```
F2（記事, @reading）と F3（検索, @tabSearch）はどちらも破棄済み。

**(3) 警告**: SPEC の診断コード表に該当するものなし（`exit` はアクティブパス上に @reading を発見できており、mismatch でも見つからないケースでもない）。ただし「switch で作った検索タブが、無関係に見える `exit(@reading)` の巻き添えで消える」という帰結は診断コードでは拾われない——設計上のトラップだが仕様は警告を義務付けていない。

**(4) 確信度**: 中。個々の規則（兄弟規則・アクティブパス走査・子孫ごと破棄）はそれぞれ明記されているが、「push 製フレームの内側から switch する」という組み合わせを扱う worked example は SPEC 中に無い。根拠：「switch（中断と復帰）」節の兄弟規則、「フレーム木」節の `exit(@S)` 規則（子孫ごと破棄）。

**(5) 決められない点**: なし（機械的には一意に決まる）。ただし「検索タブが記事セッションの子になる」こと自体が意図された設計か、見落とされた corner case かは SPEC の文面からは判断できない（規則の適用結果としては一意）。

## Q2: push(A, @S) → push(B) → back(ホーム) → exit(@S)

**(1) 最終アクティブ画面**: `ホーム`（initial variant）— 下記 2 通りの解釈のどちらでも一致する。

**(2) フレーム木 / (3) 警告**: ここは SPEC の文言に**内的緊張**があり、2 通りの読みが両立してしまう。

- `push(A,@S)`: R0 の子 F1 を新規作成（barrier なし、begin=@S）。F1=[(A,initial)]。active=F1。
- `push(B)`（セッションなし）: 現在フレーム F1 に積む。F1=[(A,initial),(B,initial)]。active=F1。

ここから `back(ホーム)` の挙動が分岐する。

**解釈 A（back(X) はフレーム境界を越える）**: 「戻り先が無いとき」節の「木のどこにも積まれていない component を `back(X)` の対象に指定した場合...no-op」という文言は、`back(X)` が現在フレームだけでなく、`back()` の単段跳躍規則（barrier なしフレームの最下段では子フレームを begin マーカーごと破棄して親へ抜ける）を一般化して複数フレームをホップしうることを示唆する。F1 のスタックに `ホーム` は無い→ F1 に barrier が無いので F1 を（begin マーカー `@S` ごと）破棄して親 R0 へ抜ける→ R0 のスタックトップは既に `(ホーム,initial)` → 発見、停止。
結果: F1 と `@S` はここで**既に破棄**される。木は R0=[(ホーム,initial)] のみ。続く `exit(@S)` はアクティブパス（R0 のみ）にも木全体（remote）にも `@S` が無いので **no-op**。ツールは R002（`exit`/`dismiss` の対象セッションが見つからない）を警告してよい。

**解釈 B（back(X) は現在フレームのスタックしか見ない）**: 対応表の `back(X)` 行に「見つかれば**同じ F**」と明記されている——これは複数フレームを跨がず、開始フレーム自身のスタック内だけを探すとも読める。この場合 `ホーム` は F1=[(A,initial),(B,initial)] の中に無いので **no-op**（F1 と `@S` は温存）。続く `exit(@S)` はアクティブパス上（現在フレーム F1 の begin が `@S`）で発見、F1 を破棄して親 R0 へ戻る。結果は解釈 A と同じ最終木・同じ最終画面になるが、こちらは**正規の exit**（警告なし）。

**(4) 確信度**: 低（解釈の選択について）／最終アクティブ画面のみ高（両解釈で一致するため）。

**(5) 決められない**: `back(X)` が現在フレームの外（祖先フレーム）まで探索・破棄しながら遡るのか、現在フレームのスタック内に限定されるのかは SPEC 内で**矛盾する記述**がある（対応表の「同じ F」 vs. 「戻り先が無いとき」節の「木のどこにも...no-op」という全木規模の言い回し、および `back()`（引数無し）に明記された単段跳躍規則をどこまで `back(X)` に一般化するか）。これにより、`@S` が `back(ホーム)` の時点で暗黙に破棄されるか、後続の `exit(@S)` まで生き残るかが未規定——結果画面は同じでも、**警告が出るかどうか（R002 の有無）**が解釈によって変わる。

## Q3: present(A, @S) → push(B) → switch(A, @S)

**(1) 最終アクティブ画面**: `B`（push(B) の initial variant のまま。A の initial には戻らない）

**(2) フレーム木**
- `present(A,@S)`: R0 の子 F1（barrier あり、begin=@S）。F1=[(A,initial)]。active=F1。
- `push(B)`: 現在フレーム F1 に積む。F1=[(A,initial),(B,initial)]。active=F1。
- `switch(A,@S)`: `@S` は生存中（F1 自身がそれ）。「@S が生存していれば、現在フレームを中断して @S の中断位置（そのフレームの最上段）へ復帰する。このとき X は無視される」。ここでは中断対象と復帰先が同一フレーム F1 なので、実質的に何も変わらない——F1 はそのまま、トップは `(B,initial)`。

最終木:
```
R0 = [(ホーム, initial)]
└─ F1 (present製, barrier=あり, begin=@S) = [(A,initial),(B,initial)]  ← active、トップ=B
```

**(3) 警告**: SPEC は「ツールは定義と異なる X を警告してよい」と明記（X=A を渡したが、実際に resume した最上段は B）。診断コード表に採番されたコードは無く、任意の lint 扱い。

**(4) 確信度**: 高。「switch（中断と復帰）」節に直接該当する記述がある。

**(5) 決められない点**: なし。

## Q4: present(A, @S) → present(B) → present(C, @T) → dismiss()

**(1) 最終アクティブ画面**: `A`（F1 の initial variant）

**(2) フレーム木**
- `present(A,@S)`: R0 の子 F1（barrier あり、begin=@S）。F1=[(A,initial)]。active=F1。
- `present(B)`（無名）: F1 の子 F2（barrier あり、begin=無名）。F2=[(B,initial)]。active=F2。
- `present(C,@T)`: F2 の子 F3（barrier あり、begin=@T）。F3=[(C,initial)]。active=F3。
- `dismiss()`: アクティブパス（F3→F2→F1→R0）を遡り、**直近の無名セッション**を探す。F3 は named（@T）なので素通り。F2 が無名 → target。F2 と**子孫（F3=@T ごと）**を破棄。「素通りした名前付きセッションは道連れにされて消える」の通り、@T も消える。active は F2 の親 F1 に戻る（begin 地点 = F1 のトップ = (A,initial)）。

最終木:
```
R0 = [(ホーム, initial)]
└─ F1 (present製, barrier=あり, begin=@S) = [(A,initial)]  ← active
```
@T・F2・F3 はすべて破棄。@S（F1）は無傷で残る。

**(3) 警告**: なし。「多段 present は無名セッションが積み重なり、`dismiss()` は LIFO で直近の無名を 1 つ破棄」「素通りした named session は道連れ」という規則通りの正規動作であり、mismatch や見つからないケースではない。

**(4) 確信度**: 高。「present / dismiss は compound verb」節に直接記述がある worked パターン。

**(5) 決められない点**: なし。

## Q5: switch(##展開, @weird)

**(1) 最終アクティブ画面**: **決められない**

**(2) フレーム木**: 部分的に決まる。`@weird` は未作成なので switch は新規作成（create）分岐に入る。現在（唯一の）フレームは R0 で、R0 は switch 製ではない → 兄弟規則により新規フレームは R0 の**子**になる（barrier あり、begin=@weird）。ここまでは一意に決まる。しかし新規フレームのスタック内容 `[(?, 展開)]` の `component` 部分が定まらない。

**(3) 警告**: 不明。裸の `##展開` が指す component が実在しない/未定義なら「未定義 component」相当の扱い（設計原則によりエラーにはしない可能性が高い）だが、SPEC の診断コード表には「未定義 variant を参照した」に対応するコードが無い（未定義 component は明示的に許容されると書かれているが、未定義 variant についての言及はない）。

**(4) 確信度**: 低。

**(5) 決められない理由（未規定点）**:
- `nav-target` の文法は `"##" name`（裸 variant 参照）を `push`/`present`/`goto`/`switch` すべてに対して許可している。だが SPEC が明示的に worked example を示すのは `goto(##表示)`（同一フレームの最上段の variant を書き換えるだけの操作）のみ。
- 「document common（最初の `#` より前）」節で明言されているのは「裸の `##variant` は**同一 component 内の variant を指す記法**だが、母体となる component が無い文脈（document common）では書けない」という原則——つまり裸 `##variant` は常に**母体となる component（=この記法が書かれている場所の host component）**に対して解決される。これは**字句的（lexical）**な解決だと読める。
- しかし `switch` の create 分岐は、書かれた場所とは無関係な**新しいフレーム**をどこか（今回は R0 の子）に生成する。「母体となる component」が字句上のホスト（このインタラクション行が属する component 定義）を指すのか、実行時のカレントアクティブ component（この場合たまたま `ホーム`）を指すのかを、SPEC は switch の文脈では明記していない。
- 本問は前後の `.shitae` ソース文脈（このインタラクション行がどの component の定義内にあるか）を与えられていないため、字句的ホストが特定できず、どちらの解釈でも「決められない」。仮に実行時カレント（`ホーム`）だと仮定しても、`ホーム` に `展開` という variant が定義されている保証はどこにもない。

## Q6: present(ホーム, @tabHome) → switch(検索, @tabSearch) → switch(通知, @tabNotif) → exit(@tabSearch)

**(2) フレーム木**
- `present(ホーム,@tabHome)`: R0 の子 F1（barrier あり、begin=@tabHome）。F1=[(ホーム,initial)]。active=F1。
- `switch(検索,@tabSearch)`: @tabSearch 未作成。現在フレーム F1 は switch 製でない→新規フレームは F1 の**子**。F2=[(検索,initial)]（barrier あり、begin=@tabSearch）。active=F2。

- `exit(@tabSearch)`: アクティブパス（F3→F1→R0）を走査するが `@tabSearch` は見つからない（F2 はアクティブパス上に無い、兄弟であって祖先ではない）。「見つからなければ木全体から @S を探して遠隔破棄する（そのフレームを子孫ごと裏で破棄し、アクティブフレーム＝画面は動かない）」規則が適用。F2 を遠隔破棄。active（F3）は変化しない。

```
R0 = [(ホーム, initial)]
└─ F1 (present製, barrier=あり, begin=@tabHome) = [(ホーム, initial)]
```

F2（検索, @tabSearch）は破棄済み。

**(3) 警告**: なし。「中断中（非アクティブ）の @S への exit(@S) は可。そのフレームを裏で破棄し、画面は動かない」という規則通りの正規動作。

**(4) 確信度**: 高。「フレーム木」節の遠隔破棄規則、「switch（中断と復帰）」節の兄弟規則にほぼそのまま合致する worked パターン。

## Q7: show(ミニプレイヤー##再生中) → show(ミニプレイヤー##一時停止)

**(1) 最終アクティブ画面**: フレーム側は無変化（`ホーム`、初期状態のまま——`show`/`hide` はフレーム木を操作しない別カテゴリ）。オーバーレイとして表示される variant は `ミニプレイヤー##一時停止`。

**(2) フレーム木**: 変化なし。`R0=[(ホーム,initial)]`。
オーバーレイ集合（フレーム木とは別の実行時状態）: `{ ミニプレイヤー(一時停止) }`——1 エントリのみ。

根拠: オーバーレイ集合は「掲示中の component の**集合**」であり ID は component 名が兼ねる。「同一 component の多重掲示は初版では扱わない」と明記されているため、同じ `ミニプレイヤー` を 2 回 `show` しても集合のエントリは 1 つのまま増えず、2 回目の `##一時停止` 指定がそのエントリの表示 variant を上書きする、と読むのが自然。

**(3) 警告**: なし。SPEC の診断コード表・lint 推奨のいずれにも該当条件が無い。

**(4) 確信度**: 中。「同一 component の多重掲示は扱わない」という**制約**は明記されているが、「では同じ component を variant違いで再 show したときに何が起きるか（上書きされる／2回目が無視される／エラー）」を直接説明する文はなく、集合の定義（ID=component名の集合）から**上書き**を導いている推論。

**(5) 決められない点**: 2 回目の `show` が「1 回目を上書きする」のか「（同一 component なので）no-op で 1 回目のまま残る」のかは、SPEC の文面から論理的に上書きの方が自然だが、明示的な記述はない——ここは推論であり、SPEC には**この 2 者を区別する記述が無い**。

## Q8: push(A, @S) → back() → exit(@S)

**(1) 最終アクティブ画面**: `ホーム`（`back()` 実行時点で初期状態に戻り、続く `exit(@S)` は no-op）

**(2) フレーム木**
- `push(A,@S)`: R0 の子 F1 を新規作成（barrier なし、begin=@S）。F1=[(A,initial)]。active=F1。
- `back()`: F1 のスタックは 1 段のみ＝最下段。barrier を持たない子フレームの最下段での `back()` は「子フレームを（begin マーカーごと）破棄して親フレームへ抜ける」。F1（と `@S`）を破棄し、active は R0 に戻る（トップ=(ホーム,initial)、無変化のまま）。
- `exit(@S)`: `@S` はアクティブパス（R0 のみ）にも木全体にも存在しない（既に破棄済み）→ no-op。

最終木:
```
R0 = [(ホーム, initial)]
```
初期状態と完全に一致（`@S` を含めどのフレームも残らない）。

**(3) 警告**: `exit(@S)` は「戻り先が見つからない」ケースに該当し、ツールは **R002 相当の警告を出してよい**（「セッションの mismatch」節・「戻り先が無いとき」節）。

**(4) 確信度**: 高。「barrier を持たない子フレームの最下段での back()」規則が対応表・本文双方に明記されており、この設問はその規則に正確に一致する。

**(5) 決められない点**: なし。

## 総括

**最も自信がない問**: Q5。`switch(##展開, @weird)` は、裸の `##variant` を nav-target として switch の**新規フレーム作成**分岐に使った場合の意味論が SPEC から一意に定まらない。「裸 `##variant` は母体となる component に対して解決される」という原則（document common 節）は明言されているが、その「母体」が**字句的ホスト**（このインタラクション行が定義されている component）を指すのか、**実行時のカレント component** を指すのかを、switch のように書かれた場所と無関係な新規フレームを生成する verb の文脈で明記していない。加えて本問自体が `.shitae` のソース文脈（この switch がどの component 内の行か）を与えていないため、二重に未決定。

次点は Q2。`back(X)` が現在フレームのスタックに限定されるのか（対応表の「見つかれば同じ F」という文言）、`back()`（引数無し）の単段跳躍規則を一般化して複数フレームを跨いで探索・破棄しうるのか（「戻り先が無いとき」節の「木のどこにも積まれていない...no-op」という全木規模の言い回し）、SPEC 内に**字面上の緊張**がある。この設問では最終的なアクティブ画面はどちらの解釈でも一致するため実害は小さいが、`@S` が `back(ホーム)` の時点で暗黙に破棄されるかどうか（＝後続 `exit(@S)` で警告が出るか）が解釈依存になる。

**SPEC のどこが曖昧だったか（まとめ）**:
1. `back(X)` の探索範囲（現在フレーム限定か、非 barrier フレームを跨いで祖先まで遡るか）——対応表の文言と「戻り先が無いとき」節の文言が完全には整合しない。
2. 裸 `##variant` を nav-target に使う際の「母体 component」の解決規則が、`goto` 以外の verb（特に新規フレームを作る `push(X,@S)` / `present` / `switch` の create 分岐）でも同じ字句的解決なのか、実行時解決なのか未確認。
3. `show(X##v)` を同一 component に対して variant 違いで連続実行したときの挙動（上書き／no-op）が、オーバーレイ集合の定義から論理的には推測できるが明文化されていない。
