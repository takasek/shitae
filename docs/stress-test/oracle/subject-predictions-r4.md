# frame 意味論オラクル r4 — 被験者予測

## Q1

予測: switch 実行後もアクティブ画面は `確認`（`push(確認, @co)` が開いた frame の最上段、initial variant）のまま変化しない。`別枝` は開かれない。

根拠: 「フレーム木」節・「switch（中断と復帰）」節。`push(確認, @co)` は現在フレーム（ルート）の子フレーム F′ を新規作成し begin マーカーを `@co` とする。以降 F′ がアクティブ。次の `switch(別枝, @co)` はこのアクティブな F′ 自身の中で発火する。`switch(X, @S)` の規則は「@S が生存していれば、現在フレームを中断して @S の中断位置へ復帰する（X は無視）」だが、ここで @S＝`@co` が指すフレームはまさに「現在フレーム」F′ 自身である。中断してから同じ F′ の中断位置（＝ (確認, initial)）へ復帰する操作は、対象と現在が同一フレームであるため観測可能な変化を生まない。`@co` は「生存」しており未作成でも破棄済みでもないため、resume-or-create のうち resume 経路を取り、新規フレーム作成（＝`別枝` を開く）は起きない。

確信度: 中。上記は「switch（中断と復帰）」節の規則（生存時は中断→復帰、X は無視）を機械的に適用した帰結だが、SPEC 中の例はすべて「@S の対象フレームが現在フレームとは異なる（中断中の別フレームへ切り替える）」ケースのみを扱っており、「@S の対象フレームが呼び出し元の現在フレームそのものである」という自己参照的なケースを明示的に扱った記述は無い。この一点において外挿を含む。

## Q2

予測: 発火後、共有レジストリの (mod, 状態) は `停止` に書き換わる。

根拠: 「モジュール化」節「別名::の解決は、その参照が書かれたファイルのimport表による」および「モジュールの同一性はファイルで決まる」。`> タップ(停止ボタン) -> set(状態##停止)` は `ミニ` の body に書かれており、`ミニ` 自体が `mod.shitae` で定義されている。裸参照の解決は「参照が書かれたファイル」を基準にする原則（`::` 修飾参照の解決規則の一般化）に従うため、この裸の `状態` は `mod.shitae` 内で定義された `#! 状態`（当該 singleton）を指し、`ホーム`（エントリファイル）から `show(mod::ミニ)` で掲示していても変わらない——「オーバーレイ」節も「掲示中の component の interaction はどのフレームがアクティブでも有効」とするのみで、参照解決先を変えるとは書いていない。`set(X##v)` は「singleton component」節により遷移・掲示を伴わず共有 variant のみを書き換える state verb であり、対象が singleton であることも前提を満たす。

確信度: 中。「モジュール識別＝ファイル」「::解決は書かれたファイルのimport表による」という原則から、無修飾の裸参照も同様に「書かれたファイル」で解決されると外挿しているが、SPEC には「同一ファイル内の裸（無修飾）component 参照が、表示元ファイルではなく定義元ファイルで解決される」と一文で明言した記述が無い。document common の「未定義 component は参照したファイルに属する」規則は対象が未定義の場合限定であり、`状態` は定義済みのためこの規則の適用外である点も含め、確度をやや割り引いた。

## Q3

予測: `push(学習)` は `##ハート切れ` で開く。

根拠: 「singleton component」節「singleton の variant は共有レジストリへの参照であり、スナップショットをどこにも作らない」「戻り系は…singleton は除く——常に共有 variant の現在値が見える」。この一般規則は「variant 指定なしで開くと初回は initial、以降は最後に遷移した variant で開く」という既定の singleton 版オーバーライドであり、singleton の場合は常に共有レジストリの現在値がそのまま見える。`set(学習##ハート切れ)` は同節「set(X##v) は遷移も掲示もせずに共有 variant だけを書き換える」により、まさにこの共有レジストリの値を書き換える。同節に載る用例（`> タップ(選択肢) -> [不正解・ハート切れ] set(学習##ハート切れ)` の直後に `学習` へ戻る想定）も同じ構図であり、`set` 後に `学習` を開けばハート切れが見える設計意図と整合する。

確信度: 高。

## Q4

予測: 3 手目 `push(支払い, @co)` で R005 警告が出る。

根拠: 「フレーム木」節・「セッション」節・診断コード表 R005「生存中の同名 @S がアクティブパス上にある状態での再 begin（push/present）」。`push(確認, @co)` がフレーム F1（begin=@co）を作成し F1 がアクティブになる。`present(モーダル)`（無名）は F1 の子フレーム F2（barrier あり、begin=無名）を作成し F2 がアクティブになる。この時点でのアクティブパスは root→F1→F2 であり、F1 はこのパス上に生存している。3 手目 `push(支払い, @co)` は F2 の子として `@co` を再び begin しようとするが、`@co` はすでにアクティブパス上（F1）に生存しているため、R005 の条件（アクティブパス上に生存中の同名 @S がある状態での再 begin）に完全に合致する。

確信度: 高。

## Q5

予測:
(i) 3 手目 `push(X, @a)` では R005 警告は**出ない**。
(ii) `exit(@a)` 後のアクティブ画面は `タブB`（push 前の variant、`switch(タブB, @b)` で開いた initial variant）。畳まれるのは push(X, @a) 3 手目で `タブB` の中に新規作成された方の `@a`（step3 で作られたフレーム）であり、`タブA` を開いた `switch(タブA, @a)` 側の `@a` ではない。

根拠: 「switch（中断と復帰）」節の兄弟規則により、`switch(タブA, @a)` は root の子フレーム F_a（begin=@a）を作る。続く `switch(タブB, @b)` は、現在フレーム F_a 自身が switch 製フレームであるため「祖先方向に最も近い switch 製フレーム」は F_a 自身に一致し、新規フレーム F_b はその兄弟（root の子）として作られる——F_a と F_b は root を共通の親とする兄弟。3 手目 `push(X, @a)` は現在アクティブな F_b の子として `@a` を begin するが、この時点のアクティブパスは {F_b, root} のみであり、`@a` を保持する F_a は F_b の兄弟であって祖先ではないためアクティブパス上に無い。診断コード表 R005 は文言上「アクティブパス上にある状態での再 begin」に限定されており、木全体を見れば同名 `@a` が別枝に存在していても、それは「フレーム木」節が明言する「木の複数箇所に同名の @S が存在する場合…」の想定内の状況であって R005 の発火条件を満たさない。よって (i) は不発。`exit(@a)` は「フレーム木」節「まずアクティブパスを『新しい方から最初の @S』規則で走査し…見つからなければ木全体から遠隔破棄する」に従う。`exit(@a)` 実行時のアクティブフレームは step3 で作られた F_a2（begin=@a、タブB の子）そのものであり、アクティブパスの走査で即座に（距離 0 で）見つかる。ゆえに遠隔探索（タブA の @a）に進む前に F_a2 が破棄対象として確定し、その親 F_b（タブB）の begin 地点へ戻る。タブA 側の switch 製 `@a` は別枝にあり手つかずのまま残る。

確信度: 高。

## Q6

予測: `set(学習##ハート切れ)` 後、掲示中の `学習` の表示 variant は `##ハート切れ` になる（即時反映）。

根拠: 「オーバーレイ」節「X が singleton（#!）の場合、エントリは共有レジストリへの参照であり、initial への上書き規則は適用しない（共有 variant の現在値が常に見える）」、および「singleton component」節「掲示中の singleton にも即時反映される（掲示中のミニプレイヤーが singleton なら、他画面からの set がその場で見た目を変える）」。`show(学習)`（variant 省略）で掲示したエントリは共有レジストリへの参照そのものであり、スナップショットを取らない。したがって `set(学習##ハート切れ)` による共有 variant の書き換えは、掲示中のエントリにもそのまま反映される。

確信度: 高。

## Q7

予測: `set(記事##展開)` は診断コード **E030**（`set()` の対象が定義済みの非 singleton component）に該当する構文/意味エラーとして検出される。`記事` は singleton ではないため共有レジストリのエントリ自体を持たず、この呼び出しによってアクティブ画面・フレーム木・オーバーレイ集合のいずれも変化しない——ただし「E030 検出後、処理系が実行時にこの result をどう扱うか（この result だけ無視して後続を続けるのか、文書全体を無効として扱いシミュレーション自体を拒否するのか）」は SPEC からは決められない。

根拠: 診断コード表「E030 | set() の対象が定義済みの非 singleton component（インスタンス独立のため書き込み先が定まらない）| error」。「singleton component」節「共有するのは variant（見た目の状態）だけ…独立インスタンスが欲しければ既定の # のまま」「対象は singleton のみ——通常 component はインスタンス独立で『どのインスタンスに書くか』が定まらないため、set の対象にできない（E030）」。severity が warning の R00x 系（R002〜R005）については「no-op として実行は継続するが警告してよい」という運用が本文中で明示されているのに対し、E00x 系（error）については診断コード表がラベルを与えるのみで、error 判定時に処理系がどの時点（構文解析／意味解析／実行時）で止まるべきか、あるいは当該 result のみをスキップして残りの result-list を実行するのかについての一般規則が本文に見当たらない。

確信度: E030 が該当することは高。E030 検出後の runtime の具体的挙動（実行継続 vs 拒否）は決められない——SPEC に error severity 診断の実行時扱いを定めた記述が無いため。
