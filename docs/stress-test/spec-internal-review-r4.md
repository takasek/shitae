# SPEC 内部整合レビュー — r4 範囲

対象は docs/SPEC.md 単体の精読のみ。GLOSSARY・AI_GUIDE・examples・packages・.claude・docs/stress-test の既存文書・docs/adr は参照していない。文体・誤字は対象外、内部整合（矛盾・片方にしかない条件・用語の揺れ・適用範囲の曖昧さ）のみを列挙する。分類は ❌ 矛盾 / ⚠️ 未定義・曖昧 / 💭 議論の余地。

## 1. `set`（state verb）

### ⚠️ §診断コード（E030）vs §singleton component: set の対象が「未定義 component」のときの扱いが規定されていない
問題の一文: E030 は「set() の対象が定義済みの非 singleton component」という条件でのみ発火する。
該当引用: 診断コード表 E030「`set()` の対象が定義済みの非 singleton component（インスタンス独立のため書き込み先が定まらない）」。singleton 節の該当段落（315行目付近）も「対象は singleton のみ…`set` の対象にできない（E030）」と述べるのみで、対象が定義済みか未定義かには触れない。
影響: `set(未定義##v)`（ファイル中にまだ定義が無い component を対象にした set）は「定義済みの非 singleton」に該当しないため E030 の対象外になる。presence gate には「対象が未定義 component など判定不能なときは always-on」という明示のフォールバック規則があるが（254行目付近）、set にはこれに相当する規定が無い。読者は「set の対象が未定義のとき、E030 相当のエラーになるのか、判定不能として素通りされるのか、後で定義が現れて singleton だと判明した時点で有効になる前方参照として扱われるのか」を SPEC から一意に決定できない。

### 💭 §EBNF（set-nav）vs §diagnostics: set の誤形（セッション付き・裸 ##v・collection 付き）を E029 一本に束ねる一方、hide の誤形は E020/E027 に分けている非対称
問題の一文: EBNF の set-nav コメント（206-207行目）は「裸 "##variant"…・"*"（collection）・セッションは書けない——いずれも E029」と3種の誤形を1コードに集約するが、同じく「引数の形が違う」誤りを扱う hide-nav は同種の誤りを E020（component 付き `##v`）と E027（裸 `##v`）の2コードに分けている（201-202行目）。
影響: 実害は小さいが、「引数形状の誤りを何粒度でコード分割するか」の基準が verb ごとに違って見える。hide は形状ごとに区別する理由（誤り検出のため字句上は認識する、という注記）が明示されているのに、set が1本化されている理由は書かれていない。

## 2. E027（overlay 裸 ##variant）／E028（singleton × collection）／R005（同名 @S 再 begin）

### ⚠️ §診断コード（E027）vs §EBNF（show-nav/hide-nav）: 「overlay verb（show/hide）の引数が裸 ##variant」で E027、という条件文の show 側の裏付けが弱い
問題の一文: 診断コード表 E027（755行目）は「overlay verb（show/hide）の引数が裸 ##variant」と show・hide 両方を主語にする。
該当引用: EBNF のコメントで裸 `##variant` の扱いを名指しで説明するのは hide-nav 側だけ（201-202行目「hide に "##" は本来書けないが、誤り検出のため字句上は認識する——component 付き（hide(X##v)）は E020、裸（hide(##v)）は E027」）。show-nav 側にはこの種の注記が無く、show-nav の文法自体（199行目）は component 名を必須項として要求しており、名前を欠いた裸 `##v` が show-nav としてどう認識されるかがその場では示されていない。オーバーレイ節本文（550行目）は「裸 ##variant も書けない（母体が無い。E027）」と show/hide を区別せず述べている。
影響: `show(##v)` を書いたとき、それが E027 として名指しで検出されるのか、単に「name が必須」という文法違反の一般的な構文エラーとして扱われるのか、EBNF セクションだけを読むと hide ほど明確に判定できない。

### 💭 §セッション vs §診断コード（R005）: R005 の条件が push/present に限定される理由が、読解順序上は switch 節を読むまで示されない
問題の一文: 診断コード表 R005（759行目）「生存中の同名 @S がアクティブパス上にある状態での再 begin（push/present）」。
該当引用: セッション節（384行目）は「セッションを開始できるのは積む側（push/present）と switch（新規作成時）のみ」と switch も begin 可能な verb として並記した直後、386行目で同名 @S の入れ子問題を push の例だけで説明し、R005 のコード注記も push/present に限定する。switch が resume-or-create であるため「生存中の同名 @S への switch」は必ず resume になり再 begin にはならない、という区別は switch 節（426行目以降）で初めて明かされる。
影響: セッション節を読んだ時点の読者は、switch も begin できるはずなのになぜ R005 の対象から外れているのか根拠を持てず、記載漏れではないかと疑いうる（switch 節まで読めば整合するが、セッション節の時点では説明されない）。

### 整合を確認した点（E028）
singleton 節325行目・collection 節651行目・診断コード表 E028（756行目）は「singleton に `*` を付けられない」という同一規則を3箇所で一貫して述べており、宣言側・参照側の適用範囲も揃っている。矛盾は見つからなかった。

## 3. セッションの入れ子と switch・フレーム木

### 💭 §セッション（同名 @S 入れ子）vs §フレーム木: 「直近の1つ」と「@S と子孫フレームを全部破棄」の関係が、最初の例だけでは接続されていない
問題の一文: セッション節386行目「exit(@checkout) / dismiss(@checkout) は LIFO で直近の1つしか畳まない」。
該当引用: フレーム木節415行目は一般規則として「exit(@S) / dismiss(@S) は @S とその子孫フレームを全部破棄」と述べる。386行目の例（push(確認,@checkout) の中に push(支払い,@checkout) を入れ子にする）ではこの2つの記述は矛盾なく一致する（内側の @checkout だけが「直近の1つ」として破棄され、たまたま子孫が無いので「全部破棄」も同じ結果になる）が、両者の役割分担——「直近の1つ」は破棄対象の begin フレームの選び方の規則、「子孫ごと」はそのフレームに付随して連れて行かれる範囲の規則——は明示的に接続されていない。
影響: 内側の @checkout フレームがさらに子（別の push 等）を持つケースを読者が想像したとき、「直近の1つ」という言葉から「その1フレームだけが消え子孫は残る」と誤読しうる。実際は415行目の一般規則により子孫も道連れになるはずだが、386行目の段落はこの一般規則への参照を持たない。

## 4. presence gate とオーバーレイ

### ⚠️ §操作は variant に属する（裸参照の判定規則）vs §オーバーレイ（gate は別軸）: 掲示中 component の interaction に書かれた裸 gate 参照が、どの「現在 variant」で判定されるか一意に読めない
問題の一文: presence gate の一般規則は「裸参照（投了?）は host component（その行動が書かれている component）の現在 variant の body 直下を見る」（253行目）と定義するが、この定義はホスト component が**フレームに積まれている**ことを前提にした言い回りで、オーバーレイという「フレームではない」（548行目）在り方を想定していない。
該当引用: オーバーレイ節552行目「gate（presence gate）とは別軸。gate は『その variant の実効 body に対象があるか』だけを見て、掲示状態は見ない」。この一文の「その variant」が「掲示中 component 自身の表示中 variant」を指すのか、253行目の一般規則の言い回し（host component の現在 variant）をそのまま指すのかは、文脈から強く示唆されるのみで明示されていない。
影響: document common の裸参照には「発火時にアクティブな component の現在 variant の実効 body で判定する」という明示の動的解決規則が別途用意されている（257行目）のに対し、オーバーレイの裸参照には対応する動的解決規則が明文化されていない。読者は「オーバーレイの裸 gate 参照も document common と同様にアクティブフレーム側で判定されるのでは」と類推し、実際に意図されている「掲示中 component 自身の表示中 variant で判定する」という解釈と取り違える可能性がある。

## 5. モジュール化 — 無修飾（`mod::` なし）component 参照の解決

### ⚠️ §モジュール化 vs §document common・§オーバーレイ: 掲示中 overlay の interaction／document common の interaction から発火する無修飾参照が、どのファイルの import 表で解決されるか明文化されていない
問題の一文: モジュール化節は「別名:: の解決は、その参照が書かれたファイルの import 表による」（635行目）と `::` 修飾参照についてはレキシカル（書かれたファイル基準）な解決を宣言する。一方 document common 節は「実行時に有効な document common はアクティブフレームの最上段 component が定義されているファイルのもの」（79行目）と、どの document common ブロックが「有効」かをアクティブ（実行時）基準で選ぶ規則を持つ。
該当引用: 79行目、547行目「掲示中の component は全画面で表示され…どのフレームがアクティブでも有効」、552行目「掲示中 overlay の interaction の有効性はオーバーレイ節の規則によるもので、document common のスコープとは無関係」、635行目。
影響: document common に関しては「有効な doc common ブロックはアクティブ画面のファイルのものに決まる」ため、そのブロック内の無修飾参照は結局そのファイル自身の import 表で解決すればよく実害は生じない（レキシカル基準とアクティブ基準がこのケースでは一致する）。ところがオーバーレイは事情が違う——掲示中 component（例: 別ファイル player.shitae で定義された「ミニプレイヤー」）の interaction は、それとは無関係な別ファイル（例: home.shitae）の画面がアクティブな間も発火しうる（547行目）。このとき interaction 内の無修飾参照（564行目の例そのまま `push(プレイヤー)`）が、①ミニプレイヤーが定義されているファイル（レキシカルな home＝player.shitae）の import 表で解決されるのか、②現在アクティブな画面が属するファイルの import 表で解決されるのか、SPEC はどちらの原則を採るとも明言していない。`::` 修飾参照については「書かれたファイル基準」（①相当）という一般原則があり、document common の実例もこの原則と矛盾しない結果になるため①が妥当な類推ではあるが、document common 節の「アクティブフレームの最上段 component が定義されているファイル」という言い回しがアクティブ基準（②）の存在を強く印象づけるため、オーバーレイの無修飾参照についても読者が②を類推する誤読リスクが残る。オーバーレイ節はこの点について沈黙しており（「有効性」の規定はあるが「解決」の規定が無い）、①②いずれであるかを SPEC 本文だけから一意に確定できない。

## 6. オーバーレイの singleton 特例と singleton 節

### 整合を確認した点
オーバーレイ節545行目の「X が singleton の場合…共有 variant の現在値が常に見える」「show(X##v)（明示 variant）は表示 variant の選択ではなく共有状態の書き換え」は、singleton 節313-314行目の「新規作成・show は initial variant で開く…の各規則は singleton には適用しない」「X##v 指定・goto(##v) は共有状態の書き換えとして働く（全所在に即時反映）」という一般規則をオーバーレイという具体的な文脈に適用した記述として整合しており、矛盾・欠落は見つからなかった。

### 💭 オーバーレイ節から singleton 節への参照ポインタが無い
問題の一文: オーバーレイ節545行目は singleton の挙動について詳しく述べるが、他の関連箇所（E028・E029・E030 の診断コード等）が一貫して行っている「（「singleton component」を参照）」という相互参照が無い。
影響: 実害は小さいが、singleton の一般規則とオーバーレイでの具体化が同一の規則であることを、参照ポインタ無しに読者が自力で確認する必要がある。

## 範囲外で見つけた明白な矛盾
