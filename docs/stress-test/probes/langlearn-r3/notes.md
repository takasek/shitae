# langlearn-r3 制作ノート

被験者として `docs/SPEC.md` のみを読み、他ファイル（GLOSSARY・AI_GUIDE・examples・packages 等）は一切参照せずに書いた。以下、記法ごとに参照した節・迷った点・確信度・要望をまとめる。

## タブナビゲーション（switch / present / タブの慣用句）

参照節：「switch（中断と復帰）」「タブの慣用句」（SPEC.md 397-444行）。

SPEC が「起動 component + present(ホーム, @tabHome) + タブバー部品への switch 集約」という慣用句をほぼそのまま例示していたので、そのままなぞった。`起動` をファイル先頭に置いてエントリポイントにし、`present(学習, @tabHome)` でタブ群のアンカーを作り、`タブバー` component に switch 群を持たせて各タブ画面は要素として置くだけにした。確信度：高（SPEC のワークトエグザンプルとほぼ同型）。

迷った点：`学習` タブ自身の中で `タップ(学習タブ) -> switch(学習, @tabHome)` を踏んだときの挙動（自タブ再タップ）。SPEC 417行の「生存中なので復帰。重複生成しない」を信じてそのまま書いたが、実際に無害かはツール上で確認できていない。

## レッスンフロー（present + セッション + exit の戻り先）

参照節：「present / dismiss は compound verb」「セッション」「フレーム木」。

レッスンを `present(問題, @lesson)` で開始し、正解を繰り返した末に `push(レッスン完了)`、「続ける」タップで `exit(@lesson)` して呼び出し元（学習画面）へ戻る、という設計にした。exit の戻り先が「begin 地点＝親フレームの位置」であることを「フレーム木」の対応表（487-498行あたり）で確認し、`present` から始めたので `exit` 単独で学習画面に戻れると判断した（switch を再度書く必要がないと判断）。確信度：高。

## ハート切れ判定（variant か presence gate か）

参照節：「操作は variant に属する」（218-236行）、presence gate（238-269行、日付/予約の例）。

最初は presence gate（`?`）でハートの有無に応じてレッスン開始ボタンを gate しようとした。しかし SPEC の文法（159行 `action = free-text, ["(", reference, ["?"], ")"]`）を読むと、gate は「行動そのものの対象」にしかかけられない。SPEC の日付/予約の例（257-269行）は「タップする対象そのもの」を `日付.選択可能?` のように書いており、ハートの有無で**別の対象（レッスン開始ボタン）**を gate したい場合、レッスン開始ボタンをハート component の内部要素として埋め込む必要が出てくる。これは「レッスン開始ボタンがハートの中に住む」という不自然なモデリングになるため断念し、代わりに principle 6（状態は variant で表す）に忠実に、`学習` component 自体を `##通常` / `##ハート切れ` の2 variant に分け、レッスン開始ボタンは `##通常` にしか存在しない、という設計にした。確信度：高（SPEC の「フォロー/フォロー解除」の例そのままの型）。

## ハート消費とバックグラウンド更新（諦めた表現・要望）

参照節：「フレーム木」「未定・分岐」の逐次適用（655-665行）、singleton（287-303行）。

問題を解く中でハートを使い切ったとき、`学習` 画面（非アクティブなフレーム）の variant を `##ハート切れ` に書き換える必要がある。`goto` はアクティブフレームの最上段しか書き換えられないため、直接は書けない。SPEC 663行の「`switch(フィード, @tabFeed) ; goto(##通常)` は切替後のフィードの variant を書き換える」という逐次適用の例をヒントに、`exit(@lesson) ; goto(##ハート切れ)` として「学習画面に戻ってからその場で variant を書き換える」形に落とした。これは exit の戻り先＝学習画面という前提が成り立つ今回のケースでは書けたが、**もし戻り先が違う画面だったら／複数箇所から同じ状態を書き換えたかったら、この chaining では書けない**という限界を感じた。

さらに、ハートが自然回復する（時間経過）ケースは、`学習` 画面がアクティブでない間に起きる可能性が高く、上記の chaining すら使えない。今回は諦めて `##ハート切れ` 内にコメントで「回復したら ##通常 に戻る想定」とだけ自然文で残した。

要望：**「今アクティブでないフレームの特定 variant を、事後に書き換える」ための構造的な手段**が欲しい。singleton（`#!`）はまさにこの用途のための機構だと理解したが、singleton を使うと「gate 対象の要素をその component の内部に埋め込む」という上記の不自然さが再発する（presence gate の項参照）。**「presence gate の対象は行動そのものでなく、任意の参照先の existence を見る」ような形**、あるいは**「別 component の variant を、画面遷移を伴わない副作用として書き換える」専用の result 種別**があると、今回のような「A 画面の状態が B 画面の操作可否に影響するが、B 画面自体を経由しない」というケースが自然に書けると感じた。

## ストリークバッジ（singleton + overlay の自己再 show）

参照節：singleton（287-303行）、オーバーレイの自己再 show（518-519行）。

「一度受け取ったクーポンはどこから開いても受取済」という singleton の例（291-297行）がそのまま streak バッジの要件（今日達成したらどの画面でも達成表示）に当てはまったので `#!` を使った。表示方法は、各タブ画面に要素として重複配置するのではなく、`起動` で `show(ストリークバッジ)` して以降ずっとオーバーレイとして掲示し続け、レッスン完了時に `show(ストリークバッジ##達成)`（自己再 show）で表示 variant を切り替える設計にした。singleton は「initial への上書き規則が適用されない」（520行）ため、`show(ストリークバッジ)` だけで常に現在の共有 variant が出る、という理解で書いた。確信度：中——singleton をオーバーレイとして常時掲示する使い方は SPEC に明示例が無く、自分で外挿した。

迷った点：`学習`/`リーグ`/`プロフィール` の各画面にバッジを**要素として**埋め込む案（singleton なので参照は 1 か所でも他の場所と状態は共有されるはず）も検討したが、二重表示（要素＋オーバーレイ）を避けるためオーバーレイ一本化にした。document common に要素行として置けば全 component に自動的に載る、という案も検討したが、SPEC の document common の説明（54-79行）が「用途は『どの画面でも起こるインタラクション』」と**インタラクション中心**の言葉で書かれており、要素行を置いた場合の意味論（各 component に本当に「共通要素」として展開されるのか）が文法上は許容されていても本文で明言されていなかったため、確信が持てず採用を見送った。

要望：**document common（および component common）に要素行を置いた場合の意味論の明記**が欲しい。文法上 `single-body` は element-line と interaction-line の混在を許すので書けてしまうが、本文の説明・例は一貫してインタラクション（deep link・通知・強制ログアウト）にしか触れていない。「全 component の表示にその要素が乗る」という理解で合っているか、確信が持てなかった。

## 通知バナー（overlay + document common）

参照節：「document common」「オーバーレイ」、ミニプレイヤーの例（529-542行）。

「リーグ順位変動」という外部イベントを document common のインタラクションとして書き、`show(通知バナー)` した。バナー component 側は `タップ(バナー本体) -> switch(リーグ, @tabLeague) ; hide(通知バナー)` とし、ミニプレイヤーの例と同型にした。確信度：高。

## 設定モーダル（present / dismiss）

参照節：「present / dismiss は compound verb」。

プロフィールから `present(設定)`（無名セッション）、設定側で `dismiss()` を呼ぶだけの教科書的な形。確信度：高。

## 出題ループ（諦めた表現）

参照節：「扱わないもの」（673-680行）。

1 レッスン内で複数問出題する「ループ」に相当する構造記号が無いため、最初は `goto(##出題中)` で同じ variant への遷移を繰り返す案を考えたが、そもそも `問題` component に variant を分ける必然性が無く（正誤で見た目の構造が変わるわけではない）、意味のない自己遷移になってしまうと感じてやめた。最終的に「次の問題を出題する」という自然文の副作用のみで表現した。「何問目か」「あと何問か」はデータであり `扱わないもの` に明記された範囲外だと理解しているので、これは SPEC の設計方針どおりの割り切りだと思う。確信度：中——本当にこれでよいのか（variant を割ってでも構造として出すべきだったか）は判断が割れると思う。

## 全体を通して

- gate（`?`）は結局 1 箇所も使わなかった。理由は上記のとおり「gate 対象＝行動そのものの対象」という制約が、今回のような「別 component の状態で別の要素を制御したい」ケースに合わなかったため。SPEC 本文で挙げられている例（日付の選択可否）は「対象自身の状態で対象自身への操作を制御する」ケースであり、今回の「ハートの状態でレッスン開始ボタンを制御する」ケースとは一段階ずれていた。この非対称に気づくまでに時間がかかった。
- collection（`*`）は `*選択肢` で 1 箇所使用。宣言側 `*` のみで、collection 全体への操作（`*選択肢` への括弧付き参照）は今回のフローには出てこなかった。
- singleton・presence gate・collection・condition label・overlay・switch・present/dismiss と、SPEC の主要構文はほぼ一通り触れられたが、「非アクティブな画面の状態を外から更新する」という要求が最後まで一番の摩擦点だった。
