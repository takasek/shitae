# delivery.shitae 制作記録

入力制限: `docs/SPEC.md` のみを読んで書いた。他のドキュメント・example・GLOSSARY・処理系コードは一切参照していない。CLI・simulator・テストも実行していない（構文的に妥当かどうかは自分で SPEC の文法・診断コード表と突き合わせて確認しただけで、実行による検証はできていない）。

## (a) 参照した SPEC.md の節

- 「two-layer model」「document common（最初の `#` より前）」— コンポーネント/variant の基本構造、document common の使いどころ（サポート・クーポン・カート・配達完了通知を document common に置いた）
- 「記号一覧」「文法（EBNF 風）」— `*` collection、`?` presence gate、`@` セッション、`->`/`;` の result-list 構文
- 「操作は variant に属する」の `# 日付` / `# 予約` 例 — `品目.在庫あり?` の presence gate 設計はこの例をほぼそのまま転用した
- 「transition verb」全節（push/goto と行き先、セッション、back barrier は直交、フレーム木、switch、present/dismiss は compound verb、戻り先が無いとき、セッションの mismatch）— チェックアウトフローの `present(カート確認, @checkout)` ＋ `exit(@checkout) ; push(ホーム)` 出口固定慣用句の設計根拠
- 「オーバーレイ（show/hide）」の `# プレイヤー` / `ミニプレイヤー` 例 — 配達状況バナーの設計をほぼそのまま転用した（対象を取らない bare action の書き方も含めて）
- 「行動（インタラクションの左辺）」「component に特権はない」「collection（`*`）」「未定・分岐」（`exit(@S) ; push(固定先)` 慣用句の明文箇所）「扱わないもの」（データ/コンテキストを持たないという制約）

## (b) 曖昧で迷った点

1. **チェックアウトフローに `push(X,@S)` を使うか `present(X,@S)` を使うか**。最初は「途中の画面間は back で 1 段ずつ戻れてよいはず」と考えて `push` を選んだが、要件「フローの途中でキャンセルすると入口がどこであれホームへ戻る」を厳密に守るなら、スタック最下段での暗黙の back（キャンセルボタンを押さない通常の back ジェスチャ）でも意図しない離脱ができてしまうのは望ましくないと考え直した。`push` は barrier が無いので最下段の暗黙 back でフレームごと破棄されて「入口の画面」に静かに戻ってしまう（ホームへは戻らない）。`present` なら barrier で止まり、離脱は必ず明示的な「キャンセル」を通ることになるので、要件の意図に近いと判断して `present(カート確認, @checkout)` に変更した。とはいえ段階間（カート確認→住所選択→支払い）の通常 back は barrier の内側なので普通に効く。
2. **「品切れ品目はタップできない」の範囲**。見出しは「タップできない」（一覧のカード自体が押せない）、括弧内は「カート追加が効かない」（詳細画面までは見られるが追加だけ不可）と、2 通りに読める書き方だった。両方を実装した：一覧側は `品目.在庫あり?` の presence gate で品切れカードへの遷移自体を塞ぎ、品目詳細側も `## 品切れ` variant に「カートに追加」のインタラクションを持たせない設計にした。ただし一覧側の gate がある限り、詳細画面の品切れ variant は通常到達しない（直リンク等への防御としてのみ残した）。
3. **クーポンモーダルの「ホームで受け取る」という性質の表現**。document common に `present(クーポン)` を置いて全画面から開けるようにしたが、`present(X)` は毎回 X の最初に定義された variant（`## 未受取`）で開く仕様なので、「一度受け取ったら以後は常に受取済で開く」という永続状態は表現できない（詳細は (d)）。
4. **通常の component 本体からの前方参照が許されるか**。SPEC は document common に限って「まだ定義されていない component への前方参照は可」と明記しているが、これは裏を返すと通常の component 本体からの前方参照については何も言っていないとも読める。今回はホームが店舗詳細を、店舗詳細が品目・品目詳細を、ファイル中でのちに定義される component として参照している（定義順とは無関係な設計）。EBNF や二重定義規則からは順序制約を読み取れなかったので「許される」と判断したが、確信は持てない。
5. **配達完了を document common の外部イベントとして書いてよいか**。`> 配達が完了する -> hide(配達状況バナー)` は、プッシュ通知やセッション切れの例（「セッション」節の deep link 例）に倣い、ユーザー操作でなく「外部で起きること」を行動の自然文として書いた。行動は「自然文で何でもよい」とあるので構文的には問題ないはずだが、意味的にこれが document common の想定用途に収まっているかは自信が持てない。

## (c) 各設計判断の確信度

| 判断 | 確信度 |
|---|---|
| component/variant の基本構造、presence gate の `品目.在庫あり?` 設計 | 高（SPEC の `# 日付`/`# 予約` 例をほぼそのまま転用） |
| 配達状況バナーの overlay 設計（show/hide、bare action） | 高（`# プレイヤー` 例をほぼそのまま転用） |
| `exit(@checkout) ; push(ホーム)` の出口固定慣用句 | 高（SPEC が「未定・分岐」節で名指しでこの慣用句を説明している） |
| `push` ではなく `present` でチェックアウトセッションを開始した判断 | 中（要件の字面だけからは push でも動作要件を満たせるため、設計者の意図を確認したい） |
| 品切れ品目まわりの二重実装（一覧 gate ＋ 詳細 variant） | 中（要件文の二通りの読み方をどちらも切り捨てず両方実装したが、過剰かもしれない） |
| document common からの前方参照が component 本体にも及ぶという解釈 | 中 |
| document common に「配達完了」という外部イベントを書いた判断 | 中 |
| クーポンモーダルを document common の `present(クーポン)` 一本で表現した判断 | 低（(d) の限界を回避できていない近似） |
| `dismiss()` が checkout の named session (`@checkout`) を巻き込まないことの確認 | 中（フレーム木の規則を手で追って「クーポン/サポートチャット自身の無名フレームが常に最も近いので @checkout より先に見つかる」と結論したが、simulator 等での実行検証はできていない） |

## (d) 書けなくて諦めた表現・欲しかった記法

1. **クーポンの「受け取り済み」を画面をまたいで保持する状態**。`present(X)` は毎回 X の最初に定義された variant で開く仕様であり、SPEC は「variant はインスタンスごとに独立」「データ／コンテキストは扱わない」と明言している。つまり「一度どこかで受け取ったら、以後はどの画面から開いても受取済表示になる」という、ごく普通の要件が原理的に表現できない。今回は諦めて `present(クーポン)` を document common に置き、毎回 `## 未受取` から開き直る不正確な近似で済ませた。欲しかった記法：document スコープで 1 つだけ存在する「シングルトンな」component（同じ定義への複数回の `present`/`push` が同一インスタンスの variant を共有する）を明示的に宣言する手段。今の shitae ではあらゆる `push`/`present` が常に新しいフレーム＝新しい variant インスタンスを作るので、永続的に状態を持つ画面外要素（受け取り済みバッジ、既読フラグ、カートの中身の点数、等）を一切表現できない。
2. **カートの中身（商品と点数、合計金額）が画面をまたいで実際に反映されること**。「カートに追加する」という副作用の自然文を書くところまでしかできず、それが `カート確認` 画面の `*カート内商品` に反映される、という当たり前の連動をつなぐ記法が無い。データを持たないという設計方針は理解しているが、フードデリバリーのような「カートの中身」がドメインの中心にあるアプリだと、この制約がかなり早く効いてくる感触があった。
3. **住所選択で選んだ住所が支払い・注文確定画面に引き継がれること**。同上の理由で、`住所を選択する` という副作用止まりで、選択結果が後続画面の表示に反映される様子は書けなかった。
4. **品目詳細を開いている最中に、外部要因（他の客が買い占めた等）でその場で品切れに変わるケース**。一覧側の `?` gate はすり抜けを防げるが、詳細画面を開いたあとの状態変化は「特定の 1 インスタンスに向けた外部イベント」であり、document common（画面を問わず起こる）にも、variant 内の通常インタラクション（ユーザー操作起点）にも収まらない。結局このケースは諦め、一覧側の gate だけに頼る設計にした。
5. （参考、実際には困らなかったが確認した点）overlay 集合の初期状態を明示する記法は無い。SPEC 上は暗黙に「何も掲示されていない」がデフォルトだと理解して進めたが、これを明示的に宣言する記法は無く、今回は特に問題にならなかった。

## (e) 仕様の誤読しやすい箇所

1. **`back(X)` は variant を指定できない（E016）**。「注文確定画面から戻ったらどの variant に戻るか指定したい」という発想が最初によぎったが、これはそもそも仕様上不要——戻り先はスタックに積まれた時点の variant に自動的に戻る、という規則を読み飛ばしていて、最初 back 系の設計で無駄に悩んだ。
2. **`goto` と `push` の違いの主眼**。表面的には「積むか積まないか」が主要な違いに見えるが、SPEC が実際に強調しているのは「セッションを開始できるかどうか」（`goto` はできない）という点で、しかも「既存の begin marker は保存する」という規則が独立に成り立つ、という細部は 1 回読んだだけでは取り違えやすかった。
3. **`present` は `push(X,@S)` の単なる言い換えに見える**。両方とも「セッションを開始する積む系」なので、最初は違いが分かりにくかった。実際の違いは barrier の有無であり、`present` は「モードに入る」という**意図**を one word に束ねた compound verb だという位置づけを掴むのに読み直しが必要だった。
4. **presence gate（`?`）は値や在庫数を評価しているのではない**という点。「品切れなら押せない」という要件を見た瞬間、直感的に「在庫数が 0 かどうかの条件分岐」を想像しがちだが、shitae が実際に見ているのは「品切れ variant に居るかどうか」という構造的な一点だけで、実際に在庫が何個かという値は shitae の外の話である、という区別を終始意識しておく必要があった。
5. **`dismiss()` が「直近の無名セッションだけを探し、途中の named session は素通りして道連れにする」規則**。今回のようにモーダル（クーポン・サポートチャット、いずれも無名セッション）を checkout（named session `@checkout`）の内側から開いた場合に `dismiss()` が `@checkout` を巻き込まないか、フレーム木の規則を手で追って確認する必要があった（結論：巻き込まない。モーダル自身の無名フレームが必ず `@checkout` より近いところで見つかるため）。この規則は文章で 1 回読んだだけでは動作を正確に予測しづらく、具体的な frame 列に落として初めて納得できた箇所だった。

## 一行要約

- 最大の曖昧点: チェックアウトフローを `push(X,@S)`（barrier なし）にするか `present(X,@S)`（barrier あり）にするかで、「途中キャンセルは必ずホームへ」という要件の厳密さの解釈が割れた（`present` を採用）。
- 最大の諦め: クーポンの「受け取り済み」状態や、カートの中身・選択した住所が画面をまたいで反映されるという、ごく普通のデータ永続化がそもそも shitae の設計方針（データ／コンテキストを持たない、variant はインスタンスごとに独立）と原理的に相容れず、書けなかった。
