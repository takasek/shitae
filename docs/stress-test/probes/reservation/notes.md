# reservation.shitae 作成メモ

## 参照した SPEC 節

- 「two-layer model」— component と variant の基本構造
- 「記号一覧」— 各種構文（`#`, `##`, `>`, `->`, `*`, `:`, `.`, `?`, `@` など）
- 「transition verb」— push, back, goto, exit, present, dismiss, switch の 7 語
- 「操作は variant に属する」— variant ごとに異なる UI 状態の表現方法
- 「variant の参照は必ず `##`」— variant 変更の記法
- 「セッション（`@S`）」— modal や flow の生存期間管理
- 「present / dismiss は compound verb」— barrier を持つモード遷移
- 「戻り先が無いとき」— back() が見つからない場合は no-op
- 「collection（`*`）」— 複数インスタンスの宣言と参照
- 「要素参照（`.`）」— component の内部要素を外から参照
- 「presence gate（`?`）」— 要素の存在に基づく条件付きインタラクション
- 「inline component」— その場限りの component 定義

## 仕様が曖昧・不明瞭だと感じた点

### 1. 複数ステップのモーダル内での戻るナビゲーション
**該当節**：「present / dismiss は compound verb」「戻り先が無いとき」

**曖昧性**：要件で「フロー内は 1 つずつ戻れる」と明記されているが、`present()` は back barrier を立てる。barrier を立てた場合、`back()` は（spec に「モード内から通常の back で外へ出ず」と書かれている通り）モード外には出ないはずだが、モード内の前ステップへは戻れるのか、それとも no-op なのかが不明瞭。

**自分の解釈**：barrier はモード外への脱出を防ぎ、モード内での `back()` は前フレーム（積まれた前の画面）へ戻る動作は許容すると解釈。ただし、variant 変更（`goto(##variant)`）の場合は stack に積まれないため、`back()` が機能しない。そこで明示的に `goto(##前のステップ)` で戻り先を指定する設計にした。

### 2. 複数 variant を持つ component の要素参照と presence gate の相互作用
**該当節**：「要素参照（`.`）」「presence gate（`?`）」「操作は variant に属する」

**曖昧性**：`# 日付` が `## 空きあり` と `## 満席` の 2 variant を持ち、`## 空きあり` 内に `選択対象` 要素があり `## 満席` には存在しない場合、親 component から `タップ(日付.選択対象?)` で参照したとき、presence gate `?` は「その日付のインスタンスが 空きあり variant にあるか」を条件にするのか、それとも「日付コンポーネント全体に選択対象要素が存在するか」を条件にするのか。

**自分の解釈**：presence gate `?` は、参照先 component（ここでは `日付`）の現在の variant に、指定された要素（ここでは `選択対象`）が存在するかを条件にするものと解釈。各 `日付` インスタンスは variant を独立に持つため、同じ参照でも variant によって動作が変わる。

### 3. Modal 内での variant 遷移と frame 構造の関係
**該当節**：「フレーム木」「present / dismiss は compound verb」

**曖昧性**：`present(予約フロー, @reservation)` で modal に入った後、その内側で `goto(##人数選択)` を実行したとき、frame 木の構造がどう変わるのか、特に新しい frame が作られるのか、既存 frame の variant が書き換わるのか。

**自分の解釈**：goto は「現在フレームの最上段の variant を書き換え」（spec: 「`goto(##variant)` は現在フレームの最上段の variant を書き換える」）と解釈。つまり、予約フロー modal 内では同じ frame で variant が切り替わり、新フレームは作られない。後で `back()` で戻ると、最後に set された variant に戻る。

## 主要構文ごとの確信度

| 構文 | 確信度 | 理由 |
|------|--------|------|
| `#` component / `##` variant | **高** | 基本構造として明確に説明されている |
| `>` interaction / `->` / result-list | **高** | 多数の例示があり理解が深まった |
| `push()`, `back()`, `goto()`, `exit()` | **高** | transition verb の説明が十分で、違いが明確 |
| `present()` / `dismiss()` | **中** | 概念は理解したが、barrier 内での back 挙動と variant 変更の組み合わせが実装時に想定通り動くか未確認 |
| `*` collection の参照 | **高** | 「1 インスタンスを指す」という明確な定義がある |
| `.` 要素参照と variant の組み合わせ | **中** | 別 component の内部要素参照は示されているが、variant 依存の要素参照の semantics がやや曖昧 |
| `?` presence gate | **中** | 基本的な仕組みは理解したが、複数 variant を持つ component での挙動の詳細（どの層で存在判定するか）が完全に確信できない |
| `@` session | **高** | 開始・破棄のタイミングが明確で、例も豊富 |
| `goto(##variant)` での variant 遷移 | **低** | variant change は明示されているが、modal (present) 内で複数ステップを variant 変更で実装することが想定されたユースケースなのか、別のパターンを使うべきなのか、spec からは読み取れない |

## 要件のうち素直に書けず、別の書き方に回避した表現

### 1. 「フロー内は 1 つずつ戻れる」の実装パターン
**要件**：日付選択 → 人数選択 → 予約確認 → 予約完了の順序で進み、各ステップから前ステップに戻れる。

**素直な書き方の問題**：`back()` を使うのが自然だが、`present()` の back barrier により、モード内での `back()` の挙動が不明瞭。

**選択した回避方法**：各ステップの variant 内に「戻る」ボタンを明示し、`goto(##前のステップ)` で前ステップの variant に遷移。明示的だが、「戻る先が複数あり得る（多くの step design）」場合は、variant 数が増える。

### 2. 満席の日付に対する条件付きインタラクション
**要件**：日付選択画面で、「空き」と「満席」で見た目が異なり、満席の日は選べず「キャンセル待ち登録」ボタンが出現する。

**素直な書き方の問題**：「満席の日は選べない」を、同じ `タップ(日付)` 行動で「variant によって結果が異なる」と書く方法が spec に明示されていない（condition label は結果を並べるものであり、行動対象の variant 条件ではない）。

**選択した回避方法**：日付 component に `## 空きあり` と `## 満席` の variant を持たせ、各 variant で異なる要素（`選択対象` vs `キャンセル待ち登録`）を提供。親で `タップ(日付.選択対象?)` と `タップ(日付.キャンセル待ち登録?)` の 2 行で条件を分ける。presence gate `?` により、要素が存在しない variant では行動が無効になる。

### 3. キャンセル確認ダイアログ後のナビゲーション
**要件**：予約キャンセル確認で「はい」を押すと、キャンセルを実行して確認ダイアログを閉じ、マイ予約一覧に戻る。「いいえ」でダイアログだけ閉じる。

**素直な書き方の問題**：「はい」の場合、`dismiss()` でダイアログを閉じるだけでなく、その後 `back()` で予約詳細 → マイ予約一覧へと遡る必要があるが、複数の操作を 1 行で書く構文が明瞭でない。

**選択した回避方法**：`;` で複数の result を並べる（`予約をキャンセルする ; dismiss() ; back()`）。これにより、副作用、modal 破棄、画面遷移を明示。

## その他 DSL への感想・改善案

### 感想
- **ラフさが機能する**：仕様が曖昧な部分でも「未定」や自然文で補える設計は、AI との往復に適している。完全な形式仕様ではなく、sketch に徹する判断が賢い。
- **variant と barrier の組み合わせが強力**：条件式を持たず、目に見える状態（variant）の列挙で UI の分岐を表現する方針は、実装とのギャップが小さく、デザイナーにも分かりやすい。
- **transition verb が 7 語に限定される**：語彙が少ないので学習コストが低く、各語の意味が明確。
- **インデントが意味を持たない**：見た目の整列と言語の意味が分離しているので、自動整形や diff が安定。

### 改善案
1. **複数ステップのモーダル・フローの記法**：`present(X)` の中でステップを進むとき、「前ステップへ」を明示的に書かずに自動で track する記法があると便利。例えば `goto(<<)` で「前へ」、`goto(>>)` で「次へ」のような糖衣記法。
2. **variant-conditional interaction**：現在は presence gate `?` で「要素の存在」を条件にしているが、「variant 自体を条件にした行動」を直接書けると、複数 variant に同じ要素があるが行動が異なる場合に書きやすい。例：`> タップ(button) -> [##満席] 満席メッセージ ; [##空きあり] 選択処理`。
3. **back() の明示的なターゲット指定**：`back(@reservation)` のように、どのセッションまで戻るかを明示するオプション。複数のモーダルやセッションが入れ子になった場合、戻り先の意図を明確にできる。
4. **transition verb の引数に条件ラベルを付ける**：`push(X, @S) [条件ラベル]` のように、「この遷移はいつ起こるか」を行動の直後に注記できると、実装の分岐がより明示的になる。
5. **flow ライブラリ化**：多ステップフローのパターン（「各ステップで前へ戻れる」「完了で一括終了」）が共通なので、これを component の shorthand やテンプレートとして提供できると、書き量が減る。
