# reservation プローブ採点（被験者: haiku — モデル勾配測定 / SPEC のみ / CLI 不可）

CLI check: pass（診断ゼロ）。SPEC 照合レビュー: sonnet 組と遜色ない読解。ただし gate の解釈で spec の字義から外れた（曖昧さの実証として価値が高い）。

## どう正解したか

- present(予約フロー, @reservation) → dismiss(@reservation) の対応、モーダル整合は正確。
- ウィザードを **1 component + variant 連鎖（goto(##次)）** で実装 — banking（別 component + push 連鎖）と別解。「フロー内で 1 つずつ戻れる」も goto(##前) で表現（back スタックでなく状態遷移として）。どちらも合法で、variant / component の使い分け指針が spec に無いことの実証。本人確信度「低」を申告。
- 「満席の日は選べない」を、日付 component の variant 別要素 + `タップ(日付.選択対象?)` / `タップ(日付.キャンセル待ち登録?)` の 2 行で表現 — 創造的で意図が明快な回避。

## 検出された spec の穴（sonnet 組と独立に到達したもの含む）

1. **gate を「参照先 component の現在 variant に要素が存在するか」の動的判定と解釈** — SPEC の gate は「行動が書かれた variant のスコープ」での静的注記のはずだが、対象が**別 component** のとき「どちら側の variant か」が字義から読めない。静的/動的の線引きが読者に伝わっていない実証。
2. **barrier 内の back() がモード内の前ステップへ戻れるかを読み切れなかった** — 「外へ出ない」だけでは「中では普通に戻れる」ことが伝わらない。
3. **`予約をキャンセルする ; dismiss() ; back()` — transition 2 連続**（3/3 の被験者全員が独立に到達）。

## 改善案の自己申告（アイデア収集）

`[##満席]` のような variant 条件ラベル / back のセッション指定 / ウィザード定型（前へ・次へ）の糖衣 / 遷移への条件注記。

## モデル勾配の所見

haiku でも構文面の誤りはゼロで、確信度の自己申告分布も sonnet と同傾向（frame 木・gate 交差で「中〜低」）。現行 SPEC は基本構文については弱いモデルにも耐えるが、gate・barrier・複合遷移の 3 領域はモデル能力に依らず躓く＝仕様側の問題と切り分けられる。
