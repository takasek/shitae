# ticketing-r3 実装ノート

## 参照した SPEC の節

### 必須（基本理解）
- **two-layer model**（セクション「two-layer model」）
  - component（`#`）と variant（`##`）の2階層構造
  - variant が無い component は「単一 variant だけを持つ」とみなす

- **transition verb**（セクション「transition verb」）
  - コア4語：`push` / `back` / `goto` / `exit`
  - compound verb 3語：`present` / `dismiss` / `switch`
  - フレーム木の操作モデル

- **セッション（`@S`）**（セクション「セッション」）
  - `push(X, @S)` / `present(X, @S)` で開始
  - `exit(@S)` / `dismiss(@S)` で破棄
  - begin 地点へ戻る（出口固定の慣用句：`exit(@S) ; push(固定先)`）

- **singleton component**（セクション「singleton component」）
  - `#!` で定義。document 内で単一インスタンス
  - variant 状態を全所在で共有
  - 用途：一度受け取ったクーポンはどこから開いても取得済

- **オーバーレイ（show / hide）**（セクション「オーバーレイ」）
  - フレーム木と別系統
  - どの画面でも常時表示できる component
  - `show(X)` で掲示、`hide(X)` で掲示解除
  - 掲示中への再 `show` は表示 variant を上書き

- **collection（`*`）**（セクション「collection」）
  - 宣言側：`*座席`（複数を示す）
  - 参照側：`座席` なら1インスタンス、`*座席` なら集合全体

### 重要（レイアウト・インタラクション）
- **操作は variant に属する**（セクション「操作は variant に属する」）
  - 「いつ何ができるか」を variant で表す
  - 条件式は評価しない。存在は構造的 presence で判定

- **presence gate（`?`）**
  - 行動対象への後置：`行動(対象?)`
  - 「対象が実効 body に存在する時だけ有効」
  - opt-in：既定は always-on

- **condition label**（セクション「未定・分岐」）
  - `[ラベル]` で分岐を注記
  - 評価しない。どちら転ぶかは実装で決める

- **結果の逐次適用**
  - 複数の result は左から順に適用
  - 後続の result は直前の遷移が変えた状態に対して効く
  - 例：`exit(@S) ; push(固定先)`

- **element reference（`.`）と inline component**
  - `.` で1段の要素参照
  - `{...}` で その場限りの component（要素のみ）

## 迷った点と確信度

### 1. 座席状態の variant 制御【確信度：中】
**迷い**: 要件では「座席は複数あり、空席/売切の状態がある」。これを表現する際、各座席インスタンスの variant を SPEC 上でどう記述するか。

**実装内容**: 
```
# 座席選択
*座席

# 座席
## 空席
座席番号
価格
> タップ(座席) -> 座席を選択する

## 売切
座席番号
価格
売切マーク
```

**理解**: component の variant は「定義時」に明示する。実行時に「どの座席が空席で、どの座席が売切か」は SPEC では指定しない。simulator や実装が外部データ（APIレスポンスなど）から各インスタンスの variant を決める。「座席の variant は shitae の外で決まる」という整理は「condition label」「presence gate での未定義 component」の扱いと一貫している。

### 2. Presence gate の挙動【確信度：中】
**迷い**: `> タップ(クーポン表示?) -> show(クーポン##未受取)` と書いたとき、「クーポン表示」が存在しないなら、この操作は単に無効になるだけか。それとも UI 上で「タップできない」「表示されない」のような視覚的フィードバックも含むのか。

**理解**: SPEC では「gate は掲示状態は見ない」「presence gate が見るのは『その名前の要素が variant の実効 body にあるか』という構造的な一点だけ」と明記。従って、gate の効き方（無効化 vs 非表示）は実装依存。SPEC はフロー設計のみで、UI の見せ方は含まない。

### 3. 複数座席選択での ミニカート 状態【確信度：中】
**迷い**: 「座席を選択する → show(ミニカート##チケット入り)」を複数回実行した場合、ミニカート の状態はどうなるか。

**理解**: SPEC に「掲示中への再 `show` は表示 variant を上書きする」と明記。各選択で `show()` を重ねても、最終的には最後の `show()` の内容（`##チケット入り`）が見える。チケット数などのデータ更新は SPEC 外。

### 4. 出口固定の冗長性【確信度：高】
**迷い**: 購入フロー内の複数箇所（購入確認、支払い画面など）でキャンセル時に `exit(@checkout) ; push(イベント一覧)` と繰り返し書いている。これを1度だけ書く方法はないか。

**理解**: SPEC では出口固定の慣用句として `exit(@S) ; push(固定先)` を明示的に書くことが想定設計。同じ @S でも入口が複数あれば、その入口ごとに begin 地点が異なるため、@S の begin 地点へ戻るだけでは「出口を固定」できない。每回明示的に出口を指定する冗長性は仕様上意図的。

### 5. 座席削除時のミニカート 表示【確信度：低】
**迷い**: カート画面で「チケット削除」を実行。その後ミニカート は「空」に変わるべきか。

**実装内容**: 明示的に記述していない。削除後は（データ的には削除されるが）ミニカート の variant は明に変更する遷移がない。

**推測**: 
- データ層で「チケット数が 0 になったら ミニカート を hide()」という外部ロジック
- または、「チケット削除」という効果（副作用）が、自動的にミニカート 表示を切り替える
- SPEC では「扱わないもの」に「データ・コンテキスト」が明記されているため、チケット数による条件付き非表示は実装の領分

このような「データの状態に基づく」条件付き表示は SPEC では記法を持たないと理解。

## 書けなかった表現 / 要望

### 1. 条件付き非表示（中優先度）
**要望**: 「チケット数が0なら自動的にミニカート を非表示」のような、データ値に基づく条件付き visibility を SPEC で表現したい。

**代替案**: 
- condition label で「[チケットなし]」と注記したうえで「`hide(ミニカート)`」
- または、explicit に「`チケット削除` → delete ; [チケットなし] hide(ミニカート)」

**意見**: presence gate は「構造的 presence」に限定（要素の有無のみ）という設計は理解。データ値による条件は XState などの状態機械の領分という割り切りは一貫。ただし、シンプルなケース（「リスト空」「カウント0」など）を SPEC で直接表現する軽い記法があれば、ラフ段階の表現力が上がると予想。

### 2. Multiple active overlays の制御（低優先度）
**要望**: 複数の overlay（ミニカート と クーポン通知など）が同時に表示される場合、層の順序・相互作用を SPEC で指定したい。

**代替案**: 自然文で `// ミニカートはクーポン通知の下に表示` と注記

**意見**: SPEC ではレイアウトを扱わない設計なので、この要望は SPEC の意図とは別。実装またはデザインシステムの領分と思われる。

### 3. Singleton の「初回以降は最後の variant」挙動の制御（低優先度）
**要望**: singleton で「受け取ったクーポンはどこから開いても受取済」という要件は実装できた。ただし、「アプリ再起動後は未受取状態に戻す」のような「データの永続化スコープ」を SPEC で指定したい。

**代替案**: 自然文で `// クーポン state はローカルストレージに永続化` と注記

**意見**: SPEC には「フレーム木・セッションの生存は同一プロセス内の意味論。永続化するかどうかは実装の選択」と明記。SPEC 外の要件。

### 4. Presence gate で collection 全体の存在判定（中優先度）
**要望**: `> 座席を選択可能? -> 進む` のように、collection が空でない（要素が1個以上ある）かを判定したい。

**代替案**: `*座席?` と書いても、SPEC では「`*` を剥いた名で判定する」ため、単に `座席` と同じ判定になる。collection 全体の有無は別の記法が必要。

**意見**: SPEC で presence gate は「単一要素の存在」のみ。collection 全体のサイズ・存在を条件にしたい場合は、condition label で `[座席なし] エラー表示` と注記する手段しかない。型安全な言語への発展を見据えると、collection の存在判定も言語機能として組み込まれるべき可能性があり。

## 実装時の判断メモ

- **エントリポイント**: イベント一覧（ファイル先頭）
- **セッション戦略**: @checkout で購入フロー全体をひとまとまり
- **Overlay**: ミニカート は singleton（出し入れ繰り返しても状態共有）
- **キャンセルの出口**: 毎回 `push(イベント一覧)` で明示的に固定
- **座席状態**: component 内の variant で表現（実際の所属は実装/simulator 決定）

## 確信度 Summary

| 項目 | 確信度 | 理由 |
|------|--------|------|
| component / variant の基本 | **高** | two-layer model の説明は明確 |
| transition verb（push/back/goto/exit） | **高** | 定義と例が充実 |
| present / compound verb | **中** | barrier の概念は理解したが、複雑な入れ子での挙動は未確認 |
| singleton | **高** | 要件に直結し、SPEC での説明も明確 |
| overlay | **中** | 基本は明確だが、複数 overlay 間の相互作用（SPEC 外）が不確定 |
| presence gate | **中** | 記法と目的は理解したが、実装での効き方は記述なし |
| フレーム木（単純なケース） | **高** | 単一セッション、単一 back では直感的 |
| フレーム木（複雑） | **低** | switch の兄弟規則、exit の遠隔破棄、nested session での @S 解決 |
| condition label と逐次適用 | **中** | 基本は理解。複雑な分岐での適用順序は要確認 |

## 参考：書いたコードの主な構成

```
# イベント一覧          ← エントリポイント
# イベント詳細
# 座席選択
# 座席                   ← variant: 空席/売切
# 購入確認              ← @checkout セッション開始
# 支払い画面            ← @checkout 継続
# 完了画面              ← @checkout 終了
# カート画面
#! クーポン             ← singleton（variant 共有）
#! ミニカート           ← overlay 専用（どの画面でも常時可）
```

Overlay 2 つ（ミニカート、クーポン通知）と singleton 1 つ（クーポン本体）は別実体。ミニカートをタップすればカート画面へ。クーポン通知をタップすればクーポンモーダルへ。
