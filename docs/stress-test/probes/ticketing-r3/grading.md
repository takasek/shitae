# ticketing-r3 採点（2026-07-13。被験者: haiku、SPEC のみ参照）

CLI check: **診断ゼロ**。だが意味論レベルの誤りが 4 系統 — checker の寛容さが全て素通しする（ラフさの設計どおりだが、誤読の証拠として重要）。

## ❌ 意味論エラー（診断ゼロで潜伏）

### G1: `@checkout` の多重 begin — セッションを「メンバーシップタグ」と誤読【最重要】

購入確認→支払い→完了の各段で毎回 `push(X, @checkout)` と書いた（L46, L70, L78）。notes L173 に「支払い画面 ← @checkout **継続**」と明文化——**同名 @S を再 begin すれば同じセッションが継続する**という誤概念。実際は push(@S) ごとに新フレーム・新 begin が入れ子になり、`exit(@checkout)` は LIFO で直近 1 つしか畳まない。完了画面の `exit(@checkout) ; push(イベント一覧)` は支払い画面のフレームへ戻ってから積むだけで、座席選択〜購入確認のスタックが残存——要件「支払い完了後必ずホームへ」は不成立。

SPEC は「セッションは遷移に紐つく。同じ画面を別の場所で push すれば別のセッションになる」と書くが、「**同名 @S を続けて begin したときに何が起きるか**（入れ子・LIFO）」を正面から述べる文が無い。読者は「フロー全体に @checkout という名前を付けている」つもりで各遷移にタグ付けした。

### G2: singleton への `show(X##v)` を「表示 variant の選択」と誤読

L37 `タップ(クーポン表示?) -> show(クーポン##未受取)`。クーポンは singleton なので、明示 `##v` は**共有レジストリの書き換え**（ADR-0011 / SPEC「X##v 指定は共有状態の書き換えとして働く」）——取得済みのクーポンをこの導線が**未受取へ巻き戻す**。要件「一度取得したらどこから開いても取得済み」を書き手自身が破壊した。通常 component の `show(X##v)`（表示 variant を選ぶだけ）の意味論を singleton に外挿した誤読で、oracle S2 の乖離（switch resume の X##v 書換）と同族——**明示 ##v = 状態書換、という singleton の非対称は読者の予測を裏切る**。正解は `show(クーポン)`（共有現在値がそのまま出る）。

### G3: overlay 掲示中 component 内の裸 `goto(##受取済)`

L106（クーポン ## 未受取の取得ボタン）。掲示中 overlay の interaction の裸 `##v` は**アクティブ画面側**に解決される（SPEC「variant の参照は必ず ##」L341・オーバーレイ節）——クーポンの variant は変わらず、アクティブ画面が存在しない variant へ書き換わる（実行時 W105 相当）。SPEC が明記する「正攻法は自己再 show」を読者は見つけられなかった。ただし皮肉にも クーポン は singleton なので、正攻法 `show(クーポン##受取済)` は共有書換として正しく機能したはず。

### G4: 飾り `?`（未定義参照への presence gate）×3

`タップ(クーポン表示?)` `タップ(クーポン適用?)` `タップ(チケット削除?)` — いずれも gate 対象が要素行のどの名前とも一致しない（「クーポン状況表示」要素 vs「クーポン表示」対象、等）→ 全て判定不能 → always-on の飾り。`?` を「条件付きっぽさ」の注記として使う回避行動。gate を機能させるには対象名を要素行と一致させる必要がある、が伝わっていない。

## ✅ 正しく書けたもの

- 座席の 空席/売切 を variant で分け、空席にだけ interaction を置く（「操作は variant に属する」の正統イディオム）
