# video.shitae 執筆メモ

## (1) 参照した SPEC の節

- 「two-layer model」（component と variant の二層構造、共通部分の継承規則）
- 「document common（最初の `#` より前）」
- 「記号一覧（これで全部）」
- 「文法（EBNF 風）」
- 「操作は variant に属する（条件式を持たない理由）」およびその下位節「2 種類の『ガード的なもの』」（presence gate `?` と condition label `[...]`）
- 「transition verb」全体（push/goto と行き先、variant の参照は必ず `##`、initial variant とエントリポイント、セッション `@S`、フレーム木、switch、present/dismiss、戻り先が無いとき）
- 「行動（インタラクションの左辺）」
- 「component に特権はない」
- 「inline component とグルーピング」
- 「collection（`*`）」
- 「未定・分岐」
- 「扱わないもの（意図的に持たない）」

## (2) 仕様が曖昧・不明瞭と感じた点

**PiP（小窓）のようなオーバーレイ表現。**
「フレーム木」節に「アクティブなフレームは常に 1 つ」と明記されている。
これは裏を返すと、shitae のナビゲーションモデルは常にどこか 1 画面がアクティブという前提であり、「小窓プレイヤーを再生させたまま、その上でホームや作品詳細を自由に行き来する」という、2 つの独立した表示が同時にアクティブであるような状態を表す語彙がない。
push/present/switch のどれも「今どこにいるか」を 1 つに定める遷移であり、「今どこにいてもよいが、それとは別に常に見えている要素がある」という重なりの概念とは軸が違うと感じた。
今回は document 共通のインタラクション（`#` より前）としてプレイヤー小窓へのタップ・閉じるを近似記述したが、これは「PiP が有効な間だけ」という条件を表現できておらず、正確ではないと自覚しつつの回避策である。

**presence gate `?` の適用範囲が variant スコープに閉じている点。**
「2 種類の『ガード的なもの』」の記述で `?` は「その variant に対象が存在する時だけ行動が有効」と定義されており、対象は component や `##` variant の中の要素を想定しているように読めた。
今回、小窓化ボタンは `##コントロール表示` variant にしか存在しない要素なので、component common（`##` より前）に置いた `> タップ(小窓化ボタン?) -> goto(プレイヤー小窓)` は spec の想定通りの用法だと判断し、確信を持てた。
一方、document 共通（`#` より前）の階層で `?` を使う場合、そこにはそもそも variant という単位が存在しない（`#` より前は「どの component・どの variant でも」という最上位の共通）。
このレベルで「ある種の状態（PiP 中かどうか）が存在する時だけ」という条件を書きたくなったが、`?` が対応する「対象＝要素」の存在チェックと、「アプリ全体としてある状態にあるかどうか」という条件は種類が違う気がして、結局 `?` は使わずに諦めた（詳細は (4)）。

**collection（`*`）の順序の扱いが未規定に見える点。**
「collection（`*`）」節には「複数あるという宣言」「1 インスタンスを指す」とはあるが、順序（先頭・末尾・前後関係）について明記が無い。
エピソードリストで「次のエピソード」「最終エピソード」という前後関係を表現する必要があったが、`*エピソード` という collection 宣言だけでは順序を保証している根拠が見当たらず、`[次のエピソードがある]` / `[最終エピソードである]` という condition label（評価しない注記）に頼って自然文で逃げた。
これは意図された使い方だと思うが、「collection に順序があるかどうか」自体は SPEC を読んだだけでは確証が持てなかった。

**同一 component 内で同じ alias 名を持つ複数の inline collection がある場合の参照規則。**
「参照は alias 名（または component 名）で引く」の段落に「同名の要素 alias が複数の variant にまたがって存在しても曖昧にはならない」とあるが、これは variant を跨ぐケースの記述であり、今回のホーム画面のように、同一 component（`# ホーム`）の中に `*ジャンル行: { *作品カード }` と `マイリスト行: { *作品カード }` という 2 つの別々の inline collection が同じ alias 名 `作品カード` を持つケースについては直接の記述が見当たらなかった。
「インスタンス.要素alias」（`ジャンル行.作品カード` / `マイリスト行.作品カード`）で一意に参照できるはずだと解釈して書いたが、SPEC に明記された規則ではなく類推である。

**「プレイヤーはそのまま」で次のエピソードが始まる遷移の表現。**
「行動（インタラクションの左辺）」の「注意」に「右辺に transition verb がなければ副作用（自然文）と解釈される」とある。
エピソード終了で次のエピソードが自動再生される場合、画面（プレイヤー component・variant）自体は変わらないので、`goto` 等の transition verb を使わず「次のエピソードを再生する」という自然文の副作用だけを書いた。
これで合っているはずだが、「画面は変わらないが中身（今何を再生しているか）は変わる」という遷移を transition verb 抜きで表すのが正しい使い方なのか、他に専用の書き方を用意すべきなのか、確信は中程度にとどまる。

## (3) 使った主要構文ごとの確信度

- `#` component 定義、`##` variant 定義: 高。SPEC の「操作は variant に属する」の例（フォロー/フォロー解除）とほぼ同型でマイリスト・ダウンロード状態を書けた。
- 要素行・alias（`名前: 実体`）: 高。
- collection `*`（`*エピソード` `*ジャンル行: { *作品カード }`）: 中。宣言自体の書き方には確信があるが、(2) で書いた通り順序の扱いに確信が持てない。
- inline component `{ }` と `.` 要素参照（`ジャンル行.作品カード`）: 中。書き方は SPEC の例（`フィード.サムネイル`）に忠実だが、同一 component 内の同名 alias 複数使用について規則の裏付けが弱い。
- インタラクション行 `>` / `->` / `;` / 継続行: 高。
- condition label `[...]`（次のエピソード分岐）: 高。SPEC の「未定・分岐」の例とほぼ同型。
- presence gate `?`（`小窓化ボタン?`）: 中〜高。component common での用法は SPEC の説明の典型例そのものだが、document 共通レベルでの適用可否は判断できず未使用に留めた。
- transition verb `push` / `goto` / `back(X)`: 高。特に `back(作品詳細)` で「エピソードを何話再生してもプレイヤーは goto で中身が変わるだけなのでスタックは 1 段のまま」という前提を作れたのは、フレーム木の説明を読んで納得できたため。
- `present` / `dismiss` / `switch` / `@セッション`: 未使用。今回の要件にモーダルやタブ・ログインのような「モードの出入り」に相当する概念が無かったため使う機会がなかった。理解はしたが実地の確信度は測れていない。
- document common（`#` より前のインタラクション）: 低〜中。SPEC の deep link 例（プッシュ通知タップ）を手本にしたが、今回のように「常時視覚的に存在するオーバーレイ」を表す用途は想定外の使い方だと感じている。

## (4) 書けなかった・回避した表現

**PiP 中に他画面を自由に行き来できる、という要件。**
最も素直に書けなかった箇所。
`# プレイヤー小窓` という component を定義し、そこへの遷移・そこからの遷移（タップで全画面プレイヤーに戻る、×で再生終了）は document 共通のインタラクションとして書いたが、これは「PiP になった後、ユーザーがホーム・作品詳細のどちらへ行っても小窓が画面上に重なって見え続ける」という状態そのものを表現できていない。
`goto(プレイヤー小窓)` と書いた時点で、フレームの最上段は「プレイヤー小窓」という 1 画面に置き換わってしまい、そこからホームや作品詳細へ「自由に行き来」する動線を同時に持たせる書き方が見つからなかった。
欲しかった記法は、たとえば「特定の component をアクティブフレームとは独立した最前面レイヤーとして掲示し続ける」ようなオーバーレイ宣言（画面遷移とは別軸の、常時提示のフラグのようなもの）。
`present`（モードに入る）に近いが、`present` は「戻るときはそのモードごと終える」独立フレームであり、「他のナビゲーションと並行して見え続ける浮遊要素」とは性質が違うため転用できなかった。

**PiP 中でもエピソード終了時に自動で次のエピソードが始まる、という要件。**
`# プレイヤー小窓` は最小限（閉じるボタンのみ）しか定義しておらず、全画面プレイヤーに書いた「再生が終わる」の自動遷移ロジックを小窓側には複製していない。
本来は同じロジックが必要なはずだが、PiP 自体の構造が定まらなかったため後回しにした。

**「再生ボタン」を押したときに最初から再生するか続きから再生するかの区別。**
これは shitae の表現力の問題というより要件・仕様側の曖昧さだが、`push(プレイヤー)` は単に「プレイヤーへ遷移する」としか書けず、「どのエピソードの、どの位置から」という情報は shitae の関心の外（データ・状態の保持は「扱わないもの」に明記）なので、自然文で補うことも省いた。
気になったので記録だけ残す。

## (5) その他 DSL への感想・改善案

- variant を「見えるバリエーションの列挙」として使う設計は、ダウンロード状態やマイリスト状態のような「on/off が UI に表れる」要件と非常に相性がよく、条件式を書かずに済むのは実際に書いていて気持ちがよかった。
- 逆に、今回の PiP のように「複数の画面が同時にアクティブに見える」ケースは、component/variant/frame という「常に 1 つがアクティブ」という前提の外側にあり、shitae の一番弱い面だと感じた。
  設計原則 2「専用記法を増やさない」に照らせば「自然文で書け」ということになるのだろうが、遷移グラフとしての構造を諦めて全部自然文コメントに逃がすことになり、shitae で描く旨みが薄れる。
  もし対応するなら、無理に transition verb 体系を拡張するのではなく、「この component は今アクティブなフレームと独立して表示され続ける」という程度の軽い注記記法（评価しない、图示ツールへのヒント程度のもの）があると、今回のような『小窓』『通知バナー』『トースト』のような要件を無理なく扱えそうに思う。
- `back(X)` で「間に何段積まれていても X まで戻る」という挙動は、実務でよくある「深く潜っても『ホームへ』で一気に戻る」を過不足なく書けて良かった。
  `exit(@S)` と役割が近いように最初感じたが、「セッション（まとめて破棄する期間）」と「単に画面スタックを遡る」が別概念だと理解してからは使い分けに迷わなくなった。
- SPEC 全体を通して、「フォロー/フォロー解除」の例が繰り返し参照実装のように機能しており、今回のマイリストトグルやダウンロード状態遷移もほぼこの型をなぞるだけで書けた。
  型が 1 つあるだけで新規ユーザーの学習コストがかなり下がる実感があった。
