# banking.shitae 制作メモ

## (1) 参照した SPEC の節

`docs/SPEC.md` のみを読んで書いた。特に参照した節は以下。

- 「two-layer model」「document common」— component / variant の階層と、ファイル先頭より前に置く document 共通インタラクションの用途（deep link・プッシュ通知・セッション切れによる強制ログアウト）。セッション切れの例がそのまま今回の要件と一致していたため、ほぼそのまま流用した。
- 「文法（EBNF 風）」— element-line / interaction-line / result-list の正確な形。特に `[ラベル]` が次のラベルまでの複数 result に掛かる、という規則。
- 「transition verb」全体、特に「push / goto と行き先」「セッション（`@S`）」「セッションと back barrier は直交」「present / dismiss は compound verb」「フレーム木」「戻り先が無いとき」。ログイン後フローと削除確認モーダルの例をほぼそのまま参考にした。
- 「操作は variant に属する」「2 種類のガード的なもの」— パスコード再試行回数の表現をどうするか判断する際に参照した。
- 「collection（`*`）」「inline component とグルーピング」— 取引履歴・宛先候補の複数性の表現。
- 「扱わないもの」— データ／コンテキストを持たない、という制約を確認するために参照した。

## (2) 仕様が曖昧・不明瞭と感じた点

- **「document common」節（52〜67行）**: `goto(ログイン)` の例がセッション切れの用途としてそのまま載っており、今回の「5分無操作でログインへ強制的に戻す」要件に一見ぴったり対応する。しかし「フレーム木」節（286〜297行）では `goto(X)` は「現在フレームのスタックを操作する」とあり、操作対象は現在アクティブなフレームのスタック（積まれた画面の並び）に限定されるように読める。document common のインタラクションがどのフレームの深さで発火しても、`goto(ログイン)` は現在フレームの最上段を置き換えるだけで、祖先フレーム（`@loggedIn` や `@送金` のような、途中で `present`/`push,@S` によって作られた親フレーム）が破棄されずに木の中に残ってしまうのか、それとも document common な遷移は特別にルートまで巻き戻す扱いなのか、SPEC に明記が無い。今回の要件は「タブや送金途中の状態も全て破棄」と明言しているため、フレーム木を跨いで完全リセットしてほしいが、SPEC の文面からは「現在フレームだけの置き換え」と読める余地が残る。自分の解釈としては、SPEC 記載の例をそのまま信じて `goto(ログイン)` を採用したが、フレーム木の深い場所（生体認証確認モーダルの中など）で発火した場合に本当に全消去になるかは自信が持てない。
- **「present / dismiss は compound verb」節（323〜350行）と「戻り先が無いとき」節（352〜354行）**: `exit(@S)` は「begin 地点」へ戻る、と定義されている。今回の要件では「送金ウィザードの中止」「完了画面のホームへ」は常に「ホームに戻る」と書かれているが、取引詳細から `present(金額入力, @送金)` で始めたウィザードの場合、begin 地点はホームではなく取引詳細になる。`exit(@S)` の意味論に忠実に従うなら、この経路で中止・完了した場合は取引詳細に戻ることになり、要件文の「ホームに戻る」と字面上ズレる。SPEC には「session は遷移に紐づく」「begin した地点に戻る」としか書かれておらず、任意の固定画面へ戻す（begin 地点を上書きする）記法は無いため、これは自分の設計判断で解消せざるを得なかった。該当節：261〜271行（セッション）、352〜354行（戻り先が無いとき）。
- **result-list の逐次実行順序（143〜150行）**: `[成功] 送金を実行する ; dismiss() ; push(完了)` のように、1 つのラベルの下に副作用・`dismiss()`・`push()` を並べた場合、`dismiss()` でアクティブフレームが変わった「後」に `push(完了)` が新しいアクティブフレームに対して効くのか、SPEC の意味論の記述（143〜150行、286行以降のフレーム木）は分岐（どのラベルでどの結果か）の説明が中心で、同一ラベル内の複数 result が逐次実行され、かつ前の result が状態を変えた場合に後続がその変化後の状態に対して効く、ということを明言していない。動作としては自然だが、明記が無いため確信が持てない。

## (3) 使った主要構文ごとの確信度

- `#` / `##`（component・variant 定義）: 高。two-layer model の説明が明快で、パスコード再試行回数を `##パスコード1`〜`##パスコード3` の variant として表現する判断も「状態は variant で表す」という設計原則6に沿っていると考えている。
- `>` インタラクション行・`->`・`;`・継続行での分岐（`[成功]`/`[失敗]`）: 高。「未定・分岐」節の例をほぼそのまま踏襲できた。
- `push` / `back` / `goto`: 高。EBNF と「push / goto と行き先」節の説明が具体的で、素直に書けた。
- `present` / `@S` セッション / `exit(@S)`: 中。「ログイン後フロー」の例と同型に書けた点は確信が持てるが、(2) で書いた「begin 地点」の扱いや、ネストしたフレームでの `goto` の効き方については確信が持てない。
- `dismiss()`（無名セッション）: 中。「直近の無名セッション」という規則自体は明快だが、`present(生体認証確認)` のような小さな確認ダイアログにも同じ機構を使ってよいか（barrier ありの compound verb をダイアログ程度の粒度に使うのは意図された用法か）は、SPEC の「present は見せ方を問わない」という記述（334行）から妥当と判断したものの、感触は中程度。
- `*`（collection）: 高。「複数あるという宣言、参照すると1インスタンスを指す」という規則が明快で `*取引` `*宛先候補` はそのまま書けた。
- document common（ファイル先頭より前のインタラクション）: 中。書き方自体は SPEC の例と同型で高い確信があるが、(2) で書いた通り効果範囲（フレーム木のどこまで巻き戻るか）に不安が残る。

## (4) 諦めた・回避した表現、欲しかった記法

- **「取引詳細から始めたウィザードは中止・完了で取引詳細ではなく必ずホームへ戻る」という要件の字面**は、素直には書けなかった。`exit(@S)` は begin 地点にしか戻れず、任意の固定画面を戻り先に指定する記法が無いため、`present(金額入力, @送金)` を取引詳細から呼んだ場合は begin 地点である取引詳細に戻る、という shitae の素直な帰結をそのまま採用した。要件通り常にホームへ戻したいなら、`中止`/`ホームへ` の行き先だけを `goto(ホーム)` に差し替える手もあったが、それだと `exit` が持つ「子孫フレームごと破棄する」保証（送金ウィザードの途中状態を全部消す）を失う。両立させる記法（「begin 地点を上書きして戻る／指定した画面へ戻りつつ子孫を全部破棄する」）が SPEC には無く、諦めて exit の素直な意味論を優先した。あれば欲しかったのは、`exit(@S, 戻り先)` のように戻り先を明示的に上書きできる記法。
- **「金額入力に同じ宛先が選択済みの状態で入る」**は、shitae がデータ／コンテキストを持たないと明言している（「扱わないもの」節）ため、構造的には表現できなかった。`金額入力` component の要素行に「宛先」という要素を置くところまでは書けるが、そこに実際にどの宛先の値が入るかは自然文注記にすらしておらず、単に同じ要素行を経路によらず共有するだけに留めた。フォーム値の引き継ぎは実装の関心として完全に手放した形。
- **5分無操作によるセッション切れが「タブや送金途中の状態も全て破棄」する**という要件も、(2) で書いた通りフレーム木を跨いだ全消去が `goto(ログイン)` の意味論として保証されているか確信が持てないまま採用した。もし保証されないなら、確実に全部破棄する記法（ルートまで一気に戻る `exit` 相当）が欲しい。

## (5) その他 DSL への感想・改善案

- 「行動は自由な自然文、右辺の transition verb はコア4語＋compound verb3語のみ」という非対称設計は、ラフスケッチとして書く分には迷いが少なく、書いていて心地よかった。特に「未定・分岐」節の `[成功]`/`[失敗]` 継続行の書き方は、生体認証の二段構え（初回＋再確認ダイアログ）を書くのにちょうど良い粒度だった。
- 一方で、今回のように「複数の入口から同じウィザードに入り、出口は共通にしたいが begin 地点は入口ごとに違う」という要件は、`push`/`present`＋`@S` の begin-地点モデルだけでは表現しきれず、設計判断で妥協するしかなかった。ラフスケッチの段階でこの手のフロー（ウィザードの複数入口）はよくある気がするので、begin 地点を上書きできる小さな記法があると、状態機械に「降りる」までの守備範囲がもう少し広がるのではないか。
- フレーム木・セッション・barrier の概念は強力だが、SPEC 内の説明はやや実装寄り（内部モデルの詳細な走査規則）で、初見では「結局、自分が書いた `goto`/`exit` が今の画面のどこまで影響するか」を都度フレーム木を脳内シミュレーションしないと確信が持てなかった。`push`/`goto`/`back`/`exit`/`present`/`dismiss`/`switch` それぞれについて、「今回操作した具体例でフレーム木がどう変化するか」を図示した最小サンプルが SPEC 内にあると、初めて書くときの不安がかなり減ると思う。
- variant を「パスコード再試行回数」のような一時的なカウンタ的状態に使ってよいものか、最初は少し迷った。「扱わないもの」でデータ・コンテキストは明示的に除外されている一方、「状態は variant で表す」という原則6もあるため、カウンタ的な情報でも見た目・操作の可否が variant ごとに変わるなら variant 側に寄せてよい、という整理で書いたが、この線引き（何が variant で何がデータか）についての一般的な指針が SPEC にもう少しあると助かる。
