# fitness-r4 notes

## 参照した SPEC 節

- 「two-layer model」：component と variant の定義
- 「singleton component（`#!`）」：ホームのエネルギー状態共有、バッジの獲得状態共有
- 「transition verb」：push, back, goto, exit, dismiss, switch
- 「オーバーレイ（show / hide）」：ミニ進行バー、バッジモーダルの常時掲示
- 「セッション（`@S`）」：ワークアウトフロー全体の管理（`@workout`）
- 「switch（中断と復帰）」：ホーム・ワークアウト一覧・設定のタブ切り替え
- 「present / dismiss は compound verb」：ホームへのタブ群entry と中断時の dismiss
- 「未定・分岐」：初回達成 vs 2回目以降の分岐

## 曖昧だと感じた点

1. **「時間経過でエネルギーが回復したら」の機構**
   - ホーム画面を開いていない間に回復が起きることもある、という要件から、ホームを singleton にして `set(ホーム##通常)` で variant を切り替えることにした。しかし「時間経過」自体は shitae では扱わず、外部（タイマー・OS スケジューラ等）が管理するため、どのタイミングで `set` が呼ばれるかは実装側の判断。SPEC に明記がないため、「外部イベント」として document common に書いた。

2. **初回達成判定の場所**
   - 「初回達成時にバッジ獲得の演出モーダルが出る」という要件を、結果画面の分岐（`[初回達成] ... [2回目以降] ...`）で表現した。初回判定ロジック自体（「このワークアウトは初めてか」）は shitae には書けず、実装に任せる。

3. **ミニ進行バーの進捗値表示**
   - プログレスバーの進捗（0-100%）は実装で管理される値のため、shitae には「プログレスバー」という要素だけを置いた。実際の進捗数値の更新機構は扱わない。

4. **エネルギー消費のタイミング**
   - 「ワークアウトを完了するとエネルギーを消費する」→ 結果画面から戻る際に `set(ホーム##エネルギー切れ)` で状態を切り替え。しかし「どのワークアウトかによってエネルギー消費量が異なる」など、消費量の計算や在庫管理は shitae の外。

5. **タブ群の anchor 設定**
   - ホームを singleton にしつつタブ anchor として機能させるため、起動→`present(ホーム, @tabHome)`の形にした。SPEC の「タブの慣用句」に従い、ホームタブだけが switch 製でなく、他タブが兄弟フレームになる形を意図した。

## 設計判断の確信度

| 判断 | 確信度 | 理由 |
|------|--------|------|
| ホームを singleton（`#!`）化 | **高** | エネルギー状態を全所在で共有する必要があり、singleton の `set` で non-navigational な状態変更ができるため。|
| ミニ進行バーを singleton + overlay | **高** | 「他の画面に移動しても表示」という要件が、overlay でフレーム木をまたいで掲示することで実現できる。|
| バッジを singleton + overlay | **高** | 「一度獲得したら以後どの画面から見ても獲得済み表示」→ singleton で状態を共有、overlay で常時掲示。|
| ワークアウトセッション（`@workout`）管理 | **高** | ワークアウト実行→結果→ホームへのフロー全体をセッション内で管理し、中断時に `dismiss()` で破棄。|
| タブ切り替えに switch 使用 | **高** | ホーム・ワークアウト一覧・設定を並行文脈として表現。各タブの状態を保持して行き来する。|
| エネルギー回復を document common に置く | **中** | 「ホーム非アクティブ中に回復が起きる」というイベントは、どの画面がアクティブでも起こりうるため document common が自然。ただし「外部イベント」であることを明示的に書く方法がなく、自然文注記に頼っている。|
| 初回達成を condition label `[初回達成]` で分岐 | **中** | SPEC の「未定・分岐」に従い、分岐を condition label で注記。実装で動的に判定されることを前提にしている。|

## 書けなくて諦めた表現・欲しかった記法

1. **プログレス値（進捗率）の表現**
   - ミニ進行バーのプログレスバーが「現在のワークアウト進捗」を反映しているはずだが、shitae ではデータ値を扱わないため「プログレスバー」という要素だけを書く。実装では、このオーバーレイが掲示されている間に動的に進捗数値を更新する。この「動的データの流れ」を言語レベルで表現したかった。

2. **タイマー・時間経過イベント**
   - エネルギー回復は「X 秒後に」「特定時刻に」といった時間条件で起こるはずだが、shitae には時間条件の記法がない。`> エネルギーが回復する` という自然文で書くしかない。`> [5分経過] ...` のような時間ラベルがあれば、より明確に書けたかもしれない。

3. **外部イベント vs ユーザー操作の区別**
   - プッシュ通知・時間経過・バックグラウンド処理など、外部で起きるイベントと、タップ・スワイプなどユーザー操作を区別する記法がない。現在は両方とも「行動（左辺）」で書くため、shitae の読者は文脈で判断する必要がある。

4. **遠隔状態変更の因果関係**
   - 「結果画面から戻る際に `set(ホーム##エネルギー切れ)` を実行する」と書く際、「この set はなぜ必要か」という背景（ワークアウト完了によるエネルギー消費）が shitae には記述されない。自然文コメント（`// ワークアウト完了で消費`）で補うしかない。より構造化された「原因→効果」の記法があれば、設計思想が明確になると考える。

5. **Collection への多様なアクセスパターン**
   - ワークアウトカードが複数（collection）ある場合、「スクロール時の読み込み」「カード個別タップ」など複数の操作が考えられるが、現在の記法では `*ワークアウトカード` に対するすべての操作を明示的に書く必要がある。CSS selector のような「スコープ指定」があれば、より簡潔に書けたかもしれない。

6. **Variant 間の遷移ガード**
   - ホームの「通常」と「エネルギー切れ」の variant にいくつかの要素が重複している（タブバーなど）。この共通部分を variant よりも上に抽出する仕組みはあるが、「どの variant からどの variant への遷移を許可するか」という状態機械的な制約は記述できない。`set(ホーム##通常)` は常に可能だが、実装では「実際にエネルギーが回復した」という確認が入る。

## 備考

- ワークアウトデータ（実行時間、消費エネルギー、成績等）は component に element として置くが、その具体値は実装で管理される。
- エネルギーの消費量・回復スケジュール（秒単位の計算）は shitae の外。
- ホーム画面が singleton になることで、複数の場所から異なるタイミングで状態が書き変わる可能性がある（結果画面での `set(ホーム##エネルギー切れ)`、外部タイマーでの `set(ホーム##通常)` 等）。concurrent write や race condition は実装レイヤーで対処する設計になっている。
