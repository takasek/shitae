## 意味論の誤り

### G1: `@workout` の生存中再 begin（r3 ticketing G1 と同一誤読の**再発**）

L15 `push(ワークアウト実行, @workout)` → L33 `push(結果, @workout)`。notes は確信度**高**で「フロー全体をセッション内で管理」と申告 — セッションを『フローのメンバーシップタグ』とみなす誤読が、**別モデル・別課題・SPEC 正面説明追加後（ADR-0016 B4）にも再発**。R005 は runtime 警告なので `check` では見えず、書き手は執筆時に気づけない。R005 の静的近似（同一 result-list・遷移グラフ上の begin 済み @S への push を checker/lint で指摘）を検討する材料。

### G2: セッション破棄を `dismiss()` と誤読（確信度高で乖離）

L32 中断ボタン `dismiss() ; hide(ミニ進行バー) ; back()`。@workout は push-begin（barrier なし・名前つき）なので正解は `exit(@workout)`。実測: dismiss() は畳む対象が無く **R002 no-op**、続く back() が偶然 1 段戻してホームに着く（実行画面がフロー深部なら要件「フロー全体破棄」は壊れる）。notes は確信度高で「中断時に dismiss() で破棄」— **確信度高の乖離はオラクル基準で最も危険**。SPEC の dismiss 説明（「直近のモーダルを閉じる／@S を破棄」）から「無名 dismiss は present 系にしか効かない」を読者が引けていない。

### G3: overlay をフレームと混同 — show で出したモーダルを `dismiss()` で閉じる

L39 `show(バッジモーダル##獲得)` で掲示 → L49 `set(バッジモーダル##獲得済み) ; dismiss()`。overlay はフレームでなく `hide` でしか消えない（SPEC 明記）— dismiss() では消えず画面に残り続ける。ticketing-r3 G3（overlay とフレーム木の混同）と同族。「モーダル」という語感が present/dismiss を誘発する — 演出モーダルを overlay で作ると閉じ方を間違える、という繰り返しパターン。

### G4: 掲示状態を variant で二重管理（`##未表示` / `##非表示` の発明）

バッジモーダルとミニ進行バーに「掲示されていない」ことを表す variant を用意した（中身は E010 になったコメントのみ）。掲示/非掲示はオーバーレイ集合の管轄で variant は見た目 — 「別軸」（SPEC オーバーレイ節）が伝わっていない。

### 積み残し G2（r3）の再観測: singleton への `show(X##v)`

L15/L27 `show(ミニ進行バー##実行中)`・L39 `show(バッジモーダル##獲得)` — singleton への明示 ##v show を「表示手段」として使用。今回は意図（書換＋掲示）と一致し**巻き戻し実害なし**。ただし G3/G4 と合わせ、show / set / variant の役割分担の混乱は持続。lint 化判断の材料: 同型使用は再発、実害形（巻き戻し）は再発せず。
