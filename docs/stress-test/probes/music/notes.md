# notes: music.shitae

## 1. 参照した SPEC の節

`docs/SPEC.md` のみを読んで書いた（他ファイルは未参照）。実際に参照した節は次の通り。

- 「two-layer model」（component と variant、共通部分が先・固有部分が後という構造）
- 「document common（最初の `#` より前）」（全 component 共通の要素・インタラクション）
- 「記号一覧（これで全部）」（`#` `##` `>` `*` `名前: 実体` `{}` `.` `->` `;` `[]` `?` `"..."` `@` `::` `//` の一覧）
- 「文法（EBNF 風）」全体、特に `element-line` / `interaction-line` / `result-list` / `nav-target` / `session`
- 「操作は variant に属する」「2種類のガード的なもの」「variant はインスタンスごとに独立」
- 「transition verb」全体（push/back/goto/exit、present/dismiss/switch、セッション、back barrier、フレーム木、switch（中断と復帰）、「タブの慣用句」の例、present/dismiss は compound verb、戻り先が無いとき、セッションの mismatch）
- 「行動（インタラクションの左辺）」（対象の有無、transition verb を書き忘れると副作用扱いになる注意書き）
- 「component に特権はない」
- 「inline component とグルーピング」
- 「モジュール化（名前空間）」（今回は単一ファイルなので未使用）
- 「collection（`*`）」
- 「未定・分岐」
- 「扱わないもの（意図的に持たない）」（データ／コンテキストを持たないという宣言。ミニプレイヤーの可視条件が書けなかった根拠）

## 2. 仕様が曖昧・不明瞭と感じた点

**(a) document common に「一部の component だけ除外する」記法が無い（該当節: two-layer model / document common）。**
ミニプレイヤーを document common に置くと、全 component に一律で重ねられる。実際のアプリなら「再生画面（Now Playing）自身の上にはミニプレイヤーを重ねて表示したくない」はずだが、そのための除外構文が見当たらなかった。解釈: SPEC の設計原則2「専用記法を増やさない、書けないものは自然文に開く」に従い、除外はできないまま含め、コメントで注記するに留めた。

**(b) bare name が既存 component 名と一致したときの解決規則が明言されていない（該当節: 記号一覧「参照は alias 名（または component 名）で引く」、EBNF の `ref = name`）。**
要素行に書いた bare name がたまたま別の `#` 定義済み component と同名だと、その component への埋め込み参照として解決されるのか、単なる未定義ラベルとして扱われるのかが本文からは断定できなかった。今回タブバーのボタンを最初「ホーム」「検索」「ライブラリ」と名付けようとしたが、これは画面 component 名「ホーム」「検索」「ライブラリ」と完全に一致してしまう。解釈: 名前空間はドキュメント全体でフラットで、一致すれば常にその component への参照になると仮定し、衝突を避けるためボタンラベルを「ホームタブ」「検索タブ」「ライブラリタブ」に変更して回避した。

**(c) document common からの forward reference が許されるか不明（該当節: 文法 `document = { import }, document-common, { component }`）。**
document common は文法上「最初の `#` より前」に固定されるため、その中で参照した `ミニプレイヤー` component は、ファイル中でそれより後ろで定義することになる。EBNF は定義順を要求していないように見えるが、明記はされていない。解釈: 前方参照は許されると仮定し、`# ミニプレイヤー` をファイル末尾に置いた。

**(d) 1 つの result-list に transition verb を複数並べたときの実行順序の意味論が明記されていない（該当節: 「行動」節、EBNF の `result-list`、「未定・分岐」節）。**
「再生画面から『この曲のアルバムへ』で、再生画面は閉じた上でアルバム詳細に行ける」を表すのに `exit(@nowPlaying) ; push(アルバム詳細)` と書いた。SPEC は「ラベル無しの result は常に成立する」とは書いているが、複数の transition が同一 result-list に並んだときに「順番に両方実行される」のか、他の解釈があるのかは書かれていない。解釈: 上から順に実行され、`exit` で元のフレームに戻ってから `push` でアルバム詳細に進む、という意味で書いた。

**(e) 同名セッションに対する `exit(@S)` と `dismiss(@S)` が完全に同義かどうか不明（該当節: 「present / dismiss は compound verb」「セッション（`@S`）」)。**
「present ⇄ dismiss」「push ⇄ exit」という慣用対応が書かれる一方、SPEC 自身の「ログイン後フロー」の例では `present(ホーム, @loggedIn)` で開始したセッションを `exit(@loggedIn)` で閉じている。解釈: 名前付きセッションを指定する限り `exit` と `dismiss` は同義として扱ってよいと判断し、本ファイルでは `exit` に統一した。

**(f) 「画面をまたいで生き続け、かつ動的に可視/不可視が変わる」要素を表す軸そのものが無い（該当節: two-layer model、「variant はインスタンスごとに独立」、「扱わないもの」）。**
variant は component ごとに閉じた仕組みで、document common には `##`（variant）を持たせられない（EBNF `document-common = single-body` に variant は含まれない）。ミニプレイヤーの「再生中だけ表示」は、そもそも「どの画面にいても共有される 1 つのグローバルな状態」を要求しており、これは variant の設計（インスタンスごとに独立、component に閉じる）とは相容れない。専用記法の欠如というより、shitae がデータ・グローバル状態を持たないという設計原則(「扱わないもの」)に由来する構造的な限界だと理解した。

## 3. 使った主要構文ごとの確信度

- `#` component定義 / `##` variant定義: **高**（フォロー／フォロー解除の例をそのまま踏襲）
- `>` インタラクション行、`->`、`;` による結果列の継続: **高**
- 要素行と `*` collection: **高**
- `push(X)` / `goto(X)` / `goto(##variant)` / `back` 系: **高**（本文の例と直接対応が取れる）
- `present(X, @S)` と named session の開始: **高**（「タブの慣用句」の例をほぼそのまま流用）
- `switch(X, @S)` によるタブ切替: **高**（同上）
- `exit(@S)`（named session の破棄・begin地点への復帰）: **中**（(e)で書いた通り、`dismiss(@S)` との同義性に確信が持てないまま `exit` を選んだ）
- 1 result-list 内で `exit(@S) ; push(X)` と transition を 2 つ並べる書き方: **低**（(d)の通り、この並べ方が意図通り「順に実行」と解釈される保証が本文からは取れなかった）
- document common への component 参照によるグローバル要素の表現（ミニプレイヤー）: **低**（(a)(c)(f)の通り、前方参照の可否・除外の不可・可視性条件を表現できない点、いずれも自信が持てない）
- `.` 要素参照（外部からの上書き）: 今回は不使用（タブバーの挙動は component 自身のデフォルトで足りたため、明示的な上書きが不要だった）。使わなかった判断自体への確信は中。
- `//` コメント: **高**

## 4. 書けなかった・回避した表現、欲しかった記法

- **ミニプレイヤーの「再生中の時だけ表示」という条件付き可視性は書けなかった。** shitae は変数・条件式を持たない設計だと理解しているため、専用記法が無いのは仕様として妥当だと思う一方、実務上「画面をまたいで生き続けるグローバルなオーバーレイが、あるフラグの間だけ現れる」というパターン（ミニプレイヤー、着信バナー、ネットワーク切断バナー等）はUIラフスケッチで頻出しそうなので、何らかの定石があるなら知りたかった。今回は自然文コメントで注記するに留めた。
- **再生画面を閉じてからアルバム詳細へ進む、という「1操作で2遷移」の書き方に自信が持てなかった。** `exit(@nowPlaying) ; push(アルバム詳細)` と書いたが、正しい流儀か分からない。代替として「アルバムへ遷移したら再生画面はその上に積まれたまま残る（closeしない）」という妥協も検討したが、要件「再生画面は閉じる」を削りたくなかったのでこの書き方を選んだ。
- **バックグラウンド再生という「アプリのライフサイクルに関する事実」は、画面でも component でも遷移でもないため、そもそも書ける場所が無かった。** ミニプレイヤー定義の近くにコメントとして注記するにとどめた。
- **検索・ライブラリタブの中身は要件に無い具体を勝手に増やさないよう最小限にした。** これは SPEC の曖昧さではなく、要件を超えて機能を足さないための自制（タブバー＋プレースホルダ要素1個のみ）。

## 5. その他 DSL への感想・改善案

画面遷移そのもの（push/present/switch/back/exit/dismiss の7語）は非常に少ない語彙で必要な表現がほぼ揃っており、特に「フォロー／フォロー解除」のような variant 切替パターンと、タブの「switch は中断と復帰」という一段深い概念は、書いてみると迷いなく当てはまった。一方、今回つまずいたのは次の2点に集約される。

1. 「グローバルに生き続け、条件付きで可視性が変わる」要素（ミニプレイヤー）を表す軸が無い。variant はあくまで component 内に閉じた「見た目の場合分け」であり、document common はあくまで「静的な要素の重ね合わせ」であって、両者を組み合わせても「全画面共通だが、あるグローバルな状態に応じて出たり消えたりする」を表現できなかった。これは意図的な設計上の空白だと思うが、AI_GUIDE 等（今回は読めない制約だったため未確認）に定石が書いてあるなら、SPEC 本文側にも一言リンクがあると初見でも迷わないと思う。
2. bare name の名前解決がドキュメント全体でフラットな namespace になっている点。簡潔さは良いが、タブバーのボタンラベルのように「遷移先の画面名と同じ文字列を使いたくなる」場面で、意図せず「ボタンではなく画面そのものの埋め込み」に化ける危険がある。処理系が「この bare name は既存 component 名と一致しています、component 参照のつもりですか？」と警告してくれると安心して書けると思う。

なお `exit`/`dismiss` の慣用対応（push⇄exit, present⇄dismiss）は「厳密なペアリングの強制」ではなく「典型例」だと本文から読み取ったが、初見では思わず厳密に守らなければと身構えた。「同名セッションを指定する限り exit と dismiss は同義」と一言書いてあると、初学者としては迷わず混在させられると感じた。
