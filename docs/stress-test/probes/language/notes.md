# language.shitae 制作メモ

## (1) 参照した SPEC の節

docs/SPEC.md のみを読んで書いた。参照した主な節は以下。

- 「two-layer model」（component と variant の二層構造、共通部分の継承規則）
- 「document common（最初の `#` より前）」（プッシュ通知のようなどの画面からでも起こる遷移の書き方）
- 「記号一覧」（`#` `##` `>` `*` `alias:` `{}` `.` `##参照` `->` `;` `[]` `?` `"..."` `@` `::` `//` の一覧）
- 「文法（EBNF風）」（interaction-line・result-list・nav-target などの正確な構文）
- 「操作は variant に属する」「2種類のガード的なもの」（presence gate `?` と condition label `[...]` の違い）
- 「transition verb」全体、特に push/goto/back/exit のコア4語、present/dismiss/switch の compound verb、セッション `@S`、back barrier、フレーム木、switch（中断と復帰）、present/dismiss は compound verb、戻り先が無いとき、セッションの mismatch
- 「行動（インタラクションの左辺）」（自然文の行動、括弧の省略規則）
- 「component に特権はない」「inline component とグルーピング」「collection（`*`）」
- 「未定・分岐」（未定の書き方、condition label の意味論、`->` は1行1つ）
- 「扱わないもの」（データ／コンテキスト、履歴スタックの自動解決を持たないという明言）

## (2) 仕様が曖昧・不明瞭と感じた点

**a. `switch` で resume する対象セッションの出自が問われるか不明。**
「switch（中断と復帰）」の節（299〜308行）は `switch(X, @S)` が @S を新規作成するときの規則（兄弟規則、barrier あり）を説明しているが、@S が **`present` で開始されたセッション**であっても `switch` で復帰してよいかは明記が無い。今回はレッスンを `present(選択式問題, @lesson)` で開始し、ホームの「続きから」やプッシュ通知タップでは `switch(選択式問題, @lesson)` / `switch(中断していた問題, @lesson)` で復帰する形にしたが、これが「セッションの mismatch」（356〜358行、push で積んで dismiss で閉じる、のような組み合わせ）に類する扱いになるのか、switch は begin 手段を問わず resume できる汎用の再開語なのか、SPEC からは判断できなかった。エラーにはしない方針は明記されているので実害は無いが、意図した設計かどうかが不安なまま使った。

**b. フレーム木がアプリの再起動をまたいで生存するかが不明。**
「フレーム木」の節は処理系が内部的に持つスタック構造だと説明するが、プロセスの終了・再起動（＝アプリを閉じて再度開く）に対して @S や木がどう振る舞うかへの言及が無い。「扱わないもの」に「データ／コンテキスト」「履歴スタックのデータ構造、戻り先の自動解決」が明記されているため、これは意図的にスコープ外だと解釈したが、それなら「レッスンを中断してアプリを閉じても続きから再開できる」という要件は shitae の対象外の現象を natural text で覆うしかない、という理解でよいのかは確信が持てなかった。

**c. document common は「ファイル全体」単位でしか宣言できず、中間的なグルーピングが無い。**
「document common（最初の `#` より前）」は「全 component に共通」としか書けず、「オンボーディング画面群を除く全画面」のような部分集合への共通化は記法として無い。プッシュ通知のインタラクションはホーム到達後にしか意味を持たないはずだが、document common に置くとオンボーディング中の画面（ようこそ・学習言語選択・レベル診断・目標設定）にも適用範囲が及んでしまう。実害は薄いが、意図と構文が完全には一致していない。

**d. result-list の1エントリに transition を2つ連ねてよいか不明。**
EBNF の `result = [label], (transition | effect)` は1つの result が transition か effect のどちらか一方であることは示すが、result-list の中で「dismiss() の後に別の transition を続ける」ような書き方（例：`dismiss() ; back(設定)`）が構文的に許されるのか、許されても意味論上どちらが最終的な行き先になるのかは記載が無い。今回はこの組み合わせを避け、`present`/`dismiss` の begin 地点の巻き戻り規則だけに頼る設計にした。

**e. condition label をカウンタ（何問目か）の代用に使ってよいか不明。**
「未定・分岐」の condition label は「評価しない注記」「動的な判断だが shitae は評価しない」という説明で、成功／失敗のような**2値の分岐**を想定した例しか無い。今回はレベル診断の「1問目・2問目」「3問目」や、レッスン中の「まだ問題が残っている」「10問終了」のように**回数の経過**を表すために condition label を転用したが、これが condition label の想定用途に収まるのか、それとも「扱わないもの」に挙げられた「データ／コンテキスト（変数）」に踏み込みすぎているのか、判断がつかなかった。

## (3) 使った主要構文ごとの確信度

- `#` component / `##` variant の基本定義：**高**。SPEC の例（フォロー／フォロー済み）にそのまま倣った。
- 要素行・インタラクション行（`>`）の基本、`->` と `;`：**高**。EBNF・例ともに明確だった。
- component common（`##` より前が全variant共通）：**高**。「設定」「学習言語選択」でそのまま使えた。
- document common（`#` より前が全component共通）：**高**（構文としては）／**中**（適用範囲の是非。(2)-c 参照）。
- `push` / `goto` / `back`（不使用）／`exit`：**高**。`back` は今回使わなかった（明示的な戻るボタンを置く要件が無かったため）。
- `present` / `dismiss` とセッション `@S`：**高**。SPEC のログイン後フロー・アカウント削除の例と構造が酷似する箇所（やめますか確認）は特に自信がある。
- `switch`（resume-or-create）：**中**。タブの慣用句を参考にしたが、タブ以外（レッスン中断の再開、通知タップからの再開）への転用は SPEC が明示する用例の外side。(2)-a 参照。
- condition label `[...]` の多分岐（3分岐以上）：**中**。2値の例しか SPEC に無いが、EBNF・意味論の記述上は3つ以上でも問題ない読み。カウンタ代用は (2)-e の通り自信が無い。
- collection `*`：**中**。1箇所（`*選択肢`）だけの使用で、複数形との対応や `inline` との組み合わせは試していない。
- variant を「状態」ではなく「同じ画面を別の呼び出し文脈で使い回す」目的（学習言語選択の オンボーディング／設定変更）に使ったこと：**中**。SPEC の variant 例はすべて「状態の違い」（未フォロー／フォロー済み）で、「呼び出し文脈の違い」に使えるとは明言も否定もされていない。自然な拡張だと判断したが確信は無い。
- presence gate `?`：**不使用**。今回の要件では「未定義の対象への行動を存在条件付きにしたい」場面が無かったため使わなかった。
- inline component `{ }` / module `import`：**不使用**。単一ファイルで完結する規模だったため。

## (4) 書けなかった・回避した表現、欲しかった記法

- **アプリを閉じてから再開したときの「続きから」再開**。shitae は「データ／コンテキスト」「履歴スタックのデータ構造」を明示的に扱わないと宣言しているため、プロセス再起動をまたぐ永続化は言語の対象外だと判断した。`switch(中断していた問題, @lesson)` で resume-or-create の形にはしたが、これは「同一アプリ起動中の中断」をなぞっているだけで、「アプリを完全に閉じて再度開いた場合」に @lesson がまだ有効かどうかは shitae の意味論からは導けない。要件通りには**書けなかった**。欲しかった記法があるとすれば、セッションに「プロセスをまたいで生存する」という1ビットの注記を付けられる何か（例えば `@lesson!` のような）だが、これは設計原則2「専用記法を増やさない」と真っ向から衝突するので、記法よりは「そのように書いてよい」という運用上の合意（AI_GUIDE的なもの）の方が筋が良いかもしれない。
- **10問・3問という反復回数そのもの**。shitae にはループ・カウンタが無いため、「まだ問題が残っている／10問終了」「1問目・2問目に回答／3問目に回答」という condition label で回数の経過を注記する形に**回避した**。実際に何問目かという値そのものは shitae 上のどこにも表現されない。欲しかった記法は無いが、この「N回繰り返す」パターン自体は語学学習・クイズ系アプリで頻出しそうなので、専用記法ではなく「condition label でこう書く」という慣用句をガイド文書に載せてもらえると助かる。
- **選択式問題／入力式問題で共通する「× → やめますか確認」の重複記述**。variant common（`##`より前）や document common はあるが、「2つの component 間だけで挙動を共有する」ための機構（mixin・partial のようなもの）が無いため、同じ1行を2つの component にそのまま複製した。要件は書けたが、DRYではない。
- **ホームの「コースマップ」から特定のレッスンノードを選んで開始する**という、要件文からは示唆されるがテキストでは明示されていない詳細は、要件に明記が無い部分なので意図的に作り込まず、「今日のレッスン」タップのみをレッスン開始の入口として書いた（コースマップは表示要素のみ）。これは shitae の限界ではなく、要件を勝手に膨らませないための私の判断。

## (5) その他 DSL への感想・改善案

記号の数が本当に少なく、SPEC を1回通読しただけで書き始められたのは想定通りだった。variant による「if文を書かずに状態ごとの見た目・操作を列挙する」設計は、フォロー／フォロー済みのような教科書的な例だけでなく、正解／不正解、通知ON／OFFのような今回の要件にもそのまま馴染み、条件式を一切書かずに済んだのは気持ちがよかった。`present`/`exit`/`dismiss` とセッションの組み合わせ（begin地点への巻き戻り、子孫ごと破棄）も「レッスンを×で丸ごと破棄してホームへ」という要件に過不足なくはまり、これが用意されていなければ「レッスン全体をどう畳むか」を自然文で書く羽目になっていたはずで、compound verb の設計は効いていると感じた。

一方で、詰まったところはすべて「データ」に近い領域だった。回数（何問目か）、永続化（アプリ再起動をまたぐ中断）、部分的な共通化（file全体でもcomponent単体でもない中間グループ）の3点は、いずれも「専用記法を増やさない」「データを持たない」という設計原則の直接の帰結として意図的に空けてある場所だと理解しているが、書いている最中は「これは shitae の外なのか、まだ知らない書き方があるのか」の判断がその都度必要で、初見の書き手には地味にコストが高かった。SPEC の「扱わないもの」節にもう少し「こういう要件は自然文でこう逃がす」という具体例（特に反復・永続化のような頻出パターン）が1つずつあると、今回のような判断の迷いはかなり減ると思う。

もう1点、variant を「状態の違い」だけでなく「呼び出し文脈の違い」（学習言語選択のオンボーディング／設定変更）に使えるかどうかが SPEC の例だけでは確信を持てなかった。使ってみた感触としては自然で気に入っているが、これが正しい使い方だという裏付けが欲しい。
