# podcast.shitae 執筆メモ

新規ユーザーとして `docs/SPEC.md` のみを読み、他のファイル（GLOSSARY・AI_GUIDE・examples・実装・過去の stress-test 記録）は一切参照せずに書いた。以下は迷い・確信度・諦めた表現の記録。

## (a) 参照した SPEC の節

- two-layer model（component / variant）— 全体構造
- document common（54〜72行）— プッシュ通知のドキュメント共通インタラクション、前方参照の可否
- transition verb 一覧・フレーム木・switch（中断と復帰）・タブの慣用句（347〜394行）— タブ 3 枚の設計をほぼそのまま踏襲
- present / dismiss は compound verb（396〜423行）— ダウンロード確認モーダル、フルプレイヤーの提示
- セッション・出口固定の慣用句（316〜333行）— ログアウトの `exit(@tabHome)`
- オーバーレイ（453〜472行）— ミニプレイヤーの `show`/`hide`
- 操作は variant に属する（207〜273行）— 再生速度の variant 設計
- collection（540〜549行）、inline component（497〜521行）— カード一覧の書き方
- 記号一覧・EBNF（76〜201行）— quoted name、alias、`.` 参照の文法確認

## (b) 曖昧で迷った点

1. **タブバーの `.` 参照先が未定義 component でよいか**
   SPEC 自身の「タブの慣用句」の例（381〜383行）が `タブバー.検索` のように、`# タブバー` という component 定義を一度も書かずに member 参照している。これをそのまま踏襲して `タブバー.ホーム` / `タブバー.検索` / `タブバー.ライブラリ` と書いたが、`.` 参照が指す「対象インスタンスの body」（233〜235行の presence gate の説明で言及される概念）が、そもそも定義のない component に対してどう解決されるのか SPEC 本文には説明がない。SPEC の例をそのまま信頼して採用した（確信度: 中。SPEC 自身がやっているので構文的には通ると判断したが、意味論の説明が本文になく不安が残る）。

2. **プッシュ通知の行動記法に丸括弧をどう使うか**
   `> プッシュ通知（新着エピソード）をタップ -> push(エピソード詳細)` は全角括弧（）を自然文の一部として使い、構造上の丸括弧 `(` `)`（半角）と衝突しないようにした。EBNF は `"("` `")"` の字面のみを定義しており、全角括弧が同一視されるかどうかは書かれていない。全角なら地の文として素通りされると判断したが確信は無い（確信度: 低）。半角で `タップ(新着エピソード)` と書くと「新着エピソード」が行動対象（reference）として解釈され、未定義 component への行動という別解釈になり得るため避けた。

3. **variant 名に `.` を含めてよいか（`1.5x`）**
   再生速度の 3 段階変化を variant で表現する際、`## 1.5x` と裸で書くと、`.` が「記号一覧」で要素参照の予約記号として使われているため、bare-name の一部として `.` を含めてよいか判断できなかった。安全側に倒し `## "1.5x"` と quoted name にした（確信度: 中）。他の 2 つ（`1x` / `2x`）は `.` を含まないので裸のままにした——結果として同じ variant 集合の中で quote の有無が混在する見た目になったが、意味的には正準値（quote を剥いだ文字列）で一致するので問題ないはずだと判断した。

4. **push 通知の遷移先を push にするか present にするか**
   通知タップ時、ユーザーが `present` で開いたモーダル（ダウンロード確認・フルプレイヤー）の中にいる可能性もある。その場合 `push(エピソード詳細)` は「現在アクティブなフレーム」に積まれるため、モーダルの上にエピソード詳細が積まれる形になり、`back` で戻るとモーダルに戻ってしまう（タブ画面には戻らない）。実アプリなら「通知タップで一旦モーダルを閉じてからルートへ」のような処理を期待しそうだが、SPEC のセッション出口固定慣用句（`exit(@S) ; push(X)`）は特定の @S を名指しする必要があり、「今開いているセッションが何であってもとにかく畳んでから通知先へ」という汎用的な書き方は用意されていない。今回は SPEC 自身の document common 例（61行目、単純な `push`）に忠実に単純な `push` のままにした（確信度: 中〜低。実用上は妥協）。

5. **ログアウトをどの画面に置くか**
   タスクは「ログアウトで全タブ・全状態を畳んでログイン画面へ」とだけ指定し、UI 上の設置場所までは指定していない。SPEC のタブ慣用句の例ではログアウトを `# ホーム` に直接書いていたが、実アプリの通例に寄せて `# ライブラリ`（アカウント関連が集まりやすいタブ）に置いた。`exit(@tabHome)` はアクティブパス上に @tabHome の祖先フレームが必ずあるため、どのタブから呼んでも正しく動くはず、という理解で選んだ（確信度: 高。フレーム木の親子関係から構造的に導ける）。

## (c) 各設計判断の確信度

| 判断 | 確信度 | 理由 |
|---|---|---|
| タブ 3 枚を `switch` + 兄弟規則で実装 | 高 | SPEC のタブ慣用句をほぼそのまま適用しただけ |
| ログイン → `present(ホーム, @tabHome)` を単一アンカーにする | 高 | SPEC の canonical 例と同型 |
| 番組詳細→エピソード一覧→エピソード詳細を素の `push` 連鎖にする | 高 | push の基本用法どおり |
| ダウンロード確認を `present` + `dismiss()` の無名セッションにする | 高 | SPEC の削除確認モーダル例と同型 |
| ミニプレイヤーを overlay（`show`/`hide`）で実装 | 高 | 「常時表示されうる component」の定義に完全一致 |

## (d) 書けなくて諦めた表現・欲しかった記法

1. **再生速度の「アプリ全体での持続」が書けない**
   `フルプレイヤー` を `dismiss()` して閉じ、ミニプレイヤーから再度 `present(フルプレイヤー)` すると、埋め込んだ `再生速度` component は新規インスタンスとして毎回 initial variant（`1x`）から始まる。「1.5x に設定したら、次に開いた時も 1.5x のまま」という、実際のポッドキャストアプリなら当然期待される持続を shitae では表現できなかった。これは SPEC が明示的にデータ／コンテキストの保持を「扱わないもの」としているため仕様上の想定内ではあるが、体験してみると「単一の値が画面をまたいで生き続ける」という要求は podcast アプリに限らずかなり頻出しそうで、variant では吸収しきれない。**欲しかった記法**：オーバーレイのように「フレームの生死と無関係に状態が生き続ける」性質を、オーバーレイでない通常 component の一部にも persistent な variant として持たせる何らかの機構（あるいは、オーバーレイ側に持たせて外部から見えるようにする軽量な参照方法）。

2. **「通知タップで今開いているものを何であれ一旦畳んでからエピソード詳細へ」が書けない**
   `exit(@S) ; push(X)` の出口固定慣用句は @S を名指しする必要があり、「アクティブパス上のすべてのモーダル・セッションを、名前を知らずに畳む」操作が無い。document common に置く汎用インタラクションでは「今どんなセッションが開いているか」を知りようがないため、この慣用句は使えない。**欲しかった記法**：`back` のようにアクティブパスを畳むが barrier を無視して root（あるいは指定した特定フレーム）まで戻れる、名前を問わない「畳んで戻る」操作。ただし SPEC の設計原則（専用記法を増やさない）を踏まえると、これが本当に要るかは設計者の判断を仰ぎたい。

3. **「Now Playing（フルプレイヤー）画面の上にはミニプレイヤーを出さない」を明示的に書けない**
   これは SPEC 自身が 466 行目で「初版では見送る」と明言している既知の制限。今回のフローでもフルプレイヤーが開いている間、裏でミニプレイヤーが overlay として掲示され続ける（見た目上は重なる可能性がある）ことになるが、shitae 側の記法が無いので `podcast.shitae` では特に手当てしていない。実装は自然文注記で回避するしかない。

4. **番組・エピソードの「実データ」への参照ができない**
   通知からの遷移先を「どの番組のどのエピソードか」まで指定できない（props/引数が無い）。`push(エピソード詳細)` は常に同じ単一 variant のエピソード詳細画面を指すだけで、具体的にどのエピソードかは自然文の要素行（`エピソードタイトル` 等）で示すしかない。これも SPEC の意図的な範囲外（データ／コンテキストを扱わない）と理解しているので「諦めた」というより「最初から無いと知っていた」に近いが、podcast アプリのようにコンテンツ主体のアプリだと地味に効いてくる制約だと感じた。

## (e) 仕様の誤読しやすい箇所の指摘

- **「document common からは前方参照が可」（70行目）と「component common からは前方参照可能か」が非対称**。document common の前方参照は明記されているが、component common（`##` より前）や variant 内から、まだファイル中に定義されていない component を参照してよいかは明示されていない。おそらく可（未定義 component は常に許容されると読めるため）だが、「前方参照」という言葉が document common の節にしか出てこないため、通常の component 定義の中でも同じことができるのか一瞬迷った。
- **`.` 記号がオーバーロード気味に見える**：要素参照の `.`（1段まで）と、モジュール参照の `::`、variant 参照の `##` が並記されているが、「なぜ `.` だけ 1 段制限が付くのか」の理由（E014 の存在）は文法表の近くには無く、「記号一覧」の説明文に埋もれている。EBNF だけを見て書いていると、`.` の 1 段制限に気づかず `箱.内箱.b` のような多段参照を書きそうになった（実際には書かなかったが、EBNF の `reference` 定義をよく見ないと見落としそうな注意点だった）。
- **`switch` の兄弟規則の説明（369行目）は 1 回読んだだけでは追いにくい**。「現在フレームが switch 製なら兄弟、switch 製でなければ子」という条件分岐を、タブ 3 枚を自分で図に描いて確認するまで正しく適用できているか確信が持てなかった（最終的には「ホームだけが switch 製でない → 検索・ライブラリはどちらもホームの子（＝兄弟同士）になる」という理解に落ち着いたが、文章だけでは初見の理解コストが高い）。
- **`present` のセッション省略時の挙動（無名セッション）と `dismiss()` の対応が、多段 present のケースで直感と少しずれる**：ダウンロード確認モーダルを開いている最中に別のフルプレイヤーの `present` が重なるような状況は今回は作らなかったが、「`dismiss()` は直近の無名セッションを 1 つだけ畳み、途中の named session は道連れにする」（402行目）という規則は、逆に named session を `dismiss()` で畳もうとした場合にどう見えるか（無視されて素通りされるだけで named 自体は残る、という理解でよいか）を注記で確認したくなった。

## 一行要約（曖昧点・諦めた表現）

- 曖昧点: タブバーの `.` 参照先が未定義 component でよいかの意味論、variant 名に `.` を含めてよいか、通知遷移の push/present 選択、全角括弧が構造記号と衝突しないかの扱い。
- 諦めた表現: 再生速度など「アプリ全体で持続する単一の値」の表現、通知からの「今開いているものを何であれ畳んでから遷移」、Now Playing 画面でミニプレイヤーを隠す記法、通知先エピソードの具体的データ参照。
