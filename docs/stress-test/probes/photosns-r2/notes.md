# 写真共有SNS アプリ設計記録

## 参照したSPEC節

- **transition verb** (§276-452): push/back/goto/exit/present/dismiss/switch の使い分け
- **switch（中断と復帰）** (§362-372): タブ間の状態保持の実装
- **タブ慣用句** (§373-394): ホームタブとsub-tabsの階層構造
- **variant** (§23-50): 状態遷移表現（フォロー前/後、新着あり/なし）
- **document common** (§54-72): グローバルアクセス可能なインタラクション（通知）
- **操作は variant に属する** (§207-273): presence gate (`?`) の意味論
- **collection** (§540-550): `*投稿カード` の複数性表現

---

## 曖昧で迷った点と選択理由

### 1. バッジ表示位置：Home variant vs Feed variant

**迷った二択：**
- (a) フィードコンポーネント自体に新着バリアントを持たせる
- (b) ホームコンポーネント（タブバー親）のバリアントで管理する

**選択：(b)** ホームで管理

**理由：**
- バッジは「フィードタブアイコンの上に乗る」UI要素で、フィード画面内容ではなくタブバー操作の状態
- ホームコンポーネントが`#ホーム > ## 新着あり / ## 通常`で持つことで、タップして消える挙動が自然に表現できる
- `goto(##通常)`は同じホームコンポーネント内での状態遷移なので、タブ切替と並行して実行可能

### 2. 投稿作成フローの段階設計：別コンポーネント vs 同一コンポーネント内variant

**迷った二択：**
- (a) 撮影/編集/キャプションを1つの`#投稿作成`コンポーネントの3 variantにする
- (b) 各段階を独立した`#撮影`, `#編集`, `#キャプション`コンポーネントにする

**選択：(b)** 独立コンポーネント

**理由：**
- 各段階のUI/インタラクションが大きく異なる（カメラ→画像編集→テキスト入力）
- `push(編集)` → `push(キャプション)`で深さが自然になり、`back()`で段階的に戻れる（要件「途中でキャンセル可」に対応）
- 同時に`dismiss(@postCreation)`で任意の段階からセッションごと破棄可能（SPEC「present ＋ 無 barrier なし child」のモデルに従う）

### 3. フィード開放後のバッジ消去タイミング

**迷った二択：**
- (a) バッジはサーバーデータドリブン（新着投稿件数）で、自動同期
- (b) ユーザーがフィード**タブを開く**という明示的なアクションで消去

**選択：(b)** タップしたときに明示的に消去

**理由：**
- 要件は「フィードを開くと消える」と明示的
- shitaeは状態式を評価しない（SPEC「状態の条件式・ガード・並行状態」は扱わない）
- サーバーの投稿数をガード条件にできないため、ユーザーアクション（タップ）を証拠にする
- `> タップ(タブバー.フィード) -> switch(フィード, @tabFeed) ; goto(##通常)`で実装

### 4. 通知詳細がない形での通知ディープリンク

**迷った二択：**
- (a) 通知をタップ → 通知詳細画面 → その中から投稿/プロフィールへ
- (b) 通知をタップ → 直接投稿詳細/プロフィールへ（要件「直行導線」）

**選択：(b)** + 通知コンポーネントも用意

**理由：**
- 要件「通知（いいね・フォロー）からの直行導線（どの画面に居ても）」は document common で
  - `> サーバーからいいね通知を受け取る -> push(投稿詳細, @notification)`
  - `> サーバーからフォロー通知を受け取る -> push(プロフィール, @notification)`
- 同時に通知一覧画面(`#通知`)も用意して、ユーザーが通知アイコンをタップした場合に対応
- 両方あれば、アプリが push notification（バナー）と in-app notifications（アイコン）の両方に対応できる

### 5. フォロー状態：variant の用途

**迷った二択：**
- (a) プロフィール画面は1つ。フォローボタンのラベル/挙動を条件式で変える
- (b) プロフィール自体が`##フォロー前` / `##フォロー済み`variantを持つ

**選択：(b)** variant を持つ

**理由：**
- SPEC「操作は variant に属する」が示す設計パターン：「いつ何ができるか」を variant の有無で表現
- フォロー前には「フォローボタンがある」、フォロー後には「フォロー解除ボタンがある」という構造的な違いを素直に表現できる
- `goto(##フォロー済み)` / `goto(##フォロー前)` で状態遷移が読みやすい
- 各 variant で独立したインタラクションセットを定義でき、shadow ルール（variant 固有が共通を上書き）で重複を避けられる

### 6. ストーリーサムネイル の presence gate

**迷った二択：**
- (a) ストーリーサムネイルを常に表示（ユーザーがストーリーを持たないなら空）
- (b) ストーリーを持つユーザーの variant だけストーリーサムネイルを表示

**選択：(b)** + presence gate `ストーリーサムネイル?`

**理由：**
- すべてのユーザーがストーリーを持つわけではない、という現実的な状況を shitae で表現する手段
- SPEC「presence gate（`?`・opt-in・構造的 presence）」は「対象が実効 body に存在するか」を判定
- `タップ(ストーリーサムネイル?)` で「ストーリーがあれば表示」を構造的に表現

## 各設計判断の確信度

| 判断 | 確信度 | 理由 |
|------|--------|------|
| タブ navigation (`switch`) | 高 | SPEC 例示が明確。タブ慣用句に従った |
| バッジ variant 位置 | 中 | 仕様に明示例がないが、Home を親にする設計が妥当と判断 |
| セッション名 (@tabFeed 等) | 高 | SPEC タブ慣用句に直接従う |
| 投稿作成の dismiss/back 両立 | 高 | SPEC barrier なし push のモデルに一致 |
| 通知のdocument common | 高 | SPEC deep link 例示に対応 |
| フォロー state variant | 高 | SPEC「操作は variant に属する」の直接適用 |
| 本当のバッジ消去タイミング | 低～中 | 要件は明確だが、shitae では data-driven state change を表現できない。ユーザー action に頼る折衷案 |

## 書けなくて諦めた表現・欲しかった記法

### 1. **データドリブン variant 遷移**

**欲しかったもの：** フィードの新着投稿数が 0 になったら自動的に `##通常` へ遷移

**現状の制約：**
- SPEC は条件式を評価しない（`if count > 0` のような guard 条件なし）
- condition label `[新着あり]` は「分岐の目印」にすぎず、実行時に評価されない
- 唯一の「条件」は presence gate (`?`) で、これも構造的 presence（「element がある」）だけ

**代替手段：**
- サーバーからの通知ベースで `goto(##新着あり)` → ユーザーがフィード tab を開く → `goto(##通常)`
- ラフ設計として妥協できるが、真の「新着が0になったら自動消去」は実装の領分

**改善提案：**
- `goto(##variant [条件])` のような条件付き variant 遷移か
- または、外部イベント (`@イベント名`) をセッションと同じく参照できるメカニズム
- （ただし spec 設計原則「条件式を持たない」に反するので慎重に）

### 2. **multi-instance overlay / badge への ID 割り当て**

**欲しかったもの：** 複数の投稿カードがあるとき、特定のカード上だけにバッジを出したい（未読のカードだけハイライト等）

**現状の制約：**
- SPEC「ID は component 名が兼ねる。同一 component の多重掲示は初版では扱わない」
- overlay / badge は「component 全体」の单位でしか表現できない

**代替手段：**
- 各投稿カードを独立した component にする（`カード1`, `カード2`, ...）→ 名前爆発
- または、フィード内に複数の「未読ハイライト」という要素を持つ構造を作る

**改善提案：**
- collection 要素への ID ないし key 属性（例：`*投稿カード @id=投稿ID`）
- または、後処理で component 名 + data id を合わせる仕組み

### 3. **戻り先の明示的な指定**

**欲しかったもの：** `dismiss() ; push(固定先)` より簡潔な戻り先指定

**現状：**
```
> 公開 -> exit(@postCreation) ; push(フィード)   // 2 step
```

**代替案：**
```
> 公開 -> exit(@postCreation, @tabFeed)           // compound で戻り先指定？
```

**理由：**
- 「出口は常にホーム」等の要件は SPEC 例示でも `exit() ; push()` 形式（2 step）
- ラフさの許容範囲として今は OK だが、実装に向かう時点で冗長性が目立つ

**改善提案：**
- `exit(@S) -> 戻り先`のような syntax
- ただし文法を増やすことになるので、`->` の意味が変わる注意が必要

### 4. **モーダルのバリエーション（sheet / dialog / fullscreen）**

**欲しかったもの：** `present(撮影)` だけで「どんな見せ方か」を指定したい

**現状の制約：**
- SPEC「`present` は専用セッション名を予約しない。「モードに入る」遷移全般に使う」
- 画面上の見せ方（全画面・シート・ダイアログ）は shitae スコープ外（Figma 等の領分）

**代替手段：**
- 自然文で注記：`> present(撮影) // 全画面カメラモード`
- または、コンポーネント名に含める：`#撮影_全画面` / `#撮影_シート`

**改善提案：**
- `present(コンポーネント##variant) ; // hint: fullscreen` のようなコメント convention
- または、styleguide として component naming rule を定める（例：`_sheet`, `_dialog` suffix）

### 5. **条件付き back() の戻り先制御**

**欲しかったもの：**
```
> back() -> [スタック深さ > 1] back() ; [スタック深さ == 1] dismiss()
```

つまり、「戻る先がなければ dismiss、あればそこへ」という条件付き分岐

**現状：**
- SPEC では back が barrier/戻り先なしで no-op になる仕様
- condition label は「動的に判定されない注記」なので、実行時の stack depth を判定できない

**代替手段：**
- 各コンポーネント側で「戻る」「閉じる」を明示的な 2 つのボタンにする
- または、UI framework レベルで back/dismiss を使い分ける

**改善提案：**
- `back-or-dismiss()` のような compound verb か、戻り先の検出を shitae で表現可能に

### 6. **collection の順序・索引**

**欲しかったもの：** `*投稿カード[i]` / `*投稿カード.最新` のような要素へのアクセス

**現状の制約：**
- SPEC「collection は順序を保証しない。前後関係（次の・最後の等）が要るなら condition label や自然文で注記」

**代替手段：**
- 自然文：`> スクロール(*投稿カード) -> 続きを読み込む // chronological order guaranteed`
- または、specific components: `#最新投稿`, `#古い投稿`

**改善提案：**
- `*投稿カード [順序: 降順 / 昇順]` みたいなメタデータ syntaxか
- もしくは、collection を「iterableな component」として variant 可能に

## 仕様の誤読しやすい箇所・指摘

### 1. **presence gate (`?`) は「element が body に存在するか」であって「値が空でないか」ではない**

- 初読時、`いいね数 > 0 ?` のような data condition かと思った
- SPEC「構造的 presence... 対象と同名の alias または ref が element-line として書かれているかだけを見る」と明確
- つまり、`いいね数` という要素が variant の body に書かれているかどうかだけが条件

### 2. **condition label は「評価しない注記」で、分岐の行き先は「ラベルの目印」**

- `[成功] goto(結果)` と `[失敗] show(エラー)` が並んでいても、実装時どちらに行くかは shitae 外で決まる
- shitae は「分岐があるな」という構造だけ提供し、条件判定は実装が行う
- これは仕様表現としては「ラフ」だが、逆に言うと「決定がまだ」という設計意図を明確にできる

### 3. **goto は「新規セッションを開始できない」が「既存の begin マーカーは保持」**

- `push(A, @S) → goto(B) → exit(@S)` で @S の begin 地点に戻る
- 初読時、goto は セッションスタックに影響しないと思ったが、実は begin マーカーは保存される
- 「積まない置き換え」だから begin 地点は変わらないというロジック

### 4. **switch の「兄弟規則」は tree shape の歴史依存性を防ぐ**

- 「現在フレームが switch 製なら兄弟、そうでなければ子」
- これがないと、タブ訪問順によって tree 構造が変わり、`exit(タブ1)` が後から訪れたタブ 2 を巻き込む事故が起きる
- 設計の複雑性を最小化するための工夫だが、初読では「なぜこんなルールが要るのか」が不明確だった

### 5. **document common に裸の `##variant` は書けない**

- document common には母体 component がないため、`##variant` だけでは variant 遷移先が定まらない
- `component##variant` の形で、遷移元 component を明示する必要がある
- 「なぜ document common はこんなに制限があるのか」は SPEC の「遷移先の variant 指定は必ず `##variant` の形」節から導かれる

### 6. **inline の入れ子は 1 段が上限**

- `{ { ... } }` は構文エラー
- 「それ以上の階層が要るなら名前付き `#` component に昇格させろ」という示唆だが、この line が無いと「なぜ2重括弧ダメなのか」が不明

## 最終的な設計選択のサマリー

| 機能 | 実装方針 | 根拠 |
|------|---------|------|
| **タブ** | Home (`@tabHome`) > {Feed, Discover, Me} (`@tabFeed` etc via `switch`) | SPEC タブ慣用句 |
| **バッジ** | Home の variant (`##新着あり` / `##通常`) | UI hierarchy + goto transition 自然性 |
| **投稿作成** | 独立 component (撮影→編集→キャプション) + `present(..., @postCreation)` | 段階的 back + dismiss 両立 |
| **通知ディープリンク** | document common + 個別の通知詳細画面も用意 | 「直行導線」要件 + 柔軟性 |
| **フォロー状態** | プロフィール variant (`##フォロー前` / `##フォロー済み`) | SPEC「操作は variant」の適用 |
| **ストーリー** | `present(ストーリー閲覧)` で fullscreen modal | モード性 + dismiss で元画面へ復帰 |

## 確認すべき点（次フェーズ向け）

1. **バッジ消去の実装タイミング：** ユーザーが フィード tab をタップしたときだけでよいのか、それとも フィード content を見始めた時点か
2. **投稿作成中のデータ永続化：** draft 保存機能があれば present → dismiss → present でしたら状態復帰は何をするのか
3. **複数デバイス間の状態同期：** フォロー state 等の変更が他デバイスに反映されるまでのディレイ許容度
4. **オフライン挙動：** 通知受信が server-driven だが、network offline 時の fallback
5. **ストーリーの長さ：** 1 story = 1 image か、複数 stories の sequence か（コンポーネント設計に影響）
