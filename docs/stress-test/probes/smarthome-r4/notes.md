# smarthome-r4 notes

エントリファイルは `main.shitae`（先頭 component は `起動`）。`devices.shitae` にデバイス（singleton）を、`automation.shitae` にオートメーション一覧・ウィザードを分離した。

## 参照した SPEC の節

- two-layer model（component / variant）、document common（最初の `#` より前）と component common（`##` より前）の 3 階層共通性
- singleton component（`#!`）と state verb `set`（「画面 A の出来事で画面 B の状態を書き換える」の唯一の手段）
- transition verb 対応表、`present`/`dismiss` compound verb、セッション（`@S`）と「出口固定の慣用句」`exit(@S) ; push(固定先)`
- オーバーレイ（`show`/`hide`）— 全画面常時表示・掲示中 singleton への `set` の即時反映
- 「操作は variant に属する」節、特に「A の状態で別要素 B への操作を制御する場合は host の variant を分けて set で追随させる」というガイド
- モジュール化（`import`/`as`/`::`）、singleton 共有はファイル単位という規則
- collection（`*`）、inline（`{}`）、扱わないもの（データ・props 不保持）
- 診断コード表（E029/E030/E028 など、set と singleton まわりの制約確認に使用）

## 設計判断と確信度

1. **セキュリティモードバナー＝singleton overlay**（`#!セキュリティバナー`、常時 `show` で掲示、タップで `push(モード切替)`）。確信度：高。オーバーレイは「全画面で表示・掲示中 singleton への set は即時反映」と明記されており、要件2に最も直接対応する構成だと判断した。
2. **モード切替は `set` で banner とホームの両方を書き換える**（`モード切替` 画面はホーム/バナーどちらでもない第三の画面なので、対象への反映はすべて `set` 経由）。確信度：高。
3. **ホームも singleton にした**（`#!ホーム`）。理由：就寝ボタンの表示可否を「就寝モードである」という外部状態に追随させたいが、SPEC は「A の状態で B への操作を制御する gate」を明示的に禁止し、host の variant を分けて `set` で追随させよと指示している。host（ホーム）の variant を外部（モード切替画面）から書き換えるには対象が singleton である必要があるため。確信度：高（SPEC の指示に忠実に従った結果、必然的にこの構成になった）。
4. **起動時の初期化は `set(セキュリティバナー##在宅) ; show(セキュリティバナー)` の順**（`show(X##v)` 一発ではなく set→show の順にした）。理由：SPEC は singleton への明示 variant 付き `show` を「表示選択ではなく状態の巻き戻し」と述べており、起動時であっても意味論上は同じ扱いになると読んだため、意図を明確にするため set で初期化してから無指定 `show(X)` で「現在の共有値をそのまま掲示」する形にした。確信度：中（結果は同じだが、そもそも起動時の explicit-variant show が「巻き戻り」警告の対象になるのか、SPEC には初回起動を特別扱いする記述がなく判断が割れた）。
5. **デバイスは online/offline の 1 軸だけを持たせ、電源 on/off は入れなかった**。確信度：中〜高。理由は下の「諦めた表現」参照。
6. **部屋詳細・デバイス詳細を部屋・デバイスの数だけ複製した**（`リビング`/`寝室`、`リビング照明`/`リビングエアコン`/`寝室ドア鍵`）。確信度：高。SPEC が明言する「component への引数・props は扱わない」の直接の帰結で、他に取りうる設計がない。
7. **オートメーション作成ウィザードの入口を2つ用意した**（一覧の作成ボタン、リビング照明画面の「オートメーションを作成」）。確信度：中。要件文の「完了時は必ずオートメーション一覧へ戻る（どこからウィザードに入っても）」という書き方から複数入口を想定していると読み、`present(...,@wizard)` の入口を複数にして `exit(@wizard) ; push(オートメーション一覧)` の出口固定慣用句が効くことを確認する構成にした。
8. **おやすみ解除は行き先を常に「在宅」に固定した**（就寝前が外出だった場合の復元はしない）。確信度：中。shitae はデータを持たないため「元のモードを覚えていて戻す」は表現できず、固定の行き先にするしかないという判断。ユーザー要件は「解除できる」とだけ言っており行き先までは指定していないため、これは書き手の補完。

## 曖昧だと感じた点

- **document common のスコープが「アクティブフレームの最上段 component が定義されているファイル」単位**という規則により、`main.shitae` に置いた「デバイスの外部要因オフライン化」イベントは、ユーザーが `devices.shitae`（他のデバイス詳細画面）や `automation.shitae`（一覧・ウィザード）を見ている間は発火経路として存在しない。要件は「デバイス詳細を開いていなくても」なので `main.shitae` 側の画面（ホーム・部屋詳細等）にいる間に発火できれば要件の字面は満たすが、「本当にどの画面からでも起こりうる外部事象」を1箇所に書く手段が無く、モジュールごとに同じ行を複製するか、対象ファイルのどれがアクティブでも定義に到達できるよう祈るしかない。これは document common の設計上の限界だと思うが、SPEC 本文はこの複数モジュール間のギャップについて明言していない。
- singleton への明示 variant 付き `show`（`show(X##v)`）が「巻き戻り」として警告されるのは、状態がすでに書き換わった後の再訪問を想定した書きぶりに読めるが、**起動直後でまだ一度も状態が書き変わっていない singleton** に対して同じ扱いをするのが妥当か迷った（上記判断4）。

## 書けなくて諦めた表現・欲しかった記法

- **element-line の参照はモジュール修飾を書けない**。文法上 `element-line`（`ref = name`）はモジュール名を持てず、`::` が書けるのは `reference`（行動対象）と `nav-target`（遷移先）だけだった。そのため「他モジュールで定義した component を、そのまま画面の要素として置く」ことができず、必ず「その場限りのローカルな未定義 component（同名のラベル）を要素として置き、タップ時の遷移先だけ `モジュール::component` で指定する」という回避策を踏んだ（`main.shitae` の `リビング`/`寝室` 画面で `リビング照明` 等をローカルな裸ラベルとして置き、`push(devices::リビング照明)` で実体へ飛ばした）。これは動くが、「見えている物」と「実際に遷移する先」が字面上別々の名前空間の同名語であることに気づきにくく、初見の書き手が事故りやすい。**要素行でも `モジュール::component` を書けるようにするか、少なくとも lint で「他モジュール component と同名のローカル未定義要素」を検出してほしい**。
- **variant は単一軸の enum なので、独立した2つの状態（オンライン/オフライン と 電源オン/オフ）を同時に持たせたい場面で組合せ爆発する**。デバイスに「オンライン中に電源を切り替えられる」も表現したかったが、正しくやるなら `##オンライン_オン` `##オンライン_オフ` `##オフライン` の3つ（あるいはオフライン中の電源状態も保持するなら4つ）が要り、軸が増えるたびに指数的に増える。今回は要件が明示した「オンライン/オフライン の見た目」だけを残し、電源操作は「タップで点灯・消灯する」という1つの自然文の副作用に丸めて逃げた。**variant の直交する2軸を「compose して1つの実効 variant として扱う」ような合成記法があると、この手のデバイス状態は書きやすくなる**と感じた。
- **「元のモードを覚えていて戻す」が書けない**。おやすみ解除で「就寝前のモードに戻す」を書きたかったが、shitae はデータ・変数を持たない設計なので「直前の値を覚えて後で使う」に対応する記法が無い。固定の行き先（在宅）にするしかなく、これは SPEC の「扱わないもの」に明記された制約なので想定内ではあるが、実際に手を動かすと地味に手が止まった箇所だった。
- **「単一インスタンスだが複数体ある」を表す中間の粒度が無い**。singleton（`#!`、ファイル内で完全に単一）と通常 component（インスタンスごとに独立、しかも非 singleton には他画面から `set` で書き込めない）の二択しかなく、「デバイスごとに1つずつだが、デバイスの種類は増減しうる」を1つの component 定義で表す手段がない。今回は3台なので component を3つ複製して凌いだが、台数が10, 20と増える家庭用アプリでは同じ定義の複製が延々と続くことになり、ラフスケッチとしての速さが失われる。**「名前付きインスタンス（キー付き singleton）」のような、複製せずに複数の独立した共有状態を持てる中間の記法があれば、この種のIoTデバイス一覧のようなドメインでは特に欲しい**。
