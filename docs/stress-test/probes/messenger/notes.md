# messenger.shitae 作成メモ

## (1) 参照した SPEC の節

`docs/SPEC.md` を通読した上で、特に以下の節を繰り返し参照した。「two-layer model」（component と variant）、「記号一覧」、「文法（EBNF 風）」、「transition verb」全体（push/goto/back/exit、present/dismiss/switch の compound verb）、「セッション（`@S`）」「フレーム木」「switch（中断と復帰）」「タブの慣用句」、「present / dismiss は compound verb」、「操作は variant に属する」中の「variant はインスタンスごとに独立」、「collection（`*`）」、「inline component とグルーピング」、「document common（最初の `#` より前）」、「戻り先が無いとき」。特にタブ実装は「switch（中断と復帰）」の「タブの慣用句」がそのまま手本になった。

## (2) 仕様が曖昧・不明瞭と感じた点

**a. 1 回のインタラクションで transition を 2 つ連ねてよいか（該当節: 「未定・分岐」「行動（インタラクションの左辺）」「文法」の result-list）。** SPEC には「効果（自然文）＋ 1 つの transition」を `;` で並べる例（`アカウントを削除する ; exit(@loggedIn)`）はあるが、transition を 2 つ連ねる例（`switch(...) ; push(...)` のような）は見当たらない。今回「連絡先のプロフィールから『メッセージを送る』を押すとタブがチャットに切り替わり、かつそのスレッドが開く」「プッシュ通知でどの画面からでも該当スレッドが開き、タブもチャットになる」という要件がまさにこの形を要求したため、result-list の文法上は複数 result を並べられる（`result-list = result , { (";"|newline) , result }`）ことを根拠に「先に switch、続けて push が順に効く」と解釈して書いた。ただし SPEC 本文に明記された意味論ではないため確信度は中程度に留まる。

**b. `switch` は「そのタブの現在位置」に復帰するのであって「そのタブの先頭」に戻るわけではない（該当節: 「switch（中断と復帰）」）。** プッシュ通知やプロフィールからの「メッセージを送る」で `switch(チャット一覧, @tabChat) ; push(スレッド)` と書いたが、`switch` が復帰させる先は「そのフレームの最上段の (component, variant)」であり、ユーザーがチャットタブ内で既にスレッドを開いていた場合はそのスレッドの上にさらに `push(スレッド)` が積まれる形になる。「タブを切り替えて “その” スレッドへ直接ジャンプする」という現実のメッセンジャーアプリの挙動と、「タブは中断位置に戻る」という shitae の switch のモデルは完全には一致せず、この食い違いをどう解決すべきかは SPEC からは読み取れなかった。今回はそのまま `switch` の素直な意味論に従って書いた。

**c. `起動` を明示的な component として立てる必要（該当節: 「タブの慣用句」）。** 最初、`チャット一覧` をファイル先頭 component としてそのままエントリポイントにし、そこから他タブへ `switch` する案も検討した。しかし「タブの 1 枚目だけが switch 製でないと switch で重複フレームを作ってしまう」という注意書きを読み、`チャット一覧` 自体をエントリポイント（無名ルートフレームの中身）にしてしまうと anchor frame（`@tabChat`）が存在しないままになり、後で `switch(チャット一覧, @tabChat)` した際に新規フレームが作られて元の閲覧位置を失うおそれがあると判断した。そのため `# 起動` という薄い component を立て、`present(チャット一覧, @tabChat)` で anchor frame を明示的に作る構成にした。この判断が SPEC の意図どおりかは確信が持てず（起動画面という要件は無かったため、なくても良い設計だったかもしれない）、確信度は中とした。

**d. 「どのスレッドか」「誰宛てか」をデータとして持てない（該当節: 「扱わないもの」中「データ／コンテキスト」）。** これは曖昧というより仕様上の明確な非対応だが、実装しようとして初めて実感した曖昧さとして記録する。「連絡先 A のプロフィールから送るとスレッド A が開く」「連絡先 B なら B のスレッドが開く」を区別する記法が無いため、`スレッド` という単一 component にすべての相手とのやり取りが収束する形で書かざるを得なかった。

## (3) 使った主要構文ごとの確信度

- `#` component 定義、`>` インタラクション行、`->` 行動→結果: 高。SPEC の例と 1 対 1 で対応させて書けた。
- `##` variant 定義・参照（`スレッド行` の 未読/既読）: 高。「操作は variant に属する」の例とほぼ同型。
- `*` collection（`*スレッド行` `*メッセージ` `*連絡先` 等）と、参照時に 1 インスタンスを指すという意味論: 高。
- `名前: 実体` alias（`追加ボタン: "＋"` `メッセージを送るボタン: "メッセージを送る"`）: 中。ラベル文字列をそのまま quoted-name の参照先に据えて「ボタンの見た目＝ラベルテキスト」を表す使い方は SPEC に直接の例が無く、自分で類推した用法。文法上は妥当なはずだが、意図した用途と合っているかはやや自信が薄い。
- `.` 要素参照（`タブバー.チャット` 等、未定義 component への `.要素alias`）: 中〜高。SPEC の「タブの慣用句」例がまさに未定義の `タブバー` に対して `.検索` `.ホーム` を使っており、それに倣った。ただし `タブバー` を `#` で明示定義しなかった点は、SPEC の作図規約として許容範囲か多少の迷いがある。
- `push` / `back`（暗黙）: 高。「スレッドから戻るとチャット一覧」は明示の `back()` を書かず、`push` の裏返しとして構造的に成立すると解釈した（SPEC の各例も戻るボタンを毎回明記していないため）。
- `present` / `dismiss`（画像ビューア、宛先選択モーダル、プロフィール編集の保存後 back）: 高。「present は『モードに入る』遷移全般」という説明と直結しており迷いは少なかった。ただし `プロフィール編集画面` の保存を `back()` にした点は「モーダルというよりページ遷移」という判断で、`dismiss` にすべきか `back` にすべきかは要件からは決めきれず、通常の画面遷移（`push` で来た）とみなして `back()` にした。
- `switch` + `@S` によるタブ実装: 中。基本の resume-or-create・兄弟規則・anchor frame の理解には高い確信を持てたが、(2)-b で書いた「タブ切り替え＋特定スレッドへの直接ジャンプ」の複合は SPEC が明示していない領域での類推。
- document common（プッシュ通知のインタラクション）: 中。「どの画面からでも起こる」の用途例（deep link）とは一致するが、遷移先がタブ横断＋スレッド特定という複合だったため（2）-a, b の不確実性がそのまま乗る。

## (4) 書けなかった／回避した表現、欲しかった記法

- **「どの相手とのスレッドか」を区別できない。** 連絡先ごと・通知ごとに異なる相手とのスレッドへ遷移する、という要件の核の部分は、shitae のデータ非対応の原則上、単一の `スレッド` component に丸めるしかなかった。これは shitae の設計原則（原則 2: 専用記法を増やさない、「扱わないもの」: データ／コンテキストは実装の関心）を素直に適用した結果であり、「書けない」というより「意図的に書かない」に近い。ただし読み手（人間）がこの図を見て「相手ごとに別スレッドがある」ことを正しく読み取れるかは怪しく、コメント（自然文）で毎回補足する必要があった。専用記法が欲しいとまでは思わないが、「component インスタンスに人間可読な自然文の注記を軽く添える」ことがコメント (`//`) 以外の形でもう少し目立つ形であればありがたい、とは感じた（今回は `//` コメントで代替した）。
- **タブ切り替え＋深い階層へのジャンプの複合遷移。** (2)-a, b の通り、`switch` と `push` を `;` で連ねる書き方で回避したが、「タブを切り替えた上でそのタブの “特定の場所” へジャンプする」という複合操作に対する専用の言い回しは無く、SPEC の例からの外挿になった。もし今後この複合パターンが頻出するなら、`switch(X, @S) then push(Y)` のような「switch 後に相手フレームへさらに積む」ことを明示できる軽量な記法（新しい予約語ではなく、既存 `;` の意味論として「複数 transition を順に適用してよい」という一文が SPEC に明記されるだけでも十分）があると、今回のような外挿をせずに済むと感じた。
- **未読/既読の見た目差はスレッド行の variant としてそのまま書けた**（SPEC の「variant はインスタンスごとに独立」がまさにこの用途を想定しており、諦めた点ではなく綺麗に書けた点として記録する）。

## (5) その他 DSL への感想・改善案

- タブ・モーダル・プッシュ通知的 deep link・戻る操作、という今回要求された程度の画面遷移は、「記号一覧」に載っている 7 語の transition verb と `@S` セッションだけでほぼ過不足なく表現できた。特に「present と push+セッションの違い（barrier の有無）」の説明が明快だったおかげで、モーダル（画像ビューア・宛先選択）とタブ（switch）の使い分けで迷うことはなかった。
- 一方で「未読なので `#` で定義した」`スレッド行` のように、リストの各行専用の component を切り出すか、`チャット一覧` の中に inline で書くかの判断が最初迷いどころだった。inline component は `##` variant を持てない（「inline component とグルーピング」に明記）と気づいてから `# スレッド行` を独立 component にする方針へ切り替えたが、この制約（inline は要素のみ）は「記号一覧」の `{ }` の説明だけを読むと見落としやすく、EBNF の `inline = "{" , inline-body , "}"` の注記（`(* 要素のみ。variant(##)やインタラクション(interaction-line)は持たない *)`）を読んで初めて確信した。この制約は仕様として妥当だと思うが、「記号一覧」表の `{ ... }` の説明文にも一言（「variant やインタラクションは持たない」）を足すと迷いが減ると思う。
- 全体として、「状態を variant の列挙で表す」という原則（原則 6）は UI ラフスケッチとして書きやすく、if 文や変数を持ち出さずに未読/既読の差を表現できたのは実感として気持ちよかった。逆に「相手が誰か」のようなデータ的な情報を完全に排除する設計は、メッセンジャーのような「同じ画面の型を相手ごとに複数インスタンス使う」アプリでは、遷移グラフの可読性という点でやや物足りなさを感じた（(4) で書いた通り）。ただしこれは shitae が意図的に選んだトレードオフ（原則 1: ラフであることが機能、実装の関心を持ち込まない）として理解しており、DSL の欠陥というよりスコープの外側だと考えている。
