# 初見の再試行

入口は http://127.0.0.1:8875/ui-proposal.html 。独立した新しいタブで始める。前回の報告・設計書・HTMLやJavaScriptソース・期待値・検証ログは読まない。画面から到達できる資料ページを読んでよい。自然文の目的から操作を選び、操作前に予測を記録する。操作手順やボタン名の答えは渡さない。

1. 同僚から大阪出張の申請記録を引き継いだ。金額は途中で訂正されたらしい。訂正前後の金額、訂正が起きた操作、差し戻された理由を履歴から調べ、操作を続ける位置を変えずに説明する。
2. 再申請の最初の結果から続けることを検討する。一度取り消してから、その位置へ移る。後の「支払いを予約する」がどう扱われるか説明する。
3. 画面外の文書Bの状態について、読み込んだ時点と、いま操作を続ける位置を比較する。画面の案内と対応資料を使って実値まで確認する。足りなければ必要なものを述べ、推測しない。
4. 後の支払予約の画面を見ている状態で、用意された「前の画面に戻る」と申請取下げを順に試す。各操作の直前に、続ける位置・見ている画面・後の履歴に何が起こるか予測する。取下げ後、後の履歴で何が読めて何ができないか調べる。

各シナリオ：完遂/部分/未完、予測と結果、迷い・戻り・質問、表示位置/focus、良かった点・困った点、改善候補、模型と製品の証明の違いを報告。AXと代表画像を保存する。AXの画面外到達を人の目視操作成功と扱わない。

用語の提案：画面全体から難しい語を自分で挙げ、元の語、最初の解釈、誤解の危険、短い表示案、補足説明、正確さに残る懸念を表にする。現在の言い換えにも異論を出してよい。用語名だけでなく組合せの一貫性を評価する。専門知識がない人の実証にはしない。

資料確認担当は、画面の案内で見つけたコマンドとモデル/シナリオに限りCLI利用可。もう一人の用語担当はブラウザだけで試し、CLIが必要なところは自力でどこまで進めたかを報告する。ソースから答えを探さない。成果物は各自の/private/tmp専用ディレクトリだけに保存し、入力は変更しない。
