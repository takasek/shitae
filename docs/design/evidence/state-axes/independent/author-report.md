## 1. 状態ごとの分け方とその理由

再生・ダウンロード・曲情報の 3 つを、それぞれ別の singleton（`#! 再生` `#! ダウンロード` `#! 曲情報`）に分けました。
曲の詳細画面（`# 曲の詳細`）は 3 つを要素として置くだけです。

- 再生は `停止` / `再生中` / `一時停止` です。
- ダウンロードは `未ダウンロード` / `ダウンロード中` / `完了` / `失敗` です。
- 曲情報は `読込中` / `表示` / `読込エラー` です。

理由は、出来事を組み合わせたときに、片方の変更がもう片方の答えを消してはいけないからです。

- 「再生中 → ダウンロード完了」の後は、再生中のままで、ダウンロードだけが完了になるべきです。
  - 一つの集合にまとめると、最後に `set` した側が勝ちます。
  - ダウンロード完了が再生を消して `停止` 相当になるか、再生がダウンロードの状態を消すかのどちらかになります。
- 「ダウンロード中 → 画面の外から再生が止められる」の後は、ダウンロードは中のままで、再生だけが停止になるべきです。
- 「再生中 → 曲情報の読込失敗 → 再読込」の後は、再生は止まらず、曲情報は `読込エラー` から `読込中` に戻るだけです。
- 「再生中 → ダウンロード失敗 → 曲情報の再読込」の後は、再生が `再生中`、ダウンロードが `失敗`、曲情報が `読込中` で、3 つとも残ります。

3 つとも別々の出来事で変わり、同時に保持されます。
画面の外の出来事（通知で停止、ダウンロード完了・失敗、曲情報の読込完了・失敗）は、document common から遠隔で `set` します。
`set` は singleton にしか使えないので、遠隔から書く以上 singleton にする必要もありました。

各軸の内側は、同時に成り立たない姿なので、一つの variant 集合のままにしています。
再生なら「再生中かつ一時停止」はあり得ません。
曲情報の `読込中` / `表示` / `読込エラー` も同時には成り立ちません。
ダウンロードの `ダウンロード中` と `完了` も同様です。

分けなかった組合せについて、一つの注意点があります。
「再生中かつ曲情報が読込エラー」はモデル上ありえます。
実際の挙動としてそれでよいかは、ラフの段階では私に判断できませんでした（質問 4-3 に書きました）。

## 2. 分けるべき場合と、一つの variant 集合でよい場合（一般的な言葉で）

**分けるべき場合。**
二つの問いの答えが、別々の出来事で変わります。
そして、片方が変わってももう片方は元のまま残るべきです。
たとえば「ある作業が終わったか」と「別の作業が失敗したか」は、互いの更新で上書きされてはいけません。
一つの選択肢リストにまとめると、後から起きた出来事が、先の出来事の結果を消してしまいます。

**一つの variant 集合でよい場合。**
並べた選択肢が、同時には成り立たない姿です。
たとえば「読み込み中・表示中・エラー」や「分割表示・全画面表示」は、どれか一つだけが正しいことになります。
この場合に分けると、「表示中かつエラー」のようなあり得ない組合せがモデルに生まれます。
「将来独立するかもしれない」という理由では分けません。

見分け方は、出来事を二つ組み合わせたときに、答えが二つ並んで残るべきか、一方に置き換わるべきかです。

## 3. 根拠にした AI_GUIDE の記述
