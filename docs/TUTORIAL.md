# 予約の例で試す、戻り先と状態の残り方

shitae は、操作して、表示・戻り先・状態の残り方を確かめられる、UIフローの下書きです。予約画面を少しずつ育てながら、書いた定義と、実行中に残る状態を区別して試します。

各段階のコードは、それだけで使える全文です。一つの `booking.shitae` に順に置き換え、[READMEの準備手順](../README.md#使い方)を済ませてから `check` と `simulate` を実行します。生成HTMLをブラウザで開き、表の操作を上から試してください。段階を更新するとモデルが変わるため、前段階の再生ファイルは読み込まず新しく始めます。

```bash
node packages/cli/dist/index.js check booking.shitae
node packages/cli/dist/index.js simulate booking.shitae > booking.html
```

## 1. 一覧から詳細へ進み、戻る

**画面・部品の定義（component）**を `#` で書きます。ここでは二つとも画面として使います。`>` は操作、`->` の右側はその結果です。先頭に定義した一覧から始まります。

```shitae
# 一覧
本の一覧
> 詳細を開く -> push(詳細)

# 詳細
本の説明
> 一覧へ戻る -> back()
```

| 試す操作 | 確かめること |
|---|---|
| 詳細を開く | 詳細が開く。`push` は戻り先の一覧を残す |
| 一覧へ戻る | `back` で一覧に戻る |

表示要素の「本の説明」は模式的な内容です。実際の書籍データは読み込みません。

## 2. 同じ画面の状態を変える

詳細に**状態パターン（variant）**を足します。状態パターンは「その状態で何が見え、どの操作が定義されるか」の組合せです。最初の `##` より前の操作は全状態パターンに共通します。初めて詳細を開くと、先頭の「読込中」になります。

```shitae
# 一覧
本の一覧
> 詳細を開く -> push(詳細)

# 詳細
> 一覧へ戻る -> back()
> 予約する(予約ボタン?) -> 予約処理を想定する
## 読込中
読込表示
> 読込結果を試す -> [成功] goto(##表示) ; [失敗] goto(##読込失敗)
## 表示
本の説明
予約ボタン
## 読込失敗
エラーの説明
> 読み直す -> goto(##読込中)
```

| 試す操作 | 確かめること |
|---|---|
| 詳細を開く | 読込中。予約する操作は使えない |
| 読込結果を試す → 失敗 | 同じ詳細が読込失敗に変わる |
| 読み直す → 読込結果を試す → 成功 | 詳細が表示に変わり、予約する操作が使える |
| 一覧へ戻る → 詳細を開く | 新しく開いた詳細は読込中に戻る |

`goto(##表示)` は現在の画面の状態パターンを変えます。状態は扱いますが、データ値や条件式で計算するのではなく、名前を付けたパターンで表します。

ここで二つの判定を分けます。**対象の存在判定（presence gate）**の `予約ボタン?` は、参照先の現在の状態パターンに対象要素があるかを処理系が調べます。共通部分の要素も含み、画面上に見えているかは調べません。`?` を付けない操作は、対象要素の存在を条件にしません。未定義の参照先など、判定できない場合も有効として扱います。

一方、**試すケースの目印（condition label）**である `[成功]` と `[失敗]` は人が選びます。通信の成否を自動判定する機能ではありません。「予約処理を想定する」のような自由文も記録されるだけで、予約サービスを実行しません。

## 3. 確認の作業をまとめて閉じる

「予約する」の結果を `present(確認)` に変え、受取画面を加えます。**作業のまとまり（session）**は、内側の作業をまとめて終了する範囲です。`present` で入ったまとまりの入口では、通常の `back` で外へ出られません。

```shitae
# 一覧
本の一覧
> 詳細を開く -> push(詳細)

# 詳細
> 一覧へ戻る -> back()
> 予約する(予約ボタン?) -> present(確認)
## 読込中
読込表示
> 読込結果を試す -> [成功] goto(##表示) ; [失敗] goto(##読込失敗)
## 表示
本の説明
予約ボタン
## 読込失敗
エラーの説明
> 読み直す -> goto(##読込中)

# 確認
予約内容
> 受取を選ぶ -> push(受取)
> 取り消す -> dismiss()

# 受取
受取場所の説明
> 確認へ戻る -> back()
> 取り消す -> dismiss()
> 確定結果を試す -> [成功] dismiss() ; [失敗] エラーを想定する
```

| 試す操作 | 確かめること |
|---|---|
| 詳細を開く → 読込結果を試す → 成功 → 予約する | 確認へ入る。確認の入口から通常の「戻る」で詳細には出られない |
| 受取を選ぶ → 確認へ戻る | まとまりの内側では `back` で戻れる |
| 受取を選ぶ → 取り消す | 確認と受取をまとめて閉じ、詳細の表示に戻る |
| 予約する | 新しい確認が開く。前の受取位置には戻らない |

`dismiss()` は直近の**無名**のまとまりを閉じます。名前を付けたまとまりを閉じるときは `dismiss(@名前)` または `exit(@名前)` を使い、この二つは同じ操作です。`dismiss()` が単に最も近い名前付きの作業を閉じるわけではありません。

`present` は「ひとまとまりの作業に入る」指定です。ポップアップの形や、ほかの操作を禁止するかどうかは、この指定だけでは決まりません。

## 4. タブを離れて戻る

予約一覧のタブを加えます。先頭に起動を置き、一覧の作業に `@browse` という名前を付けて入ります。これにより、タブで一覧へ戻るときも同じ作業を指定できます。

「タブ」は複数の画面の要素に置く部品です。画面として使った一覧と同じ `#` の定義で、画面用と部品用の別の仕組みはありません。

```shitae
# 起動
> 始める -> present(一覧, @browse)

# 一覧
タブ
本の一覧
> 詳細を開く -> push(詳細)

# 詳細
タブ
> 一覧へ戻る -> back()
> 予約する(予約ボタン?) -> present(確認)
## 読込中
読込表示
> 読込結果を試す -> [成功] goto(##表示) ; [失敗] goto(##読込失敗)
## 表示
本の説明
予約ボタン
## 読込失敗
エラーの説明
> 読み直す -> goto(##読込中)

# 確認
タブ
予約内容
> 受取を選ぶ -> push(受取)
> 取り消す -> dismiss()

# 受取
タブ
受取場所の説明
> 確認へ戻る -> back()
> 取り消す -> dismiss()
> 確定結果を試す -> [成功] dismiss() ; [失敗] エラーを想定する

# タブ
> 本を探す -> switch(一覧, @browse)
> 予約一覧へ -> switch(予約一覧, @reservations)

# 予約一覧
タブ
予約の一覧
```

| 試す操作 | 確かめること |
|---|---|
| 始める → 詳細を開く → 読込結果を試す → 成功 | 詳細の表示にいる |
| 予約一覧へ → 本を探す | 一覧の先頭ではなく、詳細の表示に戻る |
| 予約する → 受取を選ぶ → 予約一覧へ | 確認の作業は画面外に残る |
| 本を探す | 名前を指定した一覧の作業の中断位置、詳細へ戻る。画面外の確認を自動で再開するわけではない |

`switch` は、名前を付けた作業が残っていればその中断位置へ戻り、なければ新しく始めます。「残っている作業」を開くと、画面外の確認も調べられます。ここを開閉するだけでは移動しません。確認を表示していなくても残っているため、「見えない」と「終了した」を区別できます。

## 5. 通知と共有状態を別に残す

予約の確定が成功したケースで、予約状態を更新し、通知を出してから確認を閉じます。**状態を共有する部品（singleton）**は `#!` で定義します。同じ定義を置いた使用箇所は、同じ実行内で状態パターンを共有します。

通知は**画面とは独立して残る表示（overlay）**です。`show` で出し、`hide` で外します。確認の作業を開閉する `present` と `dismiss` とは寿命が違います。

```shitae
# 起動
予約
> 始める -> present(一覧, @browse)

# 一覧
タブ
本の一覧
予約
> 詳細を開く -> push(詳細)

# 詳細
タブ
> 一覧へ戻る -> back()
> 予約する(予約ボタン?) -> present(確認)
## 読込中
読込表示
> 読込結果を試す -> [成功] goto(##表示) ; [失敗] goto(##読込失敗)
## 表示
本の説明
予約
予約ボタン
## 読込失敗
エラーの説明
> 読み直す -> goto(##読込中)

# 確認
タブ
予約内容
> 受取を選ぶ -> push(受取)
> 取り消す -> dismiss()

# 受取
タブ
受取場所の説明
> 確認へ戻る -> back()
> 取り消す -> dismiss()
> 確定結果を試す -> [成功] set(予約##予約済) ; show(通知) ; dismiss() ; [失敗] エラーを想定する

# タブ
> 本を探す -> switch(一覧, @browse)
> 予約一覧へ -> switch(予約一覧, @reservations)

# 予約一覧
タブ
予約の一覧
予約
> 閲覧を終了する -> exit(@browse)

#! 予約
## 未予約
未予約の表示
## 予約済
予約済の表示

# 通知
予約を受け付けた案内
> 通知を外す -> hide(通知)
```

| 試す操作 | 確かめること |
|---|---|
| 始める → 詳細を開く → 読込結果を試す → 成功 → 予約する → 受取を選ぶ | 受取にいる。予約は未予約、通知なし |
| 確定結果を試す → 失敗 | 受取に残り、予約は未予約、通知なし |
| 確定結果を試す → 成功 | 確認と受取が閉じ、詳細に戻る。予約は予約済、通知あり |
| 予約一覧へ | ここでも予約済。通知も残る |
| 閲覧を終了する | 一覧側と予約一覧側の作業が終了し、起動へ戻る。予約済と通知は残る |
| 通知を外す | 通知だけが消え、予約済は残る |

同じ定義の共有状態を `set` で変えると、ほかの使用箇所にも反映されます。共有はディスクへの永続保存や、別の利用者との共有を意味しません。ここでは固定の一つの予約を表しており、書籍IDごとの予約管理や在庫判定は扱いません。

## 設計を確かめる機能

ここまでに書いた操作を実行する機能と、検討用の機能を分けて使います。

| 機能 | 何をするか |
|---|---|
| 分岐選択 | 今回試したい成功／失敗のケースを選び、その結果を実行する |
| 状態の手動試験 | presence gate の参照先を検討用の状態パターンに変える。下書きの操作を実行した結果とは区別して記録される。参照先がないモデルでは試験対象はない |
| 履歴を見る | 過去の画面を閲覧する。現在の操作位置は変えない |
| そこから続ける | 確認後に操作位置を変える。再開するだけで未実行の結果が自動的に進むわけではない |

試す前に表の期待を書き、実行後の表示や「残っている作業」と照合します。処理系は設計者の意図を推測しません。

内部構造を追いたくなったら、[用語集のframe / frame tree](GLOSSARY.md#内部構造を調べるときの用語)と[SPEC](SPEC.md)へ進めます。frame は複数の画面を積む実行中の単位で、単に「画面」と読み替えると戻り先や親子関係を取り違えます。
