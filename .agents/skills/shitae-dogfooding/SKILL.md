# shitae のドッグフーディング

shitae を使って「UI フローを記述する・設計上の疑問を確かめる・結果を他者へ渡す・設計変更後に再検討する」という一連の仕事を実際に行い、実利用に残る問題と次の開発優先度を判断する。「当面は機能追加せず実利用を続ける」という結論も認める。

この評価は版ごとに繰り返す。対象版・前回評価・公開入口の文言・題材は実行時に解決し、このファイルに書かれた具体名を正としない。

## 範囲

評価と記録だけを行う。製品コード・SPEC・既存ガイドを変更しない。issue の作成・更新、commit・push・PR 作成をしない。評価用の派生モデル、小さな補助スクリプト、レポートは新規に追加してよい。

不具合を見つけても評価中に製品を直して対象を変えない。固定版の証拠と最小再現を残す。

前提が欠けたら迂回しない。依存取得の失敗、ブラウザに届かない、認証切れ等で想定の手順が動かないときは、別手段へ切り替えず、何が詰まったかと選択肢を利用者へ報告して指示を待つ。

## 1. 実行時に解決する値

着手時に次を解決し、成果物の README に記録する。

| 項目 | 解決方法 |
| --- | --- |
| 基準ブランチ | `git fetch origin` の後、`git ls-remote --symref origin HEAD` で確認する。local の `main` や `origin/HEAD` は古いことがある |
| 評価 SHA | fetch 後の `origin/<基準ブランチ>` の 40 桁。評価中に動いても追わない |
| 実施日・出力先 | `docs/dogfooding/<YYYY-MM-DD>-end-to-end/`。同名があれば上書きせず別名にする |
| 前回評価 | `docs/dogfooding/` のうちディレクトリ名の日付が最も新しいもの。README から対象版の SHA を読み（書式は回ごとに違う）、評価 SHA の祖先であることを `git merge-base --is-ancestor` で確かめる |
| 前回以降の変更 | `git log --oneline <前回SHA>..<評価SHA>` と、対応する ADR・design 文書 |
| 前回以降の評価記録 | `git diff --name-only --diff-filter=A <前回SHA> <評価SHA> -- docs/dogfooding docs/design | cut -d/ -f1-3 | sort -u` で、追加された評価・利用試行の記録をディレクトリ単位で列挙する。後から合流した古い日付の評価や、機能実装時の利用試行も確認済み範囲に含める |
| 前回の残課題 | 前回の候補表（例: `candidates.md`）と report の未確認範囲 |
| 既存 issue | `gh issue list --state all` 等で読むだけ |
| 公開入口と表示文言 | 手順と契約は評価 SHA の README、`docs/design/session-usage.md`、`docs/design/scenario-replay-contract.md`、`docs/design/gui-history-contract.md` から取る。GUI のボタン名は生成 HTML の実画面で確かめる。記憶・過去の記録・処理系のソースから書かず、使った文言を記録する |

## 2. 準備

1. 未コミットの作業を壊さないよう、評価 SHA の detached worktree を git 管理外で消えない場所に作る。既定は主 checkout 直下の `.worktrees/dogfood-<日付>` で、別の worktree の中に入れ子で作らない。一時ディレクトリは再起動で消えるため、利用者が後で開く成果物の置き場にしない。
2. 古い dist を使わず、README の手順どおり固定 lockfile から install・build する。依存取得が失敗したら署名検証の無効化や lockfile 更新で通さず、報告して止まる。
3. OS・Node・pnpm・ブラウザ（版が取れなければ未確認と書く）・評価者の構成と、CLI と生成 HTML が使う engineVersion・modelId を記録する。再開・再生の途中で処理系を更新しない。
4. 題材に使う既存モデルと過去証拠の hash を記録し、最後に変化がないことを確かめる。
5. 過去ディレクトリの検証スクリプトは出力先が旧 evidence を指していることがある。使う前に出力先と固定 SHA の扱いを読み、旧証拠を上書きするなら使わない。

入口文書は README、`docs/AI_GUIDE.md`、`docs/design/session-usage.md`、`docs/SPEC.md`（言語仕様の唯一の正）、上表の design 文書、前回評価のディレクトリ。既存の受入・評価記録は確認済み範囲と未確認範囲を把握するために使う。

## 3. 担当の分離

可能なら次の担当を、会話を引き継がない新しいコンテキストで動かす。

- **作成担当**: 通常の利用者向け文書からモデルを作り、操作して設計を検討する（作業 A）。
- **引継ぎ担当**: 作成担当の会話を引き継がず、共有された成果物から再現・説明・継続操作する（作業 C の後半）。

起動方法はハーネスに合わせる。Claude Code では Agent ツールで新規 subagent を起動し、会話を継承する fork は使わない。Codex では新しい subagent か別の会話を使う。どちらでもブリーフが唯一の伝達経路になる。

| 担当 | 渡すもの | 渡さないもの |
| --- | --- | --- |
| 作成 | 目的、自然文の要件の方針、評価 SHA の checkout と build 済み CLI の絶対パス、作業ディレクトリ、利用者向け文書の場所 | 過去の解答モデル・操作列・不具合レポート・候補表。`docs/dogfooding/` と過去の evidence は開かないよう明示し（README からリンクされている）、報告に読んだパスを列挙させて確かめる |
| 引継ぎ（閲覧・再開） | 目的と問い、生成 HTML、scenario、処理系版 | 作成側の会話、操作列、補助スクリプト |
| 引継ぎ（編集・再生成） | 上に加えてモデル一式・全参照 module・必要な simconfig | 同上 |

評価 SHA の checkout には過去の評価記録も含まれるため、隔離は指示と読んだパスの報告に頼る。その限界を README に書く。

ブリーフには「結論に file:line または保存した証拠のパスを付ける」「実行したコマンドを報告に含める」を入れる。戻った判定は一次資料でスポットチェックしてから採用する。

subagent がブラウザを操作できるか、同じブラウザ pane を親と取り合わないかを、委譲前に確かめる。操作できなければブラウザ部分は親が行い、その分担を記録する。別コンテキストを用意できない場合は「同一評価者による再確認」と明記する。新しい Session であることと初見の評価者であることを混同しない。

## 4. 作業 A — 入口から小さなモデルを作る

README と AI_GUIDE から、自然文の要件を小さな UI フロー一本にする。題材は検索→詳細→確認モーダル→取消・確定のように現実の設計判断を含むものにする。既存 example の写経にせず、全機能を試すための不自然な要件を詰め込まない。

先に次を短く記録する。

- 確かめたい設計上の疑問。
- 要件から期待する状態の所属・寿命・戻り先。
- 今回は表現しない実データ処理やレイアウト。

SPEC や session-usage は必要になったときに参照し、その理由を記録する。最初から処理系のソースを読んで実装の動作を期待値にしない。

check→HTML 生成→ブラウザ操作→案の修正→再生成まで行う。修正前後の HTML を固有名で保存し、取り違えずに比較する。

観察すること:

- README から検査・生成・開き方を発見できるか。
- check の warning/error と HTML 生成の成功を区別できるか。
- 記法・診断・SPEC への導線がモデルの誤りの修正に役立つか。
- 操作によって設計上の疑問に答えられたか。自然文だけでは見落としていたことを具体化する。
- ツール都合の回避策や不要なモデルの書き換えが生じたか。

「モデルが通った」だけでなく、設計検討に何が得られたかを残す。

## 5. 作業 B — 保存済みモデルで設計検討をやり直す

題材は次の順で選ぶ。

1. 前回以降の変更が触る機能を通る経路（新しい GUI・照会・保存機能の初の実利用になる箇所）。
2. 前回評価が「未確認」と記録した経路。
3. 前回評価が詳しく使った保存済みモデル（`docs/dogfooding/` 配下）。同じ名前（current/proposed 等）だけで選ばず、modelId で識別する。

原モデルは変更しない。各対象を check・生成し、実ブラウザでの詳しい評価は少なくとも二本行う。

問いはモデルと要件から立て、操作名と期待もそこから確かめる。操作前に予想を記録し、利用者向け表示か公開 CLI の照会で確かめる。部品の状態表示、操作一覧、action 詳細、state、history などを必要に応じて使い、どの情報で疑問を解消したかを記録する。

CLI では同じ process で照会→操作→照会を続ける。handle と branch は実際の応答から取り、受理操作の後は取り直す。毎回全状態・全履歴を取る専用 harness を先に作らない。利用上の不便が隠れるため、JSON Lines の送受信とファイル保存だけの薄い client にとどめる。

旧 issue の修正は既存回帰テストと関連する最小例で確認する。全境界条件の手作業での総当たりは主目的にしない。

## 6. 作業 C — 作業途中を保存し、別 Session・別担当へ渡す

作業 B で実際に検討した経路を使う。保存・再生のためだけの無意味な操作列にしない。同じ経路を使い回してよく、組合せを増やす必要はない。少なくとも次を行う。

- CLI で操作→export→process 終了→別 process で replay→継続操作。
- GUI で保存した scenario を CLI へ渡す。
- CLI で保存した scenario を新しい GUI Session へ読み込む。
- GUI で操作を続ける位置を結果の途中へ移し、後の点が ghost として残った状態を保存する。読込後にその地点から別の操作を行い、再保存・再開する。

保存・読込・位置変更の手順と文言は 1 節で解決した文書に従う。export 成功応答のうち scenario 部分だけを UTF-8 JSON に保存する。CLI に公開されていない seek を作らない。GUI では履歴を見ただけで操作位置が変わったと思わず、位置の変更を確定する操作まで行ったかを表示で確かめる。

GUI の保存はファイルのダウンロード、読込はファイル選択を伴う。使うブラウザ手段がダウンロードとファイル選択を扱えるかを先に確かめる。ブラウザ自動化の file chooser・file upload 機能で file input にファイルを渡すのは実操作に含める。ページの内部関数を呼ぶ、DOM や Session へ scenario を直接流し込むといった代替はしない。使っているブラウザ手段で扱えないときは、未確認にする前に利用者へ報告し、扱える手段（例: Claude Code なら Claude in Chrome のファイル送信）へ切り替えるかを尋ねる。切り替えない判断なら、その範囲を未確認とする。ダウンロードがハーネスの確認対象なら利用者に承認を求める。ダウンロードやファイル選択の呼出しが長く戻らないことがあるが、製品の性能問題と断定しない。

引継ぎ担当には目的・問いと 3 節の表の成果物だけを渡し、操作列を逐一教えて成功させない。引継ぎ担当は元の会話や作者の補助スクリプトに頼らず、「何を検討した記録か」「現在どの状態か」「どの分岐を選んだか」を説明し、次の操作を一つ行う。不足した情報、追加質問、開くファイルの迷いを記録させる。

特に確認すること:

- 同じ現在地に戻っただけでなく、途中の経路・分岐・状態の由来を説明できるか。
- 元 process のメモリや古い handle に依存せず再開できるか。
- 表示設定と実行状態の復元範囲を理解できるか。
- scenario にモデル本文が含まれないことが分かるか。
- reset 前や破棄した経路も保存対象であることを、共有前に理解できるか。

架空のデータを使い、共有不要な情報を成果物に含めない。

## 7. 作業 D — モデルを一箇所変更し、再検討する

実作業で得た設計上の疑問から小さな要件変更を一件だけ選ぶ。原モデルではなく派生コピーを編集し、変更前後の意図を記録する。

変更前の scenario を変更後モデルへ渡し、拒否を確認する。現行の照合契約（1 節で確認したもの）が要求する一致を満たさない拒否は、それだけで不具合に分類しない。

評価すること:

- 診断から不一致の対象・理由を理解できるか。
- 元のモデル一式へ戻れば作業を再開できるか。
- 新しいモデルで scenario を作り直す手順が分かるか。
- 変更前後の比較にどれだけ再入力・転記が要るか。
- GUI で不一致の保存物を読み込んでも、それまでの Session を失わず操作を続けられるか。

自動 migration、類似操作への自動対応、scenario の手編集で無理に通すことはしない。版固定が適切でも実利用上の負担が残るなら、「不具合」と「将来検討する利便性」を分けて記録する。過去に保存した scenario が旧 engine のため拒否されても直ちに回帰と扱わない。中心の比較には評価 SHA で新しく保存した scenario を使う。

## 8. 証拠と判定

各作業で次を必要最小限で記録する。

- 目的、期待、操作・分岐、実際の結果。
- 文書・モデル本文・実装コードへ戻った回数と理由。
- 操作特定や分岐選択の失敗、再入力、手動転記、引継ぎの追加質問。
- 結論を支える scenario、CLI 入出力、重要な画面の画像。

検証の種類を区別する。

- 実ブラウザ操作、headless/VM 検証、保存証拠の確認を区別する。DOM スタブや内部関数の呼出しを実ブラウザ操作と呼ばない。
- file URL を開けない環境では一時的な loopback HTTP で配信し、終了後に停止して停止を確かめる。実ブラウザを使えなければその範囲は未確認とする。
- CLI と GUI は共通エンジンなので、両者の一致だけでは意味の正しさを示せない。要件・SPEC から得た独立の期待と照合する。
- condition label は手動選択であり、自由記述の effect は実ファイル保存・通信・focus 移動などの成功を示さない。
- 測っていない過去の所要時間や負担と比べて改善率を作らない。初見 agent 一名の結果を人間一般の使いやすさに広げない。

問題は次に分類する。

- 処理系の不具合・回帰
- モデルの誤り
- ガイドや診断の不足
- 正しい結果を理解しにくい表示・照会
- 保存・共有・再検討の作業負担
- 仕様上の意図した制約

候補は既存 issue・完了済み実装・前回の候補表と照合し、重複や旧情報を除く。前回の残課題は今回の版で再確認し、解消・継続・未確認のどれかを付ける。頻度、作業を妨げる程度、回避策、最小変更で得られる効果から優先度を判断する。仕様変更や大きな基盤追加を最初の解決策にしない。

## 9. 成果物と最終報告

出力先には次を置く。

- `README.md`: 評価 SHA（次回が前回評価として読む行）、前回評価と比較の起点、環境、実施範囲、使った公開入口の文言、再実行入口。
- `report.md`: 作業ごとの効果・負担・問題・未確認事項。
- `models/`、`scenarios/`、`evidence/`: 再現に必要なものだけ。
- 改善候補の短い表（候補なしでもよい）。

最後に差分を確認する。`git status --short` と `git diff --stat <評価SHA>` で、変化が今回の出力先だけであり、原モデル・旧証拠・製品コードに変更がないことを示す。

チャットでの最終報告は次の順にする。

1. 一連の仕事を完遂できたか。
2. shitae によって判断できた設計上の事項。
3. 残った実利用上の問題。重要なものから最大 3 件。
4. 次に着手すべきこと、または機能追加を止めて実利用を続ける判断。
5. 未確認範囲と成果物の場所（絶対パス）。

## よくある誤り

| 誤り | 正しい扱い |
| --- | --- |
| local の `main` や `origin/HEAD` を最新とみなす | fetch 後に `ls-remote --symref` で基準ブランチを確かめ、`origin/<基準>` を固定する |
| 過去の記録や記憶にあるボタン名・コマンドで操作する | 手順は評価 SHA の session-usage・gui-history-contract、ボタン名は生成 HTML の実画面から取り、使った文言を記録する |
| 前回評価のディレクトリだけを確認済み範囲とみなす | 前回 SHA 以降に追加された評価・利用試行の記録も読む。合流順とディレクトリ名の日付は一致しないことがある |
| 前回と同じモデルを同じ問いで回すだけ | 前回以降の変更点と前回の未確認範囲から題材を選ぶ |
| 作成担当に過去の候補表や解答モデルを渡す | 作成担当には利用者向け文書だけを渡す。前回の残課題は親が後で照合する |
| 生成成功を check 通過とみなす | warning 付きでも生成は成功する。check の結果を別に記録する |
| 照合失敗を scenario の手編集で通す | 契約どおりの拒否として記録し、元のモデル一式へ戻るか新しく記録し直す |
| 検証スクリプトを再実行して旧 evidence を上書きする | 出力先を確かめ、新しい出力先へ向けるか使わない |
